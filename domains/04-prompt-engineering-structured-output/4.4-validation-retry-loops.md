# 4.4 Implement validation, retry, and feedback loops for extraction quality

## At a glance

- Retry-with-error-feedback: appending specific validation errors to the prompt on retry to guide the model toward correction.
- The limits of retry: retries are ineffective when the required information is simply absent from the source document (vs format or structural errors).
- Feedback loop design: tracking which code constructs trigger findings (`detected_pattern` field) to enable systematic analysis of dismissal patterns.
- The difference between semantic validation errors (values don't sum, wrong field placement) and schema syntax errors (eliminated by tool use).

## Example

### Validate, then retry with the specific errors

```python
import json
from pydantic import BaseModel, ValidationError, model_validator


class LineItem(BaseModel):
    description: str
    quantity: float
    unit_price: float


class Invoice(BaseModel):
    invoice_number: str
    stated_total: float | None
    calculated_total: float | None
    conflict_detected: bool = False
    line_items: list[LineItem]

    @model_validator(mode="after")
    def totals_match(self):
        # Semantic rule: the schema cannot express it, so code must catch it
        if self.stated_total is not None and self.calculated_total is not None:
            if abs(self.stated_total - self.calculated_total) > 0.01:  # tolerance absorbs rounding, not real mismatches
                raise ValueError(
                    f"stated_total {self.stated_total} != calculated_total {self.calculated_total}"
                )
        return self


def extract_with_retry(document: str, call_model, max_retries: int = 2) -> Invoice | dict:
    messages = [{"role": "user", "content": f"Extract the invoice.\n\n<document>\n{document}\n</document>"}]
    for attempt in range(max_retries + 1):
        raw = call_model(messages)            # returns the tool_use input dict
        try:
            return Invoice.model_validate(raw)
        except ValidationError as e:
            if attempt == max_retries:
                # Bounded retries: a persistent failure usually means the answer is not in the source, so stop and route to a human
                return {"status": "needs_review", "extraction": raw, "errors": e.errors()}
            # original document + failed extraction + the specific errors
            # Specific errors let the model fix the named fields instead of re-guessing the whole extraction
            messages.append({"role": "assistant", "content": json.dumps(raw)})
            messages.append({
                "role": "user",
                "content": f"Validation failed:\n{e}\n\nRe-read the document above and correct only "
                           "the fields that failed. If the information is not in the document, use null.",
            })
```

### Retry helps vs does not help

| Error | Retry works? |
| - | - |
| Date in the wrong format, value in the wrong field, totals mismatch from a misread | Yes: the information is in the document |
| Required value only exists in an external document you did not provide | No: nothing new to find; route to review or fetch the source |
| Field absent from the source | No: make it nullable and return `null` |

### Self-check fields in the schema

```json
{
  "stated_total": 500.00,
  "calculated_total": 500.00,
  "conflict_detected": false
}
```

Extract `calculated_total` next to `stated_total`, and a `conflict_detected` boolean when the source contradicts itself, so discrepancies are flagged instead of silently resolved.

### `detected_pattern` on review findings

```json
{
  "file": "billing.py",
  "line": 12,
  "severity": "high",
  "issue": "Bare except hides payment failures",
  "detected_pattern": "bare_except_pass"
}
```

When developers dismiss findings, group the dismissals by `detected_pattern` to see which constructs generate false positives and fix those prompts.

## Why this matters

> [!IMPORTANT]
> **The principle**

A retry only helps when the correct answer exists in the source. Validation turns silent errors into explicit, specific messages, and retry-with-feedback gives the model a chance to correct a misread. When the information is absent, a retry has nothing new to find and invites fabrication; the right response is a null value or routing to review. The design therefore separates three cases: syntax errors (removed by tool use), semantic errors that are fixable from the document (retry with the specific error), and absence or contradiction in the source (flag, do not retry).

**The flow**

- The `model_validator` encodes a semantic rule the schema cannot: stated and calculated totals must agree within a rounding tolerance. This is the check that catches what 4.3 says tool use cannot.
- On failure the retry sends the original document, the failed extraction and the specific validation error. The document is needed because the model must re-read the source; the failed output shows what was wrong; the error names which fields to fix. A bare "try again" restarts guessing and tends to reproduce the same mistake.
- The retry prompt says "correct only the fields that failed" and "if the information is not in the document, use null". The second clause is the safety valve that stops a retry loop from pressuring the model into inventing a value to satisfy the validator.
- `max_retries` bounds the loop. After the last attempt the result becomes `needs_review` with the raw extraction and the errors attached, so a person sees exactly what failed. Unbounded retries burn cost on cases that cannot succeed.
- The table of retry-works versus retry-does-not separates fixable errors (format, wrong field, misread totals) from structural impossibilities (value only in an external document, field absent). The second group needs a different remedy: nullable fields, fetching the missing document, or review.
- `calculated_total` beside `stated_total`, and `conflict_detected`, let the model report inconsistency instead of silently choosing one number. A flagged conflict is a reviewable event; a silently resolved one is a hidden error.
- `detected_pattern` on findings creates the feedback loop for review systems. Dismissed findings grouped by pattern show which constructs produce false positives, so prompt fixes target the real source of noise (links to 4.1).

## Trade-offs

- **Retry with feedback vs routing to a human immediately:** retry is cheap and fixes many format or misread errors; routing avoids wasted calls when failure is structural. A small retry limit combines both.
- **Validate in code vs ask the model to self-check:** code validators are exact and cheap; model self-checks are probabilistic. Self-check fields in the schema (calculated total, conflict flag) are still useful because they expose evidence for the code to compare.
- **Tolerance thresholds:** too tight causes spurious retries on rounding; too loose misses real errors. Set per field from observed data.
- **Retry cost vs accuracy:** each retry adds latency and tokens. In a batch pipeline, failed validations can be retried synchronously for only those documents (4.5).
- **Fetching missing context vs null:** if the information lives in another document the pipeline can obtain, fetch it and re-extract; if not, `null` plus review is correct.
- **`detected_pattern` vs free-text issue:** a controlled label supports aggregation at the price of one more field the model must fill consistently.

> [!WARNING]
> **Exam traps**

- "Retry until the validation passes": retries cannot create absent information and push the model to fabricate. Rule: retries help only when the information exists in the source.
- "Re-run the same prompt with no error detail": the model repeats its error. Rule: feed the specific validation error plus the document and the failed output back.
- "Use stricter JSON schema to catch the totals mismatch": a schema cannot compare fields. Rule: tool use removes syntax errors, not semantic errors.
- "Make the missing field required and retry": forces invention. Rule: absent field means nullable and `null`.
- "Silently choose the printed total when it disagrees with the line items": hides data quality problems. Rule: extract both and flag a conflict.
- "Aggregate false positive rates globally": hides which construct is noisy. Rule: track `detected_pattern` so dismissal analysis points to specific prompt fixes.

## Quick check

- Extraction fails validation because the invoice date came back as `03/04/25` while ISO format was required. Will a retry help? Yes; the information is in the document and the error is specific, so a retry with the error and the format rule should fix it.
- An invoice references "see attached purchase order" for the PO number, which is not provided. A retry returns different made-up numbers. What is wrong? The information is not in the available source; make the field nullable, return `null`, and route to review or fetch the attachment.
- Developers dismiss many review findings. How do you find out why? Record a `detected_pattern` on each finding and group dismissals by it to identify constructs that cause false positives, then fix those prompts.
