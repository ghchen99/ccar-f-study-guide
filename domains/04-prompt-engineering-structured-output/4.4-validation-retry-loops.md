# 4.4 Implement validation, retry, and feedback loops for extraction quality

> [!NOTE]
> **At a glance**
>
> - **Retry with feedback:** append the specific validation errors so the model corrects the named fields.
> - **Limit:** retries cannot recover information absent from the source; they only fix format or structural errors.
> - **Error types:** syntax errors are removed by tool use; semantic ones (totals, wrong field) need code validation.
> - **Feedback loop:** a `detected_pattern` field lets you group dismissed findings and find noisy constructs.

## Example

### Validate, then retry with the specific errors

```python
import json
from pydantic import BaseModel, ValidationError, model_validator


class LineItem(BaseModel):
    description: str
    quantity: float
    unit_price: float


class Invoice(BaseModel):
    invoice_number: str
    stated_total: float | None
    calculated_total: float | None
    conflict_detected: bool = False
    line_items: list[LineItem]

    @model_validator(mode="after")
    def totals_match(self):
        # Semantic rule: the schema cannot express it, so code must catch it
        if self.stated_total is not None and self.calculated_total is not None:
            if abs(self.stated_total - self.calculated_total) > 0.01:  # tolerance absorbs rounding, not real mismatches
                raise ValueError(
                    f"stated_total {self.stated_total} != calculated_total {self.calculated_total}"
                )
        return self


def extract_with_retry(document: str, call_model, max_retries: int = 2) -> Invoice | dict:
    messages = [{"role": "user", "content": f"Extract the invoice.\n\n<document>\n{document}\n</document>"}]
    for attempt in range(max_retries + 1):
        raw = call_model(messages)            # returns the tool_use input dict
        try:
            return Invoice.model_validate(raw)
        except ValidationError as e:
            if attempt == max_retries:
                # Bounded retries: a persistent failure usually means the answer is not in the source, so stop and route to a human
                return {"status": "needs_review", "extraction": raw, "errors": e.errors()}
            # original document + failed extraction + the specific errors
            # Specific errors let the model fix the named fields instead of re-guessing the whole extraction
            messages.append({"role": "assistant", "content": json.dumps(raw)})
            messages.append({
                "role": "user",
                "content": f"Validation failed:\n{e}\n\nRe-read the document above and correct only "
                           "the fields that failed. If the information is not in the document, use null.",
            })
```

### Retry helps vs does not help

| Error | Retry works? |
| - | - |
| Date in the wrong format, value in the wrong field, totals mismatch from a misread | Yes: the information is in the document |
| Required value only exists in an external document you did not provide | No: nothing new to find; route to review or fetch the source |
| Field absent from the source | No: make it nullable and return `null` |

### Self-check fields in the schema

```json
{
  "stated_total": 500.00,
  "calculated_total": 500.00,
  "conflict_detected": false
}
```

Extract `calculated_total` beside `stated_total`, plus a `conflict_detected` boolean when the source contradicts itself, so discrepancies are flagged, not silently resolved.

### `detected_pattern` on review findings

```json
{
  "file": "billing.py",
  "line": 12,
  "severity": "high",
  "issue": "Bare except hides payment failures",
  "detected_pattern": "bare_except_pass"
}
```

Group dismissed findings by `detected_pattern` to see which constructs generate false positives, then fix those prompts.

## How it works

> [!IMPORTANT]
> **A retry only helps when the correct answer exists in the source.** Separate three cases: syntax errors (tool use removes them), semantic errors fixable from the document (retry with the specific error), and absence or contradiction in the source (flag; do not retry).

1. **Encode semantic rules in code.** The `model_validator` checks stated against calculated totals within a rounding tolerance: what the schema cannot express ([4.3](4.3-structured-output-tool-use.md)).
2. **Retry with three inputs.** Send the original document, the failed extraction and the specific error; a bare "try again" restarts guessing and repeats the mistake.
3. **Allow null.** "If the information is not in the document, use null" stops the loop pressuring the model into inventing values.
4. **Bound the loop.** After `max_retries` return `needs_review` with the raw extraction and errors; unbounded retries burn cost on impossible cases.
5. **Remedy by cause.** Format, wrong-field and misread errors are retryable; absent fields need nullable, and external-only values need fetching or review.
6. **Surface conflicts and patterns.** `conflict_detected` makes inconsistency reviewable; `detected_pattern` aims prompt fixes at real noise sources ([4.1](4.1-explicit-criteria.md)).

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Retry with feedback | Cheap; fixes many format and misread errors | Wasted calls when failure is structural. A small retry limit with human routing combines both |
| Code validators vs model self-check | Exact and cheap | Self-check is probabilistic, but its fields (calculated total, conflict flag) expose evidence for code to compare |
| Tolerance threshold | Absorbs rounding | Too tight causes spurious retries; too loose misses real errors. Set per field from data |
| Synchronous retry | Fixes failed documents quickly | Latency and tokens per retry. In a batch, retry only the failures synchronously ([4.5](4.5-batch-processing.md)) |
| Fetch missing context vs `null` | Fetch when the pipeline can obtain it | Otherwise `null` plus review is correct |
| `detected_pattern` vs free text | Supports aggregation | One more field to fill consistently |

> [!WARNING]
> **Exam traps**
>
> - **"Retry until validation passes"** → retries cannot create absent information and push the model to fabricate. They help only when the information exists in the source.
> - **"Re-run the same prompt with no error detail"** → the model repeats its error. Feed back the specific error, the document and the failed output.
> - **"Stricter JSON schema to catch the totals mismatch"** → a schema cannot compare fields. Tool use removes syntax errors, not semantic ones.
> - **"Make the missing field required and retry"** → forces invention. An absent field means nullable and `null`.
> - **"Silently choose the printed total when it disagrees"** → hides data quality problems. Extract both and flag a conflict.
> - **"Aggregate false positive rates globally"** → hides which construct is noisy. Track `detected_pattern` so dismissals point to specific prompt fixes.

## Check yourself

<details>
<summary>Validation fails because the invoice date came back as <code>03/04/25</code> when ISO format was required. Will a retry help?</summary>

Yes; the information is in the document and the error is specific, so a retry with the error and the format rule should fix it.
</details>

<details>
<summary>An invoice says "see attached purchase order" for the PO number, which is not provided, and retries return different made-up numbers. What is wrong?</summary>

The information is not in the available source. Make the field nullable, return <code>null</code>, and route to review or fetch the attachment.
</details>

<details>
<summary>Developers dismiss many review findings. How do you find out why?</summary>

Record a <code>detected_pattern</code> on each finding and group dismissals by it to identify constructs causing false positives, then fix those prompts.
</details>
