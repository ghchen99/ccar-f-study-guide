# 4.5 Design efficient batch processing strategies

> [!NOTE]
> **At a glance**
>
> - **Message Batches API:** 50% cheaper, up to 24-hour window, no latency SLA.
> - **Fit:** non-blocking, latency-tolerant work (overnight reports, weekly audits, nightly test generation); never blocking checks such as pre-merge.
> - **Limit:** single-turn only; client-side tools cannot run mid-request and return results.
> - **Correlation:** `custom_id` pairs each request with its result.

## Example

### Pick the API by latency need

| Workflow | API |
| - | - |
| Blocking pre-merge check | Synchronous Messages API |
| Overnight technical-debt report, weekly audit, nightly test generation | Message Batches API (50% cheaper, up to 24h, no latency SLA) |

### Create a batch with `custom_id`

`custom_id` must match `^[a-zA-Z0-9_-]{1,64}$` and be unique. Results can come back in any order, so correlate by `custom_id`.

```python
import anthropic
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"


def make_request(doc_id: str, text: str) -> Request:
    return Request(
        # Results return in any order; this id is the only link between a result and its document
        custom_id=f"doc-{doc_id}",
        params=MessageCreateParamsNonStreaming(
            model=MODEL,
            max_tokens=2048,
            messages=[{"role": "user", "content": f"Extract the invoice fields.\n\n{text}"}],
        ),
    )


batch = client.messages.batches.create(requests=[make_request(i, t) for i, t in docs.items()])
```

### Poll, then stream results and sort out failures

```python
import time

# Polling, not waiting on a response: the batch is asynchronous with no latency guarantee
while (batch := client.messages.batches.retrieve(batch.id)).processing_status != "ended":
    time.sleep(60)

succeeded, retry_same, needs_fix = {}, [], []
for result in client.messages.batches.results(batch.id):
    outcome = result.result
    if outcome.type == "succeeded":
        succeeded[result.custom_id] = outcome.message
    elif outcome.type == "errored":
        # Split by cause: resubmitting a request-level failure unchanged would fail the same way
        if outcome.error.error.type == "invalid_request_error":
            needs_fix.append(result.custom_id)    # e.g. exceeded context: chunk the document, then resubmit
        else:
            retry_same.append(result.custom_id)   # server error: resubmit unchanged
    else:  # "expired" or "canceled": not billed
        retry_same.append(result.custom_id)
```

Resubmit only the failed IDs, with changes where needed (e.g. split an oversized document into chunks with new `custom_id`s such as `doc-17-part1`). Result types: `succeeded`, `errored`, `canceled`, `expired`. One failure does not affect other requests.

### Submission frequency against an SLA

```text
Requirement: results within 30 hours of document arrival. A batch can take up to 24 hours.
Worst case = wait for the next submission window + 24h processing.
  window  4h -> 4 + 24 = 28h  <= 30h  OK
  window  8h -> 8 + 24 = 32h  >  30h  breaks the SLA
So submit at least every 6 hours; 4 hours leaves margin.
```

### Refine on a sample first

Run the prompt synchronously on ~20 representative documents, fix recurring failures, then submit the full batch. This lifts first-pass success and avoids paying for resubmission.

### Limits worth remembering

- Up to 100,000 requests or 256 MB per batch; results kept 29 days; batches expire after 24h.
- No `stream`; no `max_tokens: 0`.
- A batch request is one-shot: client-side tools cannot run mid-request. (Server tools such as web search do.)

## How it works

> [!IMPORTANT]
> **Choose the API by the latency contract, not cost alone.** Batches trade a 50% discount for asynchronous processing with no latency guarantee: right for work nobody waits on, wrong for anything blocking a person or pipeline. One system can use both.

1. **Split by workflow.** A blocking pre-merge check uses the synchronous API; overnight, weekly and nightly jobs use batches.
2. **Correlate by `custom_id`.** Results arrive in any order, so only the id links a result to its document and traces partial failures.
3. **Branch on result type.** Keep `succeeded`; split `errored` by cause; resubmit `expired` and `canceled` unchanged.
4. **Resubmit only failed ids, fixing the cause first.** A request-level error (oversized input) fails identically again, so chunk it (`doc-17-part1`); transient server errors resubmit as is. Successes are never paid for twice.
5. **Size the window from the worst case.** A document arriving just after submission waits a full window plus 24h: for a 30h SLA the window is at most 6h, so 4h leaves margin. Daily submission breaks it.
6. **Sample first.** Refining on ~20 documents synchronously avoids paying for and waiting on a full resubmission.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Batch | Half the cost | No predictability. If a human or merge gate waits, use synchronous |
| Synchronous | Immediate results, simple control flow | Full price |
| Batch with timeout fallback to synchronous | Appears to give both | Second code path, double-processing risk, primary path still has no latency guarantee. Unjustified for a blocking workflow |
| Small, frequent windows | Lower worst-case wait, no extra per-request cost | More orchestration. Infrequent large batches are simpler but can violate SLAs |
| Resubmit as is vs modify | Straight resubmission suits transient failures | Request errors need a change (chunking, trimming); treating both alike wastes cost or loops |
| Sample first | Saves resubmitting a large batch | A little synchronous spend and time up front |

Tasks needing tool calls mid-task run synchronously in an agent loop; batch cannot host them.

> [!WARNING]
> **Exam traps**
>
> - **"Switch everything to batch for the 50% saving" (Q11, B)** → the pre-merge check blocks developers and batch has no latency SLA, whatever typical completion times are.
> - **"Switch both to batch with a real-time fallback on timeout" (Q11, D)** → adds complexity without addressing that one workflow is latency-sensitive. Don't add infrastructure that misses the diagnosed cause.
> - **"Keep both real-time because batch results are unordered" (Q11, C)** → `custom_id` solves correlation; ordering is irrelevant.
> - **"Resubmit the whole batch when some requests fail"** → wasteful. Resubmit only the failed ids.
> - **"Retry an oversized document unchanged"** → fails identically. Modify the request (chunk it).
> - **"Submit once per day because batches finish in 24 hours"** → ignores wait before submission. Worst case is window plus processing time.
> - **"Use batch for a tool-using agent"** → client tools cannot run mid-request. Multi-turn tool calling needs the synchronous path.
