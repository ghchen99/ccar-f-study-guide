# 4.5 Design efficient batch processing strategies

## Knowledge of

- The Message Batches API: 50% cost savings, up to 24-hour processing window, no guaranteed latency SLA.
- Batch processing is appropriate for non-blocking, latency-tolerant workloads (overnight reports, weekly audits, nightly test generation) and inappropriate for blocking workflows (pre-merge checks).
- The batch API does not support multi-turn tool calling within a single request (cannot execute tools mid-request and return results).
- `custom_id` fields for correlating batch request/response pairs.

## Skills in

- Matching API approach to workflow latency requirements: synchronous API for blocking pre-merge checks, batch API for overnight/weekly analysis.
- Calculating batch submission frequency based on SLA constraints (e.g., 4-hour windows to guarantee 30-hour SLA with 24-hour batch processing).
- Handling batch failures: resubmitting only failed documents (identified by `custom_id`) with appropriate modifications (e.g., chunking documents that exceeded context limits).
- Using prompt refinement on a sample set before batch-processing large volumes to maximize first-pass success rates and reduce iterative resubmission costs.

## Code snippets

### Pick the API by latency need

| Workflow | API |
| - | - |
| Blocking pre-merge check | Synchronous Messages API |
| Overnight technical-debt report, weekly audit, nightly test generation | Message Batches API (50% cheaper, up to 24h, no latency SLA) |

### Create a batch with `custom_id`

`custom_id` must match `^[a-zA-Z0-9_-]{1,64}$` and be unique. Results can come back in any order, so correlate by `custom_id`.

```python
import anthropic
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"


def make_request(doc_id: str, text: str) -> Request:
    return Request(
        # Results return in any order; this id is the only link between a result and its document
        custom_id=f"doc-{doc_id}",
        params=MessageCreateParamsNonStreaming(
            model=MODEL,
            max_tokens=2048,
            messages=[{"role": "user", "content": f"Extract the invoice fields.\n\n{text}"}],
        ),
    )


batch = client.messages.batches.create(requests=[make_request(i, t) for i, t in docs.items()])
```

### Poll, then stream results and sort out failures

```python
import time

# Polling, not waiting on a response: the batch is asynchronous with no latency guarantee
while (batch := client.messages.batches.retrieve(batch.id)).processing_status != "ended":
    time.sleep(60)

succeeded, retry_same, needs_fix = {}, [], []
for result in client.messages.batches.results(batch.id):
    outcome = result.result
    if outcome.type == "succeeded":
        succeeded[result.custom_id] = outcome.message
    elif outcome.type == "errored":
        # Split by cause: resubmitting a request-level failure unchanged would fail the same way
        if outcome.error.error.type == "invalid_request_error":
            needs_fix.append(result.custom_id)    # e.g. exceeded context: chunk the document, then resubmit
        else:
            retry_same.append(result.custom_id)   # server error: resubmit unchanged
    else:  # "expired" or "canceled": not billed
        retry_same.append(result.custom_id)
```

Resubmit only the failed IDs, with changes where needed (e.g. split an oversized document into chunks with new `custom_id`s such as `doc-17-part1`). Result types: `succeeded`, `errored`, `canceled`, `expired`. One failure does not affect other requests.

### Submission frequency against an SLA

```text
Requirement: results within 30 hours of document arrival. A batch can take up to 24 hours.
Worst case = wait for the next submission window + 24h processing.
  window  4h -> 4 + 24 = 28h  <= 30h  OK
  window  8h -> 8 + 24 = 32h  >  30h  breaks the SLA
So submit at least every 6 hours; 4 hours leaves margin.
```

### Refine on a sample first

Run the prompt synchronously on ~20 representative documents, fix recurring failures, then submit the full batch. It lifts first-pass success and avoids paying to resubmit.

### Limits worth remembering

- Up to 100,000 requests or 256 MB per batch; results kept 29 days; batches expire after 24h.
- No `stream`; no `max_tokens: 0`.
- A batch request is one-shot: your client-side tools cannot run mid-request and feed results back. (Server tools such as web search do run within the request.)

## Commentary: the concepts behind the code

SDK names are illustrative; know the concept, not the exact parameter.

### The design decision

Choose the API by the latency contract of the workflow, not by cost alone. The Batches API trades a 50% discount for asynchronous processing of up to 24 hours with no latency guarantee. That is right for work nobody is waiting on (overnight reports, weekly audits, nightly test generation) and wrong for anything that blocks a person or a pipeline (a pre-merge check). Cost optimisation is applied per workflow: the same system can use both APIs.

### Walk-through

- The workflow table is the decision itself: blocking pre-merge check uses the synchronous API; overnight, weekly and nightly jobs use batches. A mixed system splits by workflow rather than picking one for everything.
- `custom_id` ties each result to its source document. Results can arrive in any order, so position in the response list carries no meaning. Without ids, a partial failure cannot be traced to a document and the whole batch would need resubmitting.
- The loop branches on the result type. `succeeded` is kept; `errored` splits by cause; `expired` and `canceled` are resubmitted unchanged. The split matters because a request-level error (for example an input too large for the context window) will fail again identically unless the input changes, whereas a transient server error may succeed on resubmission.
- Only failed `custom_id`s are resubmitted. One failed document does not invalidate the others, so resubmitting the entire batch pays twice for the successes.
- Chunking an oversized document into `doc-17-part1`, `doc-17-part2` with new ids is the modification that addresses the diagnosed cause (size) rather than retrying blindly.
- The SLA arithmetic works from the worst case: a document arriving just after a submission waits a full window and then up to 24 hours of processing. For a 30-hour guarantee the window must be no more than 6 hours; 4 hours leaves margin. Daily submission would break the guarantee even though each batch is "within 24 hours".
- Refining the prompt on about 20 representative documents synchronously before the big submission raises first-pass success, because every systematic prompt failure discovered after a full batch means paying for and waiting on a resubmission.
- The one-shot limit (no client-side tool execution mid-request) means batch suits single-turn tasks such as extraction or generation, not agentic loops that need tool results.

### Trade-offs and alternatives

- **Batch vs synchronous:** batch halves the cost but removes predictability; synchronous costs more but gives immediate results and simple control flow. If a human or a merge gate waits on the answer, use synchronous.
- **Batch with timeout fallback to synchronous:** appears to give both benefits but adds a second code path, double processing risk and still depends on a service with no latency guarantee for the primary path. It is not justified when the workflow is simply blocking.
- **Larger vs smaller submission windows:** frequent small batches reduce worst-case wait and cost nothing extra per request, at the price of more orchestration; infrequent large batches are simpler but can violate SLAs.
- **Resubmit as is vs modify:** transient failures justify straight resubmission; request errors need a change (chunking, trimming). Treating both the same wastes cost or loops.
- **Sample-first vs submit-all:** sampling costs a little synchronous spend and time up front and saves resubmission of a large batch.
- **Multi-turn workloads:** if the task needs the model to call tools and continue, run it synchronously in an agent loop; batch cannot host it.

### Exam traps

- "Switch everything to batch for the 50% saving" (Q11, option B): the pre-merge check blocks developers and batch has no latency SLA. Rule: the Batches API cannot back a blocking workflow, regardless of typical completion times.
- "Switch both to batch with a real-time fallback on timeout" (Q11, option D): adds complexity without addressing that one workflow is simply latency-sensitive. Rule: do not add infrastructure that does not address the diagnosed cause.
- "Keep both real-time because batch results are unordered" (Q11, option C): ordering is solved by `custom_id`. Rule: correlation, not ordering, is the mechanism.
- "Resubmit the whole batch when some requests fail": wasteful. Rule: resubmit only the failed ids.
- "Retry an oversized document unchanged": fails identically. Rule: modify the request to fix the cause (chunk it).
- "Submit once per day because batches finish in 24 hours": ignores wait time before submission. Rule: worst case is window plus processing time.
- "Use batch for a tool-using agent": batch requests cannot execute client tools mid-request. Rule: multi-turn tool calling needs the synchronous path.

### Check yourself

- Nightly test generation for 2,000 modules is running at full price through the synchronous API. Should it move? Yes; nobody is waiting on the result and it is single-turn, so batch gives the 50% saving. Use `custom_id` per module and handle failures by id.
- Documents must be processed within 30 hours of arrival, and a batch can take 24 hours. How often must batches be submitted? At least every 6 hours (worst-case wait plus processing must stay within 30), with a shorter window such as 4 hours to leave margin.
- 12 of 1,000 requests errored with a context-size error. What is the right follow-up? Resubmit only those 12 ids after chunking the documents, not the whole batch and not unchanged.
