# 4.2 Apply few-shot prompting to improve output consistency and quality

> [!NOTE]
> **At a glance**
>
> - **Format:** a few examples fix output shape when detailed instructions alone give inconsistent results.
> - **Ambiguity:** examples show why one action was chosen over a plausible alternative (tool selection, coverage gaps).
> - **Generalisation:** reasoning in examples carries judgement to novel patterns, not just listed cases.
> - **Extraction:** examples of varied structures and absent values (`null`) reduce hallucination.

## Example

### Output format via examples (location, issue, severity, fix)

```text
<example>
<code>
def get_user(id):
    return db.execute(f"SELECT * FROM users WHERE id = {id}").fetchone()
</code>
<finding>
location: users.py:2
issue: SQL built by string interpolation allows injection via `id`
severity: critical
suggested_fix: db.execute("SELECT * FROM users WHERE id = ?", (id,))
</finding>
</example>
```

### Acceptable pattern vs genuine issue (reduces false positives, still generalises)

```text
<example>
<code>
try:
    cache.invalidate(key)
except CacheUnavailable:
    pass  # cache is best-effort; the DB is the source of truth
</code>
<finding>none</finding>
<reason>Swallowing CacheUnavailable is deliberate and documented. Do not flag.</reason>
</example>

<example>
<code>
try:
    charge_card(order)
except Exception:
    pass
</code>
<finding>
location: billing.py:12
issue: Bare except hides payment failures; the order is treated as paid
severity: high
</finding>
</example>
```

Two to four examples, each showing why one action was chosen over a plausible alternative.

### Ambiguous tool selection (customer support)

```text
Customer: "I was double charged for order #8841"
-> lookup_order(order_number="8841") first. The identifier is an order number, and billing
   facts live on the order. get_customer is needed only before process_refund.

Customer: "My email is jane@example.com, what's going on with my account?"
-> get_customer(email=...). No order number was given; identify the account first.

Customer: "Check order 5521 for jane@example.com"
-> get_customer first (verify identity), then lookup_order. Order details are only
   returned for a verified customer ID.
```

### Extraction across document structures

```text
<example>
<doc>As shown by Lee et al. (2021), accuracy rose to 91%.</doc>
<out>{"claim": "accuracy rose to 91%", "citation_style": "inline", "source": "Lee et al. (2021)"}</out>
</example>
<example>
<doc>Accuracy rose to 91%.[3]  ...  References: [3] Lee, K. et al. 2021.</doc>
<out>{"claim": "accuracy rose to 91%", "citation_style": "bibliography", "source": "Lee, K. et al. 2021"}</out>
</example>
<example>
<doc>(no methodology section; sample size mentioned only in a footnote: "n=240")</doc>
<out>{"sample_size": 240, "sample_size_location": "footnote"}</out>
</example>
<example>
<doc>The study does not report a sample size.</doc>
<out>{"sample_size": null}</out>
</example>
```

The last example matters: `null` for absent information reduces fabrication.

## How it works

> [!IMPORTANT]
> **Show the decision, not just the answer.** An example with the reason one action beat a plausible alternative teaches a rule; input and output alone teach a pattern to copy.

The snippets above are prompt text, so reasoning lives here: a comment inside an example would be read as part of it.

1. **Fix the format.** A worked finding (location, issue, severity, fix) keeps the shape stable where prose descriptions drift, so downstream tooling can rely on the fields.
2. **Pair acceptable with genuine.** A documented `CacheUnavailable` swallow is not flagged; a bare `except: pass` around `charge_card` is. One example alone flags everything or nothing.
3. **Include the reason.** The `<reason>` line is what generalises: the model applies the same logic to unseen exception handling.
4. **Resolve tool ambiguity.** Order number leads to `lookup_order`, email to `get_customer`, both to verify identity first; each says why, which beats a longer tool description.
5. **Vary document structure.** Inline citation, bibliography and footnote all yield the same output shape, so the model does not depend on one layout.
6. **Show absence.** If every example has a value, the model invents one when the source is silent; a `null` example makes absence correct.

Keep the set small (2-4), aimed at ambiguous cases, not easy ones.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Examples vs more instructions | Show the boundary of borderline cases | Instructions still suit hard constraints needing no demonstration |
| More examples | Wider coverage | Tokens on every call; bias towards surface features. A few varied ones beat many near-duplicates |
| Examples with reasoning and varied structure | Generalise to new cases | Examples limited to listed cases only match those |
| Few-shot vs schema | Shapes judgement | A schema guarantees syntax ([4.3](4.3-structured-output-tool-use.md)); they complement each other |
| Few-shot vs fine-tuning or a classifier | Cheap to iterate; try first | Heavier options add infrastructure and maintenance |

Examples are part of the prompt: update them when criteria change, or stale ones silently reintroduce old behaviour.

> [!WARNING]
> **Exam traps**
>
> - **"Add more detailed instructions"** → when detailed instructions already give inconsistent output, show the target with examples.
> - **"Add a confidence threshold to cut false positives"** → demonstrate acceptable patterns versus genuine issues instead.
> - **"Make the field required so it is always filled"** → forces fabrication when data is absent. Show `null` and make the field nullable ([4.3](4.3-structured-output-tool-use.md)).
> - **"List every acceptable pattern in the prompt"** → the model matches only listed cases. Examples with reasoning generalise.
> - **"One example per easy case"** → examples earn their place on ambiguous cases, where plausible alternatives need distinguishing.
> - **"One long set for all document types"** → the model overfits to one layout. Include varied structures when extraction fails on format variety.

## Check yourself

<details>
<summary>An extractor returns empty or invented sample sizes when a paper has no methodology section. What helps most?</summary>

Few-shot examples with the number found in a footnote and a document with no sample size returning <code>null</code>, teaching varied locations and honest absence.
</details>

<details>
<summary>A reviewer flags a deliberate, documented exception swallow. How do you stop this without suppressing genuine bare-except problems?</summary>

Add a paired example: the documented swallow marked "no finding" with a reason, and a bare except hiding payment failures marked as a finding.
</details>

<details>
<summary>Why should few-shot examples include the reason for the chosen action?</summary>

The reasoning lets the model apply the same judgement to unseen cases; without it, it only copies the surface pattern.
</details>
