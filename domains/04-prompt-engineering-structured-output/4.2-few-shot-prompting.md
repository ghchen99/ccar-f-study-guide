# 4.2 Apply few-shot prompting to improve output consistency and quality

## At a glance

- Few-shot examples as the most effective technique for achieving consistently formatted, actionable output when detailed instructions alone produce inconsistent results.
- The role of few-shot examples in demonstrating ambiguous-case handling (e.g., tool selection for ambiguous requests, branch-level test coverage gaps).
- How few-shot examples enable the model to generalize judgment to novel patterns rather than matching only pre-specified cases.
- The effectiveness of few-shot examples for reducing hallucination in extraction tasks (e.g., handling informal measurements, varied document structures).

## Example

### Output format via examples (location, issue, severity, fix)

```text
<example>
<code>
def get_user(id):
    return db.execute(f"SELECT * FROM users WHERE id = {id}").fetchone()
</code>
<finding>
location: users.py:2
issue: SQL built by string interpolation allows injection via `id`
severity: critical
suggested_fix: db.execute("SELECT * FROM users WHERE id = ?", (id,))
</finding>
</example>
```

### Acceptable pattern vs genuine issue (reduces false positives, still generalises)

```text
<example>
<code>
try:
    cache.invalidate(key)
except CacheUnavailable:
    pass  # cache is best-effort; the DB is the source of truth
</code>
<finding>none</finding>
<reason>Swallowing CacheUnavailable is deliberate and documented. Do not flag.</reason>
</example>

<example>
<code>
try:
    charge_card(order)
except Exception:
    pass
</code>
<finding>
location: billing.py:12
issue: Bare except hides payment failures; the order is treated as paid
severity: high
</finding>
</example>
```

Two to four examples, each showing why one action was chosen over a plausible alternative.

### Ambiguous tool selection (customer support)

```text
Customer: "I was double charged for order #8841"
-> lookup_order(order_number="8841") first. The identifier is an order number, and billing
   facts live on the order. get_customer is needed only before process_refund.

Customer: "My email is jane@example.com, what's going on with my account?"
-> get_customer(email=...). No order number was given; identify the account first.

Customer: "Check order 5521 for jane@example.com"
-> get_customer first (verify identity), then lookup_order. Order details are only
   returned for a verified customer ID.
```

### Extraction across document structures

```text
<example>
<doc>As shown by Lee et al. (2021), accuracy rose to 91%.</doc>
<out>{"claim": "accuracy rose to 91%", "citation_style": "inline", "source": "Lee et al. (2021)"}</out>
</example>
<example>
<doc>Accuracy rose to 91%.[3]  ...  References: [3] Lee, K. et al. 2021.</doc>
<out>{"claim": "accuracy rose to 91%", "citation_style": "bibliography", "source": "Lee, K. et al. 2021"}</out>
</example>
<example>
<doc>(no methodology section; sample size mentioned only in a footnote: "n=240")</doc>
<out>{"sample_size": 240, "sample_size_location": "footnote"}</out>
</example>
<example>
<doc>The study does not report a sample size.</doc>
<out>{"sample_size": null}</out>
</example>
```

The last example matters: it shows `null` for absent information, which reduces fabrication.

## Why this matters

All snippets in this file are prompt text, so reasoning is kept here rather than inside the examples: a comment inside a few-shot example would be read by the model as part of the example.

> [!IMPORTANT]
> **The principle**

When instructions alone produce inconsistent output, a small number of well-chosen examples is the most effective lever. Examples define the output format, show how ambiguous cases are resolved and why, and let the model generalise the judgement to patterns the examples never listed. The design principle: show the decision, not just the answer. An example that includes the reason one action was chosen over a plausible alternative teaches a rule; an example that is only an input and output teaches a pattern to copy.

**The flow**

- The format example (location, issue, severity, suggested fix) fixes the shape of every finding. Prose descriptions of the format drift between runs; a worked example does not, and downstream tooling can rely on the fields.
- The acceptable-vs-genuine pair is the false-positive control. Swallowing `CacheUnavailable` with a documented reason is not flagged; a bare `except: pass` around `charge_card` is. Without the first example the model flags both; without the second it may learn to flag nothing. The pair teaches the distinguishing feature (documented, deliberate, low-stakes versus hidden payment failure), which generalises to other exception handling.
- The `<reason>` line in the first example is the part that generalises: it states why the pattern is acceptable, so the model can apply the same reasoning to a novel case.
- The customer-support examples cover ambiguity in tool selection: order number leads to `lookup_order`, an email leads to `get_customer`, both together lead to identity verification first. Each says why, which resolves the overlap between similar tools better than a longer tool description alone.
- The extraction examples cover varied structure: inline citation versus bibliography, a detail in a footnote rather than a methodology section. Each shows the same output shape from a different input layout, so the model does not depend on one document structure.
- The final `null` example is the anti-fabrication control. If every example has a value, the model learns that a value is always expected and invents one when the source is silent. A worked example of absence makes `null` the correct answer.
- The set is deliberately small (2-4 targeted examples), chosen for the ambiguous cases, not for the easy ones.

## Trade-offs

- **Examples vs more instructions:** adding rules lengthens the prompt and does not resolve borderline cases; examples show the boundary. Instructions remain better for hard constraints that need no demonstration.
- **Number of examples:** more examples improve coverage but cost tokens on every call and can bias the model toward copying their surface features. A few targeted, varied examples beat many near-duplicates.
- **Coverage vs generalisation:** if examples only include the cases listed in the prompt, the model matches those and fails on new ones. Including the reasoning and varied structures lets it generalise.
- **Few-shot vs schema:** a schema guarantees syntax (4.3) but not judgement; few-shot shapes judgement. They are complementary, and the exam tends to place few-shot against ambiguity and inconsistency problems.
- **Few-shot vs fine-tuning or a classifier:** heavier options add infrastructure and maintenance; examples are cheap to iterate on and the first thing to try.
- **Maintenance:** examples are part of the prompt and must be updated when the criteria change; stale examples silently reintroduce old behaviour.

> [!WARNING]
> **Exam traps**

- "Add more detailed instructions to fix inconsistent output": when detailed instructions already produce inconsistent results, the next step is examples showing the target. Rule: few-shot is the most effective technique for consistent format and ambiguous-case handling.
- "Add a confidence threshold to cut false positives": Rule: demonstrate acceptable patterns versus genuine issues instead.
- "Make the field required so the model always fills it": this forces fabrication when the data is absent. Rule: show `null` in an example and make the field nullable (see 4.3).
- "List every acceptable pattern in the prompt": the model matches only the listed cases. Rule: examples with reasoning generalise to novel patterns.
- "Use one example per easy case": examples earn their place on ambiguous cases, where the choice between plausible alternatives needs showing.
- "Write one long few-shot set for all document types without varied structures": the model overfits to one layout. Rule: include varied structures (inline vs bibliography, footnote vs methodology) when extraction fails on format variety.

## Quick check

- An extractor returns empty or invented sample sizes when the paper has no methodology section. What addition helps most? Few-shot examples showing the number found in a footnote and a document with no sample size returning `null`, so the model learns both varied locations and honest absence.
- A reviewer flags a deliberate, documented exception swallow as a bug. How do you stop this without suppressing genuine bare-except problems? Add a paired example: the documented swallow marked "no finding" with a reason, and a bare except hiding payment failures marked as a finding.
- Why should few-shot examples include the reason for the chosen action? The reasoning is what lets the model apply the same judgement to cases not shown; without it the model only copies the surface pattern.
