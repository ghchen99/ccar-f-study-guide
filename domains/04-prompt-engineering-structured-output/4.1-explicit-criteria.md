# 4.1 Design prompts with explicit criteria to improve precision and reduce false positives

> [!NOTE]
> **At a glance**
>
> - **Criteria:** specific categorical rules beat vague ones ("flag comments only when claimed behaviour contradicts the code").
> - **Caution prompts:** "be conservative" and "only high-confidence findings" do not improve precision.
> - **Severity:** anchor each level with a concrete code example.
> - **Trust:** a high false-positive category undermines confidence in the accurate ones.

## Example

Prompt patterns for a PR-review system prompt.

### Vague vs explicit

```text
# Vague: does not improve precision
Check that comments are accurate. Be conservative. Only report high-confidence findings.

# Explicit categorical criteria
Report a comment issue ONLY when the behaviour the comment claims contradicts what the
code actually does (e.g. comment says "returns None on failure" but the code raises).
Do not report: outdated wording, missing comments, style or grammar of comments.
```

The model is already confident about its false positives, so "be conservative" and thresholds change little. Define what counts.

### Report vs skip

```text
REPORT
- Bugs: logic errors, unhandled error paths, off-by-one, null dereference
- Security: injection, missing authz checks, secrets in code, unsafe deserialization

SKIP
- Minor style and formatting
- Local naming patterns that match the surrounding file
- Suggestions that are purely preference
```

### Severity with concrete examples

```text
critical  Exploitable or data-destroying in production.
          e.g. `query = f"SELECT * FROM users WHERE id = {user_id}"`  (SQL injection)
high      Wrong behaviour on a common path.
          e.g. `if len(items) > 0: total = items[0].price`  (ignores items 1..n)
medium    Wrong behaviour on an uncommon path.
          e.g. missing timeout on an outbound HTTP call
low       Correct but fragile.
          e.g. relies on dict ordering without documenting it
```

### Restore trust while you fix a noisy category

```python
# Per-category switches: the noisy category goes quiet without muting the accurate ones
ENABLED_CATEGORIES = {
    "bug": True,
    "security": True,
    "comment_accuracy": False,   # 40% false positives; disabled until the prompt is fixed
    "naming": False,
}
```

Switch noisy categories off temporarily and iterate on their prompts offline.

## How it works

> [!IMPORTANT]
> **Precision comes from defining what counts, not from asking for care.** A wrong model is usually confidently wrong, so confidence thresholds filter little; explicit categorical criteria turn a vague judgement into a testable rule.

1. **Name the qualifying condition.** Claimed behaviour contradicts actual behaviour; wording, missing comments and grammar are explicitly out of scope.
2. **Pair REPORT with SKIP.** Without a skip list the model reports everything, and reviewers learn to ignore all of it, real bugs included.
3. **Anchor severity in code.** An SQL-injection line and a `len(items) > 0` bug mark the level boundaries, so two runs classify alike.
4. **Disable per category.** Trust is shared, so 40% false positives in `comment_accuracy` would teach developers to dismiss bug and security comments too.
5. **Fix offline, then re-enable.** Accurate categories keep running while the noisy one is tested against labelled examples.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Stricter skip rules | Less noise | Drops some true positives. Skip low-cost misses (style); keep costly ones (security) and tighten their definitions |
| Disable a noisy category | Restores trust immediately | No coverage there until fixed. Preferred when noise damages trust in other categories |
| Concrete examples | More consistent than adjectives | Longer prompt; may be copied too narrowly ([4.2](4.2-few-shot-prompting.md)) |
| Self-reported confidence | Routing signal once calibrated ([5.5](../05-context-management-reliability/5.5-human-review-confidence.md)) | Does not define the category; a calibrated score on a vague category is still vague |

> [!WARNING]
> **Exam traps**
>
> - **"Only report high-confidence findings"** → the model is already confident about its false positives. Confidence filtering does not fix poor criteria.
> - **"Add 'be conservative'"** → general caution defines nothing. Specific categorical criteria win.
> - **"Keep every category on and let developers filter"** → noisy categories erode trust in accurate ones. Disable the noisy one temporarily.
> - **"Switch to a larger model"** → the cause is an unspecified criterion, not capability. Don't add capability that misses the diagnosed cause.
> - **"Severity described in words ('serious', 'minor')"** → inconsistent between runs. Define each level with a concrete code example.
> - **"Post-filter formatting and naming findings in CI"** → the fix is a skip list in the review criteria, not filtering the output.

<summary>A PR reviewer flags outdated comment wording in 40% of PRs and developers ignore all its comments. First action?</summary>

Disable the noisy comment category to restore trust. Rewrite it to report only comment/code contradictions, then re-enable after offline testing.

The model is typically confident in its false positives, so the threshold removes little. Define precisely what to report and skip.
