# 4.1 Design prompts with explicit criteria to improve precision and reduce false positives

## Knowledge of

- The importance of explicit criteria over vague instructions (e.g., "flag comments only when claimed behavior contradicts actual code behavior" vs "check that comments are accurate").
- General instructions like "be conservative" or "only report high-confidence findings" fail to improve precision compared to specific categorical criteria.
- The impact of false positive rates on developer trust: high false positive categories undermine confidence in accurate categories.

## Skills in

- Writing specific review criteria that define which issues to report (bugs, security) versus skip (minor style, local patterns) rather than relying on confidence-based filtering.
- Temporarily disabling high false-positive categories to restore developer trust while improving prompts for those categories.
- Defining explicit severity criteria with concrete code examples for each severity level to achieve consistent classification.

## Code snippets

Prompt patterns for a PR-review system prompt.

### Vague vs explicit

```text
# Vague: does not improve precision
Check that comments are accurate. Be conservative. Only report high-confidence findings.

# Explicit categorical criteria
Report a comment issue ONLY when the behaviour the comment claims contradicts what the
code actually does (e.g. comment says "returns None on failure" but the code raises).
Do not report: outdated wording, missing comments, style or grammar of comments.
```

"Be conservative" and confidence thresholds fail because the model is already confident about its false positives. Define what counts.

### Report vs skip

```text
REPORT
- Bugs: logic errors, unhandled error paths, off-by-one, null dereference
- Security: injection, missing authz checks, secrets in code, unsafe deserialization

SKIP
- Minor style and formatting
- Local naming patterns that match the surrounding file
- Suggestions that are purely preference
```

### Severity with concrete examples

```text
critical  Exploitable or data-destroying in production.
          e.g. `query = f"SELECT * FROM users WHERE id = {user_id}"`  (SQL injection)
high      Wrong behaviour on a common path.
          e.g. `if len(items) > 0: total = items[0].price`  (ignores items 1..n)
medium    Wrong behaviour on an uncommon path.
          e.g. missing timeout on an outbound HTTP call
low       Correct but fragile.
          e.g. relies on dict ordering without documenting it
```

### Restore trust while you fix a noisy category

```python
# Per-category switches: the noisy category goes quiet without muting the accurate ones
ENABLED_CATEGORIES = {
    "bug": True,
    "security": True,
    "comment_accuracy": False,   # 40% false positives; disabled until the prompt is fixed
    "naming": False,
}
```

High false-positive categories erode trust in the accurate ones, so switch them off temporarily and iterate on their prompts offline.

## Commentary: the concepts behind the code

SDK names are illustrative; know the concept, not the exact parameter.

### The design decision

Precision comes from telling the model exactly which categories of finding are worth reporting, with concrete examples at each severity level, not from asking it to be careful or confident. A model that is wrong is usually wrong confidently, so a confidence threshold filters very little. Explicit categorical criteria change what counts as a finding; they turn a vague judgement into a testable rule. The second half of the principle is operational: developer trust is shared across categories, so a noisy category should be switched off while it is repaired.

### Walk-through

- The vague prompt ("be conservative", "only high-confidence") gives the model no definition of an issue. The explicit version names the single condition that qualifies (claimed behaviour contradicts actual behaviour) and lists what is out of scope (wording, missing comments, grammar). Both halves matter: the report list defines positives, the skip list removes the recurring low-value ones.
- The REPORT/SKIP lists separate bugs and security from style and preference. Without a skip list the model reports everything it notices, and reviewers learn to ignore all of it, including the real bugs.
- Severity levels are anchored by code examples, not adjectives. "Critical" or "high" means little on its own; an SQL-injection line and a `len(items) > 0` bug show the boundary between levels, so two runs classify the same finding the same way.
- `ENABLED_CATEGORIES` shows the operational response to a bad category: 40% false positives in `comment_accuracy` are disabled, not tolerated. Left on, that category teaches developers to dismiss comments from the bug and security categories as well.
- The flag is per category, not global, so the accurate categories keep running while the noisy ones are improved offline against labelled examples and then re-enabled.

### Trade-offs and alternatives

- **Stricter criteria vs coverage:** every skip rule removes some noise and some possible true positives. Skip categories where the cost of a miss is low (style, preference); keep categories where a miss is costly (security) even if noisier, and tighten their definitions instead of dropping them.
- **Disable vs tune in place:** disabling restores trust immediately but loses coverage in that category until the prompt is fixed. Tuning while live keeps coverage but keeps the noise. Temporary disabling is preferred when the false positive rate is high enough to damage trust in the other categories.
- **Concrete examples vs longer prose rules:** examples fix consistency better than additional adjectives, at the cost of prompt length and the risk that the model copies the example too narrowly (4.2 addresses mixing examples).
- **Self-reported confidence as a filter:** usable as a routing signal after calibration (see 5.5), but it is no substitute for defining the category; a calibrated score on a badly defined category is still a badly defined category.
- **Maintenance:** criteria and category flags live in config and prompts, so they can be reviewed and versioned like code.

### Exam traps

- "Tell the model to only report high-confidence findings": the model is already confident about its false positives. Rule: confidence-based filtering does not fix poorly specified criteria.
- "Add 'be conservative' to the prompt": a general instruction with no definition of what to report. Rule: specific categorical criteria beat general caution.
- "Keep every category on and let developers filter": noisy categories erode trust in accurate ones. Rule: protect trust first; temporarily disable the noisy category.
- "Fix the false positives by switching to a larger model": the cause is an unspecified criterion, not capability. Rule: do not add capability or infrastructure that does not address the diagnosed cause.
- Severity described only with words ("serious", "minor"): inconsistent between runs. Rule: define each severity level with a concrete code example.
- Pre-merge checks in the CI scenario that flag formatting and naming: the fix is a skip list in the review criteria, not post-filtering the output.

### Check yourself

- A PR reviewer flags outdated comment wording in 40% of PRs and developers have started ignoring all its comments. What is the first action? Disable the noisy comment category to restore trust, then rewrite its criteria to report only contradictions between comment and code and re-enable it after offline testing.
- A teammate proposes "only report findings above 80% confidence" to cut noise. Why is this weak? The model is typically confident in its false positives, so the threshold removes little; the fix is a precise definition of what to report and skip.
- Two runs label the same missing-timeout bug "high" and "low". What fixes this? Severity definitions anchored with concrete code examples for each level.
