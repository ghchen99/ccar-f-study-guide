# 4.6 Design multi-instance and multi-pass review architectures

## At a glance

- Self-review limitations: a model retains reasoning context from generation, making it less likely to question its own decisions in the same session.
- Independent review instances (without prior reasoning context) are more effective at catching subtle issues than self-review instructions or extended thinking.
- Multi-pass review: splitting large reviews into per-file local analysis passes plus cross-file integration passes to avoid attention dilution and contradictory findings.

## Example

### Independent review instance

The reviewer is a fresh call that sees only the code (and the requirements), never the generator's reasoning or conversation.

```python
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"


def generate(task: str) -> str:
    r = client.messages.create(model=MODEL, max_tokens=4096,
                               messages=[{"role": "user", "content": task}])
    return r.content[0].text


def independent_review(code: str, requirements: str) -> str:
    # New request: no prior messages, no generator reasoning
    # Sharing only code and requirements keeps the generator's rationale from biasing the reviewer
    r = client.messages.create(
        model=MODEL, max_tokens=2048,
        system="You are a code reviewer. Report only bugs and security issues.",
        messages=[{"role": "user", "content": f"<requirements>{requirements}</requirements>\n<code>{code}</code>"}],
    )
    return r.content[0].text
```

Telling the generating session to "review your work" is weaker: it retains its own reasoning and is less likely to question it.

### Per-file passes, then an integration pass

```python
# Small, focused contexts: each file gets full attention instead of competing with 13 others
per_file = {path: review_file(path) for path in changed_files}    # same depth for every file

# The second pass reads findings, not full files: it targets cross-file issues no single-file pass can see
integration = client.messages.create(
    model=MODEL, max_tokens=2048,
    messages=[{"role": "user", "content": (
        "Per-file review results are below. Examine ONLY cross-file concerns: data flow between "
        "files, inconsistent handling of the same pattern, contract mismatches.\n\n"
        + "\n\n".join(f"## {p}\n{f}" for p, f in per_file.items())
    )}],
)
```

This addresses attention dilution: inconsistent depth, missed bugs, and contradictory feedback on the same pattern across 14 files in one pass. A larger context window or consensus voting across runs does not.

### Findings with self-reported confidence for review routing

```json
{
  "file": "stock.py",
  "line": 88,
  "severity": "high",
  "issue": "Quantity decremented before the stock check",
  "confidence": "medium",
  "detected_pattern": "mutate_before_validate"
}
```

```python
def route(finding: dict) -> str:
    # Confidence decides who looks, not whether the finding is true
    return "auto_comment" if finding["confidence"] == "high" else "human_triage"
```

Self-reported confidence needs calibrating against labelled results (see [5.5](../05-context-management-reliability/5.5-human-review-confidence.md)); it is a routing signal, not ground truth.

## Why this matters

> [!IMPORTANT]
> **The principle**

Independent review beats self-review, and focused review beats one giant pass. A model that generated code carries its own reasoning forward, so asking it to check its work in the same session tends to confirm its earlier decisions. A fresh instance sees only the artefact and the requirements and has no rationale to defend. Separately, quality degrades when one pass has to cover many files: attention is spread unevenly, depth varies and the same pattern can be judged differently in different files. The remedy is to decompose the review (local per-file passes, then a cross-file integration pass), not to enlarge the context.

**The flow**

- `independent_review` is a new request with no prior messages. The reviewer receives the code and requirements, never the generator's chain of reasoning. Any extra context would hand the reviewer the same assumptions that produced the bug.
- The note under the snippet states the weakness of self-review: the generating session retains its own reasoning and is less likely to question it. Adding "think carefully" or extended thinking in the same session does not remove that retained context.
- The reviewer's system prompt limits scope to bugs and security issues, which keeps the explicit-criteria discipline of 4.1 in the second instance.
- `per_file` runs one focused pass per changed file with the same instructions. That gives consistent depth, so obvious bugs are not skipped because a long file list diluted attention, and the same pattern is judged by the same standard in each file.
- The integration pass receives the per-file findings and is told to examine only cross-file concerns (data flow, inconsistent handling, contract mismatches). Each pass has one job; the per-file passes cannot see cross-file issues, and the integration pass does not repeat local ones.
- The 14-file PR in the CI scenario fits this pattern: inconsistent depth, missed bugs and contradictory verdicts on identical code are symptoms of attention dilution in a single pass.
- The finding schema carries `confidence` and `detected_pattern`. Confidence feeds routing: high-confidence findings are posted automatically, the rest go to a human. `detected_pattern` supports later analysis of false positives (4.4).
- The router treats confidence as a signal for where human time goes. It is self-reported, so it needs calibration against labelled outcomes before thresholds are trusted (see 5.5).

## Trade-offs

- **Independent instance vs self-review:** an extra call costs tokens and latency but catches subtle issues the generator rationalised away. For trivial changes the cost may not be worth it; for generated code with consequences, it is.
- **Independent review vs extended thinking:** more thinking in the same session still operates inside the same reasoning context. The benefit comes from removing that context.
- **Per-file plus integration vs one large pass:** more calls, but consistent quality and parallelism across files. A single pass is cheaper for small PRs where attention is not stretched.
- **Per-file passes vs asking developers to split PRs:** splitting reduces the review size but shifts the burden to developers and leaves the system unchanged; a robust reviewer handles large PRs.
- **Bigger context window vs decomposition:** a larger window lets more fit in; it does not guarantee even attention across the content.
- **Consensus voting vs single focused pass:** requiring an issue to appear in several full-PR runs suppresses real bugs that are only found intermittently, and multiplies cost.
- **Cost of the integration pass:** it consumes findings, not full source, so it stays small; if cross-file contracts need source, pass the relevant excerpts rather than the whole PR.

> [!WARNING]
> **Exam traps**

- "Ask the same session to review its own work" or "add extended thinking": the reviewer inherits the generator's reasoning. Rule: a model reviewing its own output in the same session keeps its own reasoning bias; use an independent instance.
- "Split the PR requirement to 3-4 files" (Q12, option B): moves the problem to developers. Rule: fix the system design; per-file plus integration passes address the cause.
- "Use a higher-tier model or larger context window" (Q12, option C): treats attention dilution as a capacity issue. Rule: larger context does not solve attention quality.
- "Run three passes and keep issues found twice" (Q12, option D): suppresses real, intermittently detected bugs. Rule: consensus filtering reduces recall without fixing inconsistency.
- "Treat self-reported confidence as truth": it is uncalibrated. Rule: use it for routing after validating against labelled data.
- "One mega-prompt for per-file and cross-file concerns": recreates the dilution. Rule: one focused objective per pass.

## Quick check

- A team has the same Claude session write a feature and then asks it to double-check for bugs; reviewers still find issues later. What change? Run the review in a fresh instance given only the code and requirements, so it does not share the generator's assumptions.
- A 14-file PR gets deep comments on some files, nothing on others, and the same pattern is flagged in one file and approved in another. What is the root cause and fix? Attention dilution in a single pass; review each file separately for local issues, then run an integration pass for cross-file concerns.
- Review findings carry a self-reported confidence. Is it safe to auto-post anything marked "high"? Not without calibration against labelled outcomes; treat it as a routing hint and validate accuracy per category first.
