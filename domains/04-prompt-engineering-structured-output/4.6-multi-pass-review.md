# 4.6 Design multi-instance and multi-pass review architectures

> [!NOTE]
> **At a glance**
>
> - **Self-review:** a model keeps its generation reasoning, so it rarely questions its own decisions in the same session.
> - **Independent instance:** a fresh reviewer without that context catches subtler issues than self-review instructions or extended thinking.
> - **Multi-pass:** per-file local passes plus a cross-file integration pass avoid attention dilution and contradictory findings.

## Example

### Independent review instance

The reviewer is a fresh call that sees only the code (and the requirements), never the generator's reasoning or conversation.

```python
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"


def generate(task: str) -> str:
    r = client.messages.create(model=MODEL, max_tokens=4096,
                               messages=[{"role": "user", "content": task}])
    return r.content[0].text


def independent_review(code: str, requirements: str) -> str:
    # New request: no prior messages, no generator reasoning
    # Sharing only code and requirements keeps the generator's rationale from biasing the reviewer
    r = client.messages.create(
        model=MODEL, max_tokens=2048,
        system="You are a code reviewer. Report only bugs and security issues.",
        messages=[{"role": "user", "content": f"<requirements>{requirements}</requirements>\n<code>{code}</code>"}],
    )
    return r.content[0].text
```

Telling the generating session to "review your work" is weaker: it keeps its own reasoning and is less likely to question it.

### Per-file passes, then an integration pass

```python
# Small, focused contexts: each file gets full attention instead of competing with 13 others
per_file = {path: review_file(path) for path in changed_files}    # same depth for every file

# The second pass reads findings, not full files: it targets cross-file issues no single-file pass can see
integration = client.messages.create(
    model=MODEL, max_tokens=2048,
    messages=[{"role": "user", "content": (
        "Per-file review results are below. Examine ONLY cross-file concerns: data flow between "
        "files, inconsistent handling of the same pattern, contract mismatches.\n\n"
        + "\n\n".join(f"## {p}\n{f}" for p, f in per_file.items())
    )}],
)
```

This addresses attention dilution (inconsistent depth, missed bugs, contradictory feedback on one pattern across 14 files). A larger context window or consensus voting does not.

### Findings with self-reported confidence for review routing

```json
{
  "file": "stock.py",
  "line": 88,
  "severity": "high",
  "issue": "Quantity decremented before the stock check",
  "confidence": "medium",
  "detected_pattern": "mutate_before_validate"
}
```

```python
def route(finding: dict) -> str:
    # Confidence decides who looks, not whether the finding is true
    return "auto_comment" if finding["confidence"] == "high" else "human_triage"
```

Self-reported confidence needs calibrating against labelled results (see [5.5](../05-context-management-reliability/5.5-human-review-confidence.md)); it is a routing signal, not ground truth.

## How it works

> [!IMPORTANT]
> **Independent review beats self-review, and focused review beats one giant pass.** A fresh instance sees only the artefact and requirements, with no rationale to defend; decomposing the review, not enlarging the context, fixes uneven attention.

1. **Start a new request.** The reviewer gets code and requirements, never the generator's reasoning; "think carefully" or extended thinking in the same session keeps that context.
2. **Scope the reviewer.** Limiting it to bugs and security issues keeps the explicit-criteria discipline of [4.1](4.1-explicit-criteria.md).
3. **Run one pass per file.** Same instructions each time gives consistent depth and the same standard for the same pattern.
4. **Add an integration pass.** It reads per-file findings and examines only cross-file concerns (data flow, inconsistent handling, contract mismatches); each pass has one job.
5. **Route by confidence.** Findings carry `confidence` and `detected_pattern`; high confidence auto-posts, the rest go to a human, and patterns feed false-positive analysis ([4.4](4.4-validation-retry-loops.md)).
6. **Calibrate first.** Confidence is self-reported, so validate it against labelled outcomes before trusting thresholds.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Independent instance vs self-review | Catches subtle issues the generator rationalised away | Extra tokens and latency; may not pay off for trivial changes |
| Independent review vs extended thinking | Removes the retained reasoning context | Extended thinking still operates inside the same context |
| Per-file plus integration vs one pass | Consistent quality, parallel across files | More calls; one pass is cheaper for small PRs |
| Per-file passes vs asking developers to split PRs | Handles large PRs robustly | Splitting shifts the burden to developers and leaves the system unchanged |
| Bigger context vs decomposition | More fits in | Does not guarantee even attention |
| Consensus voting | Appears to reduce noise | Suppresses intermittently found real bugs; multiplies cost |

The integration pass consumes findings, not full source, so it stays small; if contracts need source, pass relevant excerpts, not the whole PR.

> [!WARNING]
> **Exam traps**
>
> - **"Ask the same session to review its own work" or "add extended thinking"** → the reviewer inherits the generator's reasoning bias. Use an independent instance.
> - **"Split the PR requirement to 3-4 files" (Q12, B)** → moves the problem to developers. Per-file plus integration passes fix the cause.
> - **"Higher-tier model or larger context window" (Q12, C)** → treats attention dilution as capacity. Larger context does not fix attention quality.
> - **"Run three passes and keep issues found twice" (Q12, D)** → suppresses real, intermittently detected bugs. Consensus lowers recall without fixing inconsistency.
> - **"Treat self-reported confidence as truth"** → it is uncalibrated. Use it for routing after validating against labelled data.
> - **"One mega-prompt for per-file and cross-file concerns"** → recreates the dilution. One focused objective per pass.

## Check yourself

<details>
<summary>The same Claude session writes a feature and is then asked to double-check for bugs, yet reviewers still find issues. What change?</summary>

Run the review in a fresh instance given only the code and requirements, so it does not share the generator's assumptions.
</details>

<details>
<summary>A 14-file PR gets deep comments on some files, nothing on others, and one pattern is flagged in one file and approved in another. Root cause and fix?</summary>

Attention dilution in a single pass. Review each file separately for local issues, then run an integration pass for cross-file concerns.
</details>

<details>
<summary>Review findings carry a self-reported confidence. Is it safe to auto-post anything marked "high"?</summary>

Not without calibration against labelled outcomes. Treat it as a routing hint and validate accuracy per category first.
</details>
