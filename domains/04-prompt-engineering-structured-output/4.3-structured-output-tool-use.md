# 4.3 Enforce structured output using tool use and JSON schemas

## At a glance

- Tool use (`tool_use`) with JSON schemas as the most reliable approach for guaranteed schema-compliant structured output, eliminating JSON syntax errors.
- The distinction between `tool_choice`:
  - `"auto"`: model may return text instead of calling a tool
  - `"any"`: model must call a tool but can choose which
  - forced tool selection: model must call a specific named tool
- Strict JSON schemas via tool use eliminate syntax errors but do not prevent semantic errors (e.g., line items that don't sum to total, values in wrong fields).
- Schema design considerations: required vs optional fields, enum fields with "other" + detail string patterns for extensible categories.

## Example

### Extraction tool with a schema (the exam's `tool_use` approach)

Nullable fields stop the model fabricating values; `"unclear"` and `"other"` + detail handle ambiguity and extensibility.

```python
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"  # forced tool_choice caveat below

extract_invoice = {
    "name": "extract_invoice",
    "description": "Record the structured fields extracted from an invoice document.",
    "input_schema": {
        "type": "object",
        "properties": {
            "invoice_number": {"type": "string"},
            # Nullable, not required: a required field forces the model to invent a value when the source is silent
            "stated_total": {"type": ["number", "null"], "description": "Total printed on the document; null if absent"},
            # Extracted beside stated_total so a mismatch can be detected later; the schema cannot check arithmetic itself
            "calculated_total": {"type": ["number", "null"], "description": "Sum of line items you computed"},
            "currency": {"type": ["string", "null"], "description": "ISO 4217, e.g. USD; null if not stated"},
            # "unclear" and "other" give ambiguity a legal value, so the model need not force a wrong enum choice
            "payment_terms": {
                "type": "string",
                "enum": ["net_30", "net_60", "due_on_receipt", "unclear", "other"],
            },
            "payment_terms_detail": {"type": ["string", "null"], "description": "Required when payment_terms is 'other'"},
            "line_items": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "description": {"type": "string"},
                        "quantity": {"type": "number"},
                        "unit_price": {"type": "number"},
                    },
                    "required": ["description", "quantity", "unit_price"],
                },
            },
        },
        "required": ["invoice_number", "payment_terms", "line_items"],  # the rest may be null
    },
}

response = client.messages.create(
    model=MODEL,
    max_tokens=2048,
    tools=[extract_invoice],
    # Forcing the named tool guarantees a structured result; "auto" could return prose instead
    tool_choice={"type": "tool", "name": "extract_invoice"},
    # Format rules live in the prompt: the schema fixes structure, not how messy source values are normalised
    system="Normalise dates to ISO 8601 and amounts to plain numbers (no currency symbols). "
           "If a field is not in the document, return null; never guess.",
    messages=[{"role": "user", "content": document_text}],
)
data = next(b.input for b in response.content if b.type == "tool_use")
```

### Choosing `tool_choice`

| Value | Behaviour | Use for |
| - | - | - |
| `{"type": "auto"}` | May answer in text instead of calling a tool | Normal agent turns |
| `{"type": "any"}` | Must call a tool; Claude picks which | Several extraction schemas, document type unknown |
| `{"type": "tool", "name": "extract_metadata"}` | Must call that tool | Run metadata extraction before enrichment steps |

```python
# Unknown document type: guarantee a structured result from one of several schemas
# "any" fits here because forcing one named tool would push every document through the wrong schema
tools = [extract_invoice, extract_receipt, extract_contract]
client.messages.create(model=MODEL, max_tokens=2048, tools=tools, tool_choice={"type": "any"}, messages=msgs)
```

### Newer alternatives in the current API

```python
from pydantic import BaseModel

class ContactInfo(BaseModel):
    name: str
    email: str | None   # nullable when the document may not contain it

response = client.messages.parse(
    model=MODEL, max_tokens=1024,
    output_format=ContactInfo,       # sent as output_config.format (json_schema)
    messages=[{"role": "user", "content": text}],
)
print(response.parsed_output)
```

`strict: true` on a tool definition gives guaranteed schema-valid tool inputs.

In the Agent SDK the equivalent is `ClaudeAgentOptions(output_format={"type": "json_schema", "schema": {...}})`. The parsed object arrives on `ResultMessage.structured_output`, and a run that cannot produce valid output ends with subtype `error_max_structured_output_retries`.
 Notes from [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs):

- Both eliminate JSON syntax errors via constrained decoding. Neither prevents **semantic** errors (line items not summing to the total, a value in the wrong field).
- Not supported in the schema: `minimum`/`maximum`, `minLength`/`maxLength`, recursive schemas; `additionalProperties` must be `false`.
- Refusals (`stop_reason: "refusal"`) and truncation (`max_tokens`) can yield output that does not match the schema.
- Enum casing is not guaranteed, so compare case-insensitively.
- Forced `any`/`tool` is rejected on some newer models and with manual extended thinking; use `auto` + `strict: true` or `output_config.format` there (see [2.3](../02-tool-design-mcp-integration/2.3-tool-distribution-tool-choice.md)).

## Why this matters

> [!IMPORTANT]
> **The principle**

A schema guarantees syntax, not semantics. Defining extraction as a tool call with a JSON schema makes the output machine-parseable every time, so JSON syntax errors disappear. It does nothing to make the content correct: line items can still fail to sum to the total, and a value can land in the wrong field. The design therefore has two layers: the schema shapes the output and shows the model what absence and ambiguity look like (nullable fields, `"unclear"`, `"other"` plus detail), and separate validation (4.4) checks meaning.

**The flow**

- Optional and nullable fields (`stated_total`, `currency`) exist because source documents are incomplete. If a field is required, the schema obliges the model to produce something, and when the document is silent the something is invented. A nullable field makes `null` a valid, honest answer.
- Only `invoice_number`, `payment_terms` and `line_items` are required: the fields every invoice must yield for the record to be useful. Everything else may be missing.
- `payment_terms` enum with `"unclear"` and `"other"` plus `payment_terms_detail` handles both ambiguity and extensibility. Without `"unclear"` the model must pick a wrong category; without `"other"` plus detail, an unexpected term is either lost or forced into a wrong value, and the enum must be edited for every new case.
- `stated_total` next to `calculated_total` makes the semantic check possible. The schema cannot say "these must be equal", but code that sees both fields can.
- The system prompt carries format normalisation (ISO dates, plain numbers). Schemas constrain structure; they do not tell the model how to clean inconsistent source formatting.
- Forcing `extract_invoice` means the response always contains that tool call, so extraction runs before any enrichment step and no free-text answer can sneak in. `"any"` is the choice when several schemas exist and the document type is unknown: the model must call a tool but picks which. `"auto"` may reply in prose, which is wrong for a pipeline that parses the output.
- The `next(b.input ...)` line reads the structured data from the tool-use block, not from text.

## Trade-offs

- **Tool use vs schema-constrained output formats vs asking for JSON in the prompt:** prompt-only JSON can produce malformed or chatty output. Tool use or the newer structured output options guarantee syntax. The newer options are simpler for pure extraction (no pretend tool call); tool use remains the pattern the exam names, and it also fits cases where extraction is one of several tools.
- **Forced tool vs `any` vs `auto`:** forced guarantees the extraction and order; `any` guarantees structure when the schema is unknown; `auto` keeps flexibility for agent turns but lets the model skip the tool. Some newer models and settings restrict forcing, so know the design reason for each mode, not only the syntax.
- **Strict schemas vs expressive schemas:** schema features are limited (for example, no numeric range or length constraints in strict mode), so range checks belong in post-validation, not in the schema.
- **Required vs nullable:** required fields give downstream code a stable contract but force fabrication on sparse documents; nullable fields push null handling downstream. The cost of handling `null` is small compared with silently wrong data.
- **Enum with `"other"` vs free text:** the enum keeps categories analysable; `"other"` plus detail keeps extensibility and lets new categories be discovered from the detail text.
- **Failure paths:** refusals and truncation can still produce output that does not match the schema, so a pipeline checks the stop reason rather than assuming validity.

> [!WARNING]
> **Exam traps**

- "Tool use guarantees correct data": it guarantees schema-compliant syntax only. Rule: schema validity is not semantic correctness; add validation for totals and field placement.
- "Mark every field required to avoid missing data": forces fabrication when the source lacks the value. Rule: make fields optional or nullable when the document may not contain them.
- "Use `tool_choice: auto` to guarantee structured output": `auto` may return text. Rule: use `any` or a forced tool when structure must be guaranteed.
- "Force one specific tool when the document type is unknown": every document is pushed through one schema. Rule: use `any` for multiple schemas, forced selection when a particular extraction must run first.
- "Add an enum with only known values": ambiguous or novel cases are forced into wrong buckets. Rule: add `"unclear"` and `"other"` plus a detail field.
- "Parse JSON from the model's text reply and retry on errors": solves a syntax problem that tool use removes. Rule: choose the mechanism that eliminates the failure class rather than recovering from it.

## Quick check

- A pipeline extracts invoices with a strict schema, yet 2% of records have line items that do not add up to the total. Does a stricter schema fix this? No; syntax and structure are already guaranteed, and the error is semantic. Extract both totals and validate the difference in code (4.4).
- Contracts, invoices and receipts arrive mixed and unlabelled. Which `tool_choice` mode applies? `any`: a structured result is guaranteed from whichever of the three schemas fits, without forcing a single one.
- Papers often omit the sample size and the extractor keeps returning plausible numbers. What schema change helps? Make the field nullable (and show `null` in a prompt example) so absence is a valid answer.
