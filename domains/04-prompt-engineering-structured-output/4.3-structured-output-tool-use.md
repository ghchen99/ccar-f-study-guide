# 4.3 Enforce structured output using tool use and JSON schemas

> [!NOTE]
> **At a glance**
>
> - **Mechanism:** a tool with a JSON schema is the most reliable route to schema-compliant output; JSON syntax errors disappear.
> - **`tool_choice`:** `"auto"` may return text; `"any"` must call some tool; forced selection must call a named tool.
> - **Limit:** schemas stop syntax errors, not semantic ones (items not summing to total, values in wrong fields).
> - **Design:** nullable fields for missing data; enums with `"other"` plus a detail string for extensibility.

## Example

### Extraction tool with a schema (the exam's `tool_use` approach)

Nullable fields stop the model fabricating values; `"unclear"` and `"other"` + detail handle ambiguity and extensibility.

```python
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"  # forced tool_choice caveat below

extract_invoice = {
    "name": "extract_invoice",
    "description": "Record the structured fields extracted from an invoice document.",
    "input_schema": {
        "type": "object",
        "properties": {
            "invoice_number": {"type": "string"},
            # Nullable, not required: a required field forces the model to invent a value when the source is silent
            "stated_total": {"type": ["number", "null"], "description": "Total printed on the document; null if absent"},
            # Extracted beside stated_total so a mismatch can be detected later; the schema cannot check arithmetic itself
            "calculated_total": {"type": ["number", "null"], "description": "Sum of line items you computed"},
            "currency": {"type": ["string", "null"], "description": "ISO 4217, e.g. USD; null if not stated"},
            # "unclear" and "other" give ambiguity a legal value, so the model need not force a wrong enum choice
            "payment_terms": {
                "type": "string",
                "enum": ["net_30", "net_60", "due_on_receipt", "unclear", "other"],
            },
            "payment_terms_detail": {"type": ["string", "null"], "description": "Required when payment_terms is 'other'"},
            "line_items": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "description": {"type": "string"},
                        "quantity": {"type": "number"},
                        "unit_price": {"type": "number"},
                    },
                    "required": ["description", "quantity", "unit_price"],
                },
            },
        },
        "required": ["invoice_number", "payment_terms", "line_items"],  # the rest may be null
    },
}

response = client.messages.create(
    model=MODEL,
    max_tokens=2048,
    tools=[extract_invoice],
    # Forcing the named tool guarantees a structured result; "auto" could return prose instead
    tool_choice={"type": "tool", "name": "extract_invoice"},
    # Format rules live in the prompt: the schema fixes structure, not how messy source values are normalised
    system="Normalise dates to ISO 8601 and amounts to plain numbers (no currency symbols). "
           "If a field is not in the document, return null; never guess.",
    messages=[{"role": "user", "content": document_text}],
)
data = next(b.input for b in response.content if b.type == "tool_use")
```

### Choosing `tool_choice`

| Value | Behaviour | Use for |
| - | - | - |
| `{"type": "auto"}` | May answer in text instead of calling a tool | Normal agent turns |
| `{"type": "any"}` | Must call a tool; Claude picks which | Several extraction schemas, document type unknown |
| `{"type": "tool", "name": "extract_metadata"}` | Must call that tool | Run metadata extraction before enrichment steps |

```python
# Unknown document type: guarantee a structured result from one of several schemas
# "any" fits here because forcing one named tool would push every document through the wrong schema
tools = [extract_invoice, extract_receipt, extract_contract]
client.messages.create(model=MODEL, max_tokens=2048, tools=tools, tool_choice={"type": "any"}, messages=msgs)
```

### Newer alternatives in the current API

```python
from pydantic import BaseModel

class ContactInfo(BaseModel):
    name: str
    email: str | None   # nullable when the document may not contain it

response = client.messages.parse(
    model=MODEL, max_tokens=1024,
    output_format=ContactInfo,       # sent as output_config.format (json_schema)
    messages=[{"role": "user", "content": text}],
)
print(response.parsed_output)
```

`strict: true` on a tool definition guarantees schema-valid tool inputs. In the Agent SDK, use `ClaudeAgentOptions(output_format={"type": "json_schema", "schema": {...}})`; the parsed object arrives on `ResultMessage.structured_output`.

Limits of these options:

- Both remove JSON syntax errors via constrained decoding, but neither prevents **semantic** errors.
- Not supported in the schema: `minimum`/`maximum`, `minLength`/`maxLength`, recursive schemas; `additionalProperties` must be `false`.
- Refusals (`stop_reason: "refusal"`) and truncation (`max_tokens`) can yield output that does not match the schema.
- Enum casing is not guaranteed, so compare case-insensitively.

## How it works

> [!IMPORTANT]
> **A schema guarantees syntax, not semantics.** Two layers are needed: the schema shapes output and shows the model what absence and ambiguity look like; separate validation ([4.4](4.4-validation-retry-loops.md)) checks meaning.

1. **Make absence legal.** Source documents are incomplete; a required field obliges the model to invent a value, while a nullable one makes `null` an honest answer.
2. **Require only the essentials.** `invoice_number`, `payment_terms` and `line_items` are what every useful record needs; the rest may be missing.
3. **Give ambiguity an enum value.** `"unclear"` stops forced wrong picks; `"other"` plus `payment_terms_detail` absorbs new terms without editing the enum.
4. **Extract evidence for validation.** `stated_total` beside `calculated_total` lets code check what the schema cannot express.
5. **Put normalisation in the prompt.** Schemas constrain structure, not how messy source formatting (dates, currency symbols) is cleaned.
6. **Choose `tool_choice` by intent.** Forced runs extraction first with no prose; `"any"` fits several schemas and an unknown document type; `"auto"` may reply in text, wrong for parsing pipelines.

Read the data from the `tool_use` block (`next(b.input ...)`), not from text.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Tool use / structured output vs JSON in the prompt | Guaranteed syntax; prompt-only JSON can be malformed or chatty | Tool use is a pretend call for pure extraction; newer options are simpler, but tool use is the pattern the exam names |
| Forced tool vs `any` vs `auto` | Forced guarantees extraction and order; `any` guarantees structure for unknown schemas | `auto` can skip the tool. Some newer models restrict forcing |
| Strict schema | Stable contract | Limited features, so range checks belong in post-validation |
| Required vs nullable | Required gives downstream code a stable contract | Required forces fabrication on sparse documents; nullable costs only `null` handling |
| Enum with `"other"` vs free text | Analysable categories; new ones discoverable from the detail text | One more field to fill |

Refusals and truncation can still break the schema, so check the stop reason rather than assuming validity.

> [!WARNING]
> **Exam traps**
>
> - **"Tool use guarantees correct data"** → syntax only. Add validation for totals and field placement.
> - **"Mark every field required to avoid missing data"** → forces fabrication. Make fields optional or nullable when the document may omit them.
> - **"Use `tool_choice: auto` to guarantee structured output"** → `auto` may return text. Use `any` or a forced tool.
> - **"Force one specific tool when the document type is unknown"** → every document goes through one schema. Use `any` for multiple schemas; force only when a particular extraction must run first.
> - **"Enum with only known values"** → novel or ambiguous cases land in wrong buckets. Add `"unclear"` and `"other"` plus detail.
> - **"Parse JSON from the text reply and retry on errors"** → solves a syntax problem tool use removes. Pick the mechanism that eliminates the failure class.

## Check yourself

<details>
<summary>A strict-schema invoice pipeline has 2% of records whose line items do not add up to the total. Does a stricter schema fix this?</summary>

No; the error is semantic. Extract both totals and validate the difference in code ([4.4](4.4-validation-retry-loops.md)).
</details>

<details>
<summary>Contracts, invoices and receipts arrive mixed and unlabelled. Which <code>tool_choice</code> applies?</summary>

<code>any</code>: a structured result from whichever schema fits, without forcing a single one.
</details>

<details>
<summary>Papers often omit the sample size and the extractor returns plausible numbers. What schema change helps?</summary>

Make the field nullable, and show <code>null</code> in a prompt example, so absence is a valid answer.
</details>

> [!TIP]
> Forced `any`/`tool` is rejected on some newer models and with manual extended thinking; use `auto` + `strict: true` or `output_config.format` there (see [2.3](../02-tool-design-mcp-integration/2.3-tool-distribution-tool-choice.md)).
