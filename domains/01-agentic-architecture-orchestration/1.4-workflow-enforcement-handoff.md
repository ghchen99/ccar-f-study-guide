# 1.4 Implement multi-step workflows with enforcement and handoff patterns

## Knowledge of

- The difference between programmatic enforcement (hooks, prerequisite gates) and prompt-based guidance for workflow ordering.
- When deterministic compliance is required (e.g., identity verification before financial operations), prompt instructions alone have a non-zero failure rate.
- Structured handoff protocols for mid-process escalation that include customer details, root cause analysis, and recommended actions.

## Skills in

- Implementing programmatic prerequisites that block downstream tool calls until prerequisite steps have completed (e.g., blocking `process_refund` until `get_customer` has returned a verified customer ID).
- Decomposing multi-concern customer requests into distinct items, then investigating each in parallel using shared context before synthesizing a unified resolution.
- Compiling structured handoff summaries (customer ID, root cause, refund amount, recommended action) when escalating to human agents who lack access to the conversation transcript.

## Code snippets

### Programmatic prerequisite gate (Agent SDK)

The in-process `get_customer` tool records the verified ID. A `PreToolUse` hook denies `lookup_order` and `process_refund` until it exists. Prompt text alone has a non-zero failure rate.

```python
from typing import Any
from claude_agent_sdk import (
    ClaudeAgentOptions, HookMatcher, create_sdk_mcp_server, tool,
)

state: dict[str, Any] = {"verified_customer_id": None}  # one per conversation in real code


@tool("get_customer", "Look up a customer by email or phone. Returns the verified customer ID.", {"email": str})
async def get_customer(args):
    customer = {"id": "cus_123", "email": args["email"]}  # backend call goes here
    state["verified_customer_id"] = customer["id"]  # the gate keys on a recorded fact, not on the model claiming it verified
    return {"content": [{"type": "text", "text": str(customer)}]}


async def require_verified_customer(input_data, tool_use_id, context):
    if state["verified_customer_id"]:
        return {}
    return {
        "hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",
            "permissionDecisionReason": "Call get_customer and obtain a verified customer ID first.",  # fed back to Claude so it self-corrects instead of stalling
        }
    }


support = create_sdk_mcp_server(name="support", tools=[get_customer])  # + lookup_order, process_refund
options = ClaudeAgentOptions(
    mcp_servers={"support": support},
    allowed_tools=["mcp__support__get_customer", "mcp__support__lookup_order", "mcp__support__process_refund"],
    hooks={
        "PreToolUse": [
            HookMatcher(
                matcher="mcp__support__lookup_order|mcp__support__process_refund",  # gate only the dangerous tools; get_customer must stay callable
                hooks=[require_verified_customer],
            )
        ]
    },
)
```

def execute_tool(name: str, args: dict, state: dict) -> str:
    if name in GATED and not state.get("verified_customer_id"):
        return "BLOCKED: call get_customer first and use the verified customer ID."  # a model-readable message keeps the loop recoverable

### Structured handoff for a human who cannot see the transcript

```python
from typing import TypedDict


class EscalationHandoff(TypedDict):
    customer_id: str
    issue_summary: str
    root_cause: str  # the human cannot see the transcript, so the diagnosis must travel with the case
    order_ids: list[str]
    refund_amount_requested: float | None
    actions_already_taken: list[str]  # prevents the human repeating or contradicting work already done
    recommended_action: str
    escalation_reason: str  # customer request / policy gap / no progress
```

## Commentary: the concepts behind the code

SDK names are illustrative; know the concept, not the exact parameter.

### The design decision

When a wrong or skipped step has a financial, security or compliance cost, the ordering rule must be enforced by code that runs outside the model, not requested in a prompt. Prompts, few-shot examples and tool descriptions shape probabilities; a gate removes the failing path entirely. The model still decides what to do, but it cannot execute a prohibited action.

### Walk-through

- The gate keys on state written by the tool itself (`verified_customer_id` set inside `get_customer`), so it checks that verification actually happened rather than trusting the model's statement that it did.
- The hook is attached only to `lookup_order` and `process_refund`. `get_customer` must remain callable; gating it would deadlock the workflow.
- On denial, the reason text goes back to Claude, which then calls `get_customer` and retries. The failure is recoverable and self-correcting, and the sample-question failure (12% of runs skipping verification and looking up orders by stated name) becomes impossible rather than less frequent.
- The hand-written-loop variant returns a model-readable `BLOCKED` string instead of executing. The principle is the same: enforcement lives in the tool-execution layer, which the model cannot bypass.
- State is per conversation. A module-level global shared across users would let one customer's verification unlock another's session; the snippet's comment flags this.
- The handoff structure exists because the human agent has no transcript. A summary missing the root cause, amounts or actions taken forces the customer to repeat themselves and risks the human repeating or contradicting prior work.
- Multi-concern requests are split into distinct items and investigated with shared context, then merged into one resolution. Handling them as one blob risks answering one concern and dropping the other.

### Trade-offs and alternatives

- **Hooks/gates vs prompt instructions:** prompts are cheap and flexible but have a non-zero failure rate. Gates give guarantees but need code, tests and maintenance, and block legitimate variations if written too rigidly. Use gates for must-hold rules and prompts for preferences and style.
- **Gate strength:** checking that a verified ID exists is the minimum. A stricter gate also checks that the ID used in later calls matches the verified one, closing the case where the model verifies one account and then acts on another.
- **Prompt plus gate:** the prompt still earns its place by telling the model the correct order, which avoids wasted denied calls. The gate is the backstop, not the primary guidance.
- **Few-shot examples:** they improve compliance and calibration but remain probabilistic; they are the wrong tool for a hard prerequisite.
- **Routing classifier or tool subsetting:** this controls which tools are available per request type, not the order in which they run. It addresses a different problem and adds infrastructure.
- **Handoff detail vs size:** richer summaries cost tokens but save human time; keep them structured and concise.

### Exam traps

- "Strengthen the system prompt: verification is mandatory" (sample question 1, option B): probabilistic compliance is insufficient when errors cost money. Rule: deterministic enforcement beats prompt guidance when failure has a financial or compliance cost.
- "Add few-shot examples of calling `get_customer` first" (option C): same flaw. Rule: examples shape behaviour; they do not guarantee it.
- "Route requests through a classifier that enables only certain tools" (option D): controls availability, not sequence. Rule: match the fix to the diagnosed cause; do not add infrastructure that does not address it.
- Gating every tool, including `get_customer`: creates a deadlock. Rule: gate the downstream actions, not the prerequisite.
- Escalating with only "customer needs help": the human lacks the transcript. Rule: a handoff must stand alone (customer ID, root cause, amount, actions taken, recommendation).
- Sequential investigation of independent concerns: slower with no benefit. Rule: parallelise independent items, then synthesise.

### Check yourself

- An agent occasionally processes a refund before the policy check tool has run, despite explicit instructions. What change gives a guarantee? A programmatic prerequisite that blocks `process_refund` until the policy check result is recorded; more prompt text only lowers the failure rate.
- A verification gate only checks that "some customer ID exists." The agent verifies Customer A and then refunds an order belonging to Customer B. What is missing? The gate should compare the customer on the order or call arguments with the verified ID, not just test for presence.
- A human agent receives an escalation reading "customer upset about order." What should it contain instead? Customer ID, issue summary, root cause, amounts, actions already taken and a recommended next step, since the human cannot see the conversation.
