# 1.4 Implement multi-step workflows with enforcement and handoff patterns

> [!NOTE]
> **At a glance**
>
> - **Enforcement:** hooks and prerequisite gates guarantee ordering; prompt guidance only shapes probability.
> - **When it matters:** identity checks before financial operations need determinism, as prompts have a non-zero failure rate.
> - **Handoff:** mid-process escalation carries customer details, root cause and recommended actions.

## Example

### Programmatic prerequisite gate (Agent SDK)

The in-process `get_customer` tool records the verified ID. A `PreToolUse` hook denies `lookup_order` and `process_refund` until it exists.

```python
from typing import Any
from claude_agent_sdk import (
    ClaudeAgentOptions, HookMatcher, create_sdk_mcp_server, tool,
)

state: dict[str, Any] = {"verified_customer_id": None}  # one per conversation in real code


@tool("get_customer", "Look up a customer by email or phone. Returns the verified customer ID.", {"email": str})
async def get_customer(args):
    customer = {"id": "cus_123", "email": args["email"]}  # backend call goes here
    state["verified_customer_id"] = customer["id"]  # the gate keys on a recorded fact, not on the model claiming it verified
    return {"content": [{"type": "text", "text": str(customer)}]}


async def require_verified_customer(input_data, tool_use_id, context):
    if state["verified_customer_id"]:
        return {}
    return {
        "hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",
            "permissionDecisionReason": "Call get_customer and obtain a verified customer ID first.",  # fed back to Claude so it self-corrects instead of stalling
        }
    }


support = create_sdk_mcp_server(name="support", tools=[get_customer])  # + lookup_order, process_refund
options = ClaudeAgentOptions(
    mcp_servers={"support": support},
    allowed_tools=["mcp__support__get_customer", "mcp__support__lookup_order", "mcp__support__process_refund"],
    hooks={
        "PreToolUse": [
            HookMatcher(
                matcher="mcp__support__lookup_order|mcp__support__process_refund",  # gate only the dangerous tools; get_customer must stay callable
                hooks=[require_verified_customer],
            )
        ]
    },
)
```

### Same gate in a hand-written loop

```python
GATED = {"lookup_order", "process_refund"}


def execute_tool(name: str, args: dict, state: dict) -> str:
    if name in GATED and not state.get("verified_customer_id"):
        return "BLOCKED: call get_customer first and use the verified customer ID."  # a model-readable message keeps the loop recoverable
    ...
```

### Structured handoff for a human who cannot see the transcript

```python
from typing import TypedDict


class EscalationHandoff(TypedDict):
    customer_id: str
    issue_summary: str
    root_cause: str  # the human cannot see the transcript, so the diagnosis must travel with the case
    order_ids: list[str]
    refund_amount_requested: float | None
    actions_already_taken: list[str]  # prevents the human repeating or contradicting work already done
    recommended_action: str
    escalation_reason: str  # customer request / policy gap / no progress
```

## How it works

> [!IMPORTANT]
> **When a wrong or skipped step has a financial, security or compliance cost, enforce the rule in code outside the model.** Prompts, few-shot examples and tool descriptions shape probabilities; a gate removes the failing path while the model still decides what to do.

1. **Key the gate on tool-written state.** `verified_customer_id` is set inside `get_customer`, so the gate checks that verification happened, not that the model says it did.
2. **Gate downstream actions only.** The hook covers `lookup_order` and `process_refund`; gating `get_customer` would deadlock the workflow.
3. **Return a reason on denial.** Claude calls `get_customer` and retries, so the sample-question failure (12% of runs skipping verification) becomes impossible, not merely rarer.
4. **Enforce in the execution layer.** The hand-written loop returns a model-readable `BLOCKED` string; the model cannot bypass it.
5. **Scope state per conversation.** A shared module-level global would let one customer's verification unlock another's session.
6. **Make handoffs self-contained.** The human has no transcript, so missing root cause, amounts or actions taken forces repetition or contradiction.
7. **Split multi-concern requests.** Investigate items in parallel with shared context, then merge into one resolution so no concern is dropped.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Hooks / gates | Guaranteed ordering | Code, tests, maintenance; can block valid variations if rigid. Use for must-hold rules |
| Prompt instructions | Cheap and flexible | Non-zero failure rate; use for preferences and style |
| Prompt plus gate | Prompt avoids wasted denied calls; gate is the backstop | Both to maintain |
| Presence-only gate | Minimum check | Model may verify one account, then act on another; a stricter gate matches the ID used |
| Few-shot examples | Better compliance and calibration | Still probabilistic; wrong tool for a hard prerequisite |
| Classifier / tool subsetting | Controls which tools are available | Not their order; adds infrastructure |
| Rich handoff | Saves human time | Tokens; keep it structured and concise |

> [!WARNING]
> **Exam traps**
>
> - **"Strengthen the system prompt: verification is mandatory"** (sample question 1, option B) → probabilistic. Deterministic enforcement beats prompt guidance when failure costs money or compliance.
> - **"Add few-shot examples of calling `get_customer` first"** (option C) → examples shape behaviour, not guarantee it.
> - **"Route through a classifier that enables only certain tools"** (option D) → controls availability, not sequence. Match the fix to the diagnosed cause.
> - **"Gate every tool, including `get_customer`"** → deadlock. Gate the downstream actions, not the prerequisite.
> - **"Escalate with 'customer needs help'"** → the human lacks the transcript. A handoff must stand alone: customer ID, root cause, amount, actions taken, recommendation.
> - **"Investigate independent concerns sequentially"** → slower with no benefit. Parallelise, then synthesise.

## Check yourself

<details>
<summary>An agent sometimes processes a refund before the policy check runs, despite explicit instructions. What gives a guarantee?</summary>

A programmatic prerequisite that blocks <code>process_refund</code> until the policy check result is recorded. More prompt text only lowers the failure rate.
</details>

<details>
<summary>A gate only checks that "some customer ID exists"; the agent verifies Customer A, then refunds Customer B's order. What is missing?</summary>

The gate should compare the customer on the order or call arguments with the verified ID, not just test for presence.
</details>

<details>
<summary>A human receives an escalation reading "customer upset about order." What should it contain?</summary>

Customer ID, issue summary, root cause, amounts, actions already taken and a recommended next step, since the human cannot see the conversation.
</details>
