# 1.1 Design and implement agentic loops for autonomous task execution

## Knowledge of

- The agentic loop lifecycle: sending requests to Claude, inspecting `stop_reason` (`"tool_use"` vs `"end_turn"`), executing requested tools, and returning results for the next iteration.
- How tool results are appended to conversation history so the model can reason about the next action.
- The distinction between model-driven decision-making (Claude reasons about which tool to call next based on context) and pre-configured decision trees or tool sequences.

## Skills in

- Implementing agentic loop control flow that continues when `stop_reason` is `"tool_use"` and terminates when `stop_reason` is `"end_turn"`.
- Adding tool results to conversation context between iterations so the model can incorporate new information into its reasoning.
- Avoiding anti-patterns:
  - parsing natural language signals to determine loop termination
  - setting arbitrary iteration caps as the primary stopping mechanism
  - checking for assistant text content as a completion indicator

## Code snippets

### Raw Messages API loop (what the exam's `stop_reason` questions describe)

```python
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"  # any current model ID


def run_agent_loop(user_prompt: str, tools: list[dict], execute_tool) -> str:
    messages = [{"role": "user", "content": user_prompt}]
    while True:  # the model decides when to stop; the loop only reacts to stop_reason
        response = client.messages.create(
            model=MODEL, max_tokens=4096, tools=tools, messages=messages
        )
        # The whole assistant turn, tool_use blocks included, goes back into history
        messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason == "end_turn":
            return "".join(b.text for b in response.content if b.type == "text")

        if response.stop_reason == "tool_use":
            tool_results = [  # parallel tool calls arrive together; answer every one in a single user turn
                {
                    "type": "tool_result",
                    "tool_use_id": block.id,  # pairs each result with its request; a mismatch is an API error
                    "content": execute_tool(block.name, block.input),
                }
                for block in response.content
                if block.type == "tool_use"
            ]
            # Results go back as a user turn so Claude reasons over them next
            messages.append({"role": "user", "content": tool_results})
            continue

        raise RuntimeError(f"Unhandled stop_reason: {response.stop_reason}")  # e.g. max_tokens
```

### Anti-patterns

```python
for _ in range(10):                               # arbitrary cap as the primary stop condition: cuts off legitimate long tasks, wastes turns on short ones
    ...
if "I'm done" in response.content[0].text: ...    # parsing natural language for termination: phrasing varies, so it is brittle
if response.content[0].type == "text": break      # text can accompany tool_use blocks, so this exits mid-task
```

### Agent SDK: the loop is run for you

The SDK runs the same tool_use / tool_result cycle internally. You consume messages and read the final `ResultMessage`. `max_turns` and `max_budget_usd` are safety limits, not the normal stop mechanism.

```python
import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage, ResultError


async def main():
    try:
        async for message in query(
            prompt="Find and fix the failing tests in the auth module",
            options=ClaudeAgentOptions(
                allowed_tools=["Read", "Edit", "Bash", "Glob", "Grep"],
                max_turns=30,  # backstop against runaway loops; hitting it is a failure to investigate, not a normal exit
            ),
        ):
            if isinstance(message, ResultMessage):
                if message.subtype == "success":
                    print(message.result)
                else:  # error_max_turns, error_max_budget_usd, error_during_execution
                    print(f"Stopped: {message.subtype}")  # distinguish "finished" from "cut off" before trusting the output
    except ResultError as error:  # SDK 0.2.140+: raised after an error result is yielded
        print(f"Ended with {error.terminal_reason or error.subtype}: {error}")


asyncio.run(main())
```

## Commentary: the concepts behind the code

SDK names are illustrative; know the concept, not the exact parameter.

### The design decision

An agentic loop hands control flow to the model: the model chooses the next action, and the harness only executes it and reports back. The harness must therefore read the structured signal the API provides for "I want a tool" versus "I am finished" (`stop_reason`), not infer intent from prose. Structured signals are deterministic and stable across model versions; text heuristics and fixed iteration counts are guesses about what the model meant.

### Walk-through

- The full assistant turn is appended to history, including `tool_use` blocks. Without it, the next request would contain a `tool_result` with no matching request, and the model would lose its own record of what it asked for.
- Each `tool_result` carries the `tool_use_id` of its request. When Claude emits several tool calls in one response, every one needs an answer in the next user turn; a missing or mismatched id is a protocol error, not a soft failure.
- Results are returned as a user turn so the model reasons over fresh evidence before choosing the next step. This is what makes the loop model-driven: the sequence of tools is not scripted anywhere in the code.
- `end_turn` is the only normal exit. Any other `stop_reason` (for example the output being cut off by `max_tokens`) falls into the explicit `raise`, so a truncated answer is never returned as if it were complete.
- Text content cannot signal completion because a single response can contain both text ("Let me check that order") and a `tool_use` block. Exiting on text would abandon the task halfway.
- In the SDK version, `max_turns` and `max_budget_usd` exist to bound cost and runaway behaviour. Checking `ResultMessage.subtype` separates "completed" from "cut off by a limit", which matters because a limit-terminated result may be partial.

### Trade-offs and alternatives

- **Model-driven loop vs fixed pipeline or decision tree:** the loop adapts to unexpected intermediate results and handles open-ended tasks, but its path is not predictable. A fixed sequence gives predictability and easy testing but breaks when the task deviates. When a step must always happen (verification before refund), keep the loop model-driven and add enforcement around it (1.4, 1.5) rather than scripting the whole path.
- **Iteration caps:** useful as a safety net and cost control, harmful as the main stop mechanism. Too low truncates valid long tasks; too high does not stop a stuck loop sooner. Treat a cap being hit as an incident to investigate.
- **Raw Messages API vs Agent SDK:** the raw loop gives full control and is what the exam's `stop_reason` wording describes. The SDK removes boilerplate (history, tool execution, permissions, limits) at the cost of less visibility into each iteration.
- **Context growth:** every iteration adds tool output to history. Long loops raise cost and latency and risk context degradation, so large tool outputs should be trimmed (see 5.1).

### Exam traps

- "Stop after N iterations": an arbitrary cap is not a completion signal. Rule: terminate on the protocol's structured signal; use caps only as a backstop.
- "Parse the response for 'done' or 'complete'": natural language is probabilistic and phrasing drifts. Rule: do not infer control flow from free text when a structured field exists.
- "If the response contains text, the task is finished": text can accompany `tool_use`. Rule: check `stop_reason`, not content type.
- "Pre-define the tool sequence so the loop is predictable": this replaces model-driven reasoning with a script and fails on inputs the script did not anticipate. Rule: use fixed sequences only where the workflow truly is fixed.
- Answers that drop tool results from history to save tokens: the model then cannot reason about what it learned. Rule: results must reach the model before the next decision.

### Check yourself

- A loop exits whenever the latest response contains any text block, and users report tasks stopping after "Let me look that up." What is wrong? The response contained text plus a `tool_use` block; the exit should depend on `stop_reason` being `end_turn`, and the tool should have been executed and its result returned.
- An agent hits `max_turns` on 5% of runs and the team proposes raising the limit. What should be checked first? Whether those runs are stuck or looping on a failing tool; a higher cap only delays the same failure.
- The loop receives `stop_reason == "max_tokens"` and returns the text to the user. Why is that unsafe? The output was truncated, so the answer may be incomplete; it needs explicit handling rather than being treated as `end_turn`.
