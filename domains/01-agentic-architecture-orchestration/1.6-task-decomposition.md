# 1.6 Design task decomposition strategies for complex workflows

> [!NOTE]
> **At a glance**
>
> - **Prompt chaining:** fixed sequential steps, such as per-file review then a cross-file integration pass.
> - **Dynamic decomposition:** adaptive plans that generate subtasks from what each step discovers.
> - **Choosing:** fixed chains for predictable work, adaptive plans for open-ended investigation.

## Example

### Prompt chaining: per-file passes, then one integration pass

Each file gets the same depth of attention. A separate pass then looks only at cross-file data flow, using the per-file findings.

```python
import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage


async def ask(prompt: str) -> str:
    async for message in query(
        prompt=prompt,
        options=ClaudeAgentOptions(allowed_tools=["Read", "Grep", "Glob"], max_turns=15),
    ):
        if isinstance(message, ResultMessage) and message.subtype == "success":
            return message.result
    raise RuntimeError("no result")


async def review_pr(changed_files: list[str]) -> str:
    per_file = await asyncio.gather(*(  # independent per-file passes can run concurrently
        ask(f"Review {path} for local issues only (bugs, security). "  # "local only" keeps each pass focused and its depth uniform
            "Report location, issue, severity, suggested fix.")
        for path in changed_files
    ))
    findings = "\n\n".join(f"## {p}\n{f}" for p, f in zip(changed_files, per_file))
    return await ask(  # a separate pass: cross-file issues need all findings in view, which a per-file pass cannot have
        "Per-file findings are below. Now review only cross-file concerns: data flow between "
        "these files, inconsistent handling of the same pattern, broken contracts.\n\n" + findings
    )
```

### Dynamic decomposition for open-ended work

No fixed pipeline: map first, prioritise, and re-plan as dependencies appear.

```python
# The plan is not fixed up front: each step's findings decide the next, so the subtasks cannot be listed in advance
PLAN_PROMPT = """Add comprehensive tests to this legacy codebase.
1. Map the structure (entry points, modules, existing tests). Do not edit anything yet.
2. Rank areas by impact: untested code on critical paths first.
3. Write the plan, then execute it area by area. Update the plan when you find
   dependencies or discover that an area is bigger than expected."""
```

## How it works

> [!IMPORTANT]
> **Decomposition should follow how predictable the work is.** Give each call a task small enough for consistent depth, and fix the sequence statically only when it truly is static; otherwise generate and revise the plan from findings.

1. **One pass per file.** A narrow "local issues only" instruction avoids uneven depth, where early files get detail, later ones are cursory, and a pattern is flagged in one place but approved in another.
2. **Run passes concurrently.** Per-file passes are independent, so wall-clock time is the slowest file, not the sum.
3. **Add an integration pass.** It receives the per-file findings and checks only cross-file concerns; no single-file pass sees both sides, so per-file alone is incomplete.
4. **Map before acting.** "Do not edit anything yet" sets priorities from evidence, not from the first file opened.
5. **Re-plan on discovery.** A fixed plan would ignore or be broken by surprises such as hidden dependencies or an area far larger than assumed.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Prompt chaining | Consistent depth, easy debugging, validation between steps | More calls and tokens |
| One large prompt | Cheaper and simpler for small inputs | Degrades as input grows; a larger context window does not guarantee even attention |
| Fixed pipeline | Predictable, testable, auditable | Cannot adapt to discoveries; suits known multi-aspect reviews |
| Dynamic plan | Handles uncertainty | Harder to predict; bound it with a budget, turn cap or checkpoint |
| Per-file passes | Scale with file count | Cross-file issues need the integration pass |
| Per-concern passes | Focus on one dimension (security, then performance) | Multiply reads of the same files |

Integration input can itself grow large: filter or summarise findings while preserving locations.

> [!WARNING]
> **Exam traps**
>
> - **"Use a bigger context window so the whole PR fits in one pass"** → capacity is not consistent attention. Split into per-file passes plus an integration pass.
> - **"Run the review three times and keep findings present in all runs"** → suppresses real but intermittent issues. Address task size and focus, not output filtering.
> - **"Hard-code a fixed pipeline for an exploratory task"** → cannot adapt. Open-ended investigation needs adaptive decomposition.
> - **"Let the agent decide everything dynamically for a predictable review"** → loses reliability and repeatability. Predictable work suits prompt chaining.
> - **"Only per-file reviews, they are more thorough"** → misses cross-file defects. Add the integration pass.
> - **"Start writing tests immediately on a legacy codebase"** → effort lands on whatever was seen first. Map and prioritise by impact first.

## Check yourself

<details>
<summary>A 14-file PR review flags a missing null check in one file, approves the same pattern in another, and misses an API contract change between modules. What restructure fits?</summary>

Per-file local passes for consistent depth, plus a separate integration pass over the combined findings for cross-file concerns.
</details>

<details>
<summary>Why is a fixed task list a poor fit for adding tests to an unfamiliar legacy system?</summary>

Structure and dependencies are unknown until explored. Build the plan after mapping and revise it as new dependencies surface.
</details>

<details>
<summary>A nightly job always performs the same three review aspects on every change. Which decomposition suits it?</summary>

Prompt chaining: the aspects are known in advance, and the sequence benefits from predictability.
</details>
