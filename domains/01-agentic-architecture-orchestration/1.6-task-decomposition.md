# 1.6 Design task decomposition strategies for complex workflows

## At a glance

- When to use fixed sequential pipelines (prompt chaining) versus dynamic adaptive decomposition based on intermediate findings.
- Prompt chaining patterns that break reviews into sequential steps (e.g., analyze each file individually, then run a cross-file integration pass).
- The value of adaptive investigation plans that generate subtasks based on what is discovered at each step.

## Example

### Prompt chaining: per-file passes, then one integration pass

Each file gets the same depth of attention. A separate pass then looks only at cross-file data flow, using the per-file findings.

```python
import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage


async def ask(prompt: str) -> str:
    async for message in query(
        prompt=prompt,
        options=ClaudeAgentOptions(allowed_tools=["Read", "Grep", "Glob"], max_turns=15),
    ):
        if isinstance(message, ResultMessage) and message.subtype == "success":
            return message.result
    raise RuntimeError("no result")


async def review_pr(changed_files: list[str]) -> str:
    per_file = await asyncio.gather(*(  # independent per-file passes can run concurrently
        ask(f"Review {path} for local issues only (bugs, security). "  # "local only" keeps each pass focused and its depth uniform
            "Report location, issue, severity, suggested fix.")
        for path in changed_files
    ))
    findings = "\n\n".join(f"## {p}\n{f}" for p, f in zip(changed_files, per_file))
    return await ask(  # a separate pass: cross-file issues need all findings in view, which a per-file pass cannot have
        "Per-file findings are below. Now review only cross-file concerns: data flow between "
        "these files, inconsistent handling of the same pattern, broken contracts.\n\n" + findings
    )
```

### Dynamic decomposition for open-ended work

No fixed pipeline: map first, prioritise, and re-plan as dependencies appear.

```python
# The plan is not fixed up front: each step's findings decide the next, so the subtasks cannot be listed in advance
PLAN_PROMPT = """Add comprehensive tests to this legacy codebase.
1. Map the structure (entry points, modules, existing tests). Do not edit anything yet.
2. Rank areas by impact: untested code on critical paths first.
3. Write the plan, then execute it area by area. Update the plan when you find
   dependencies or discover that an area is bigger than expected."""
```

## Why this matters

> [!IMPORTANT]
> **The principle**

Decomposition strategy should follow how predictable the work is. When the aspects of a task are known in advance (review each changed file, then check how they interact), a fixed chain of focused passes is more reliable and cheaper to reason about. When the shape of the work only emerges from exploration (a legacy codebase with unknown structure), the plan must be generated and revised from intermediate findings. The principle is to give each model call a task small enough to be done with consistent depth, and to decide the sequence statically only when it truly is static.

**The flow**

- Each file gets its own pass with a narrow instruction ("local issues only"). A single pass over many files tends to give uneven depth: early files get detailed comments, later ones get cursory ones, and the same pattern may be flagged in one place and approved in another. Separate passes make attention uniform.
- Per-file passes are independent, so they run concurrently. Wall-clock time is that of the slowest file, not the sum.
- The integration pass receives the per-file findings and looks only at cross-file concerns: data flow, inconsistent handling of the same pattern, broken contracts. Splitting local and cross-file analysis prevents either from crowding out the other and keeps each prompt focused.
- A cross-file problem cannot be found by any single-file pass because no pass sees both sides. The integration step exists for that reason, which is why per-file passes alone are an incomplete design.
- The open-ended prompt starts with mapping and ranking and tells the agent to update the plan on discovering dependencies. If the plan were fixed up front, a surprise (a module with hidden dependencies, an area far larger than assumed) would either be ignored or break the plan.
- "Do not edit anything yet" in step 1 separates understanding from acting, so priorities are set from evidence rather than from the first file the agent opens.

## Trade-offs

- **Prompt chaining vs one large prompt:** chaining costs more calls and tokens but gives consistent depth, easier debugging (which stage failed) and the option to validate between steps. A single prompt is cheaper and simpler for small inputs but degrades as input grows.
- **Fixed pipeline vs dynamic decomposition:** fixed pipelines are predictable, testable and auditable; dynamic plans handle uncertainty but are harder to predict and bound. Use fixed chains for known multi-aspect reviews and dynamic plans for investigation.
- **Per-file vs per-concern passes:** per-file passes scale with file count; per-concern passes (security, then performance) multiply reads of the same files. Choose by which dimension causes the quality problem.
- **Integration-pass input size:** passing every per-file finding verbatim can itself grow large; filter or summarise while preserving locations so cross-file reasoning stays possible.
- **A larger context window does not remove the issue:** more room to read does not guarantee evenly distributed attention, so decomposition remains useful on large inputs.
- **Bounding dynamic plans:** open-ended plans need limits (a budget, turn cap or checkpoint) so exploration does not run unbounded.

> [!WARNING]
> **Exam traps**

- "Use a bigger context window so the whole PR fits in one pass": capacity is not the same as consistent attention. Rule: split large reviews into per-file passes plus an integration pass.
- "Run the review three times and keep only the findings that appear in all runs": suppresses real but intermittently detected issues. Rule: address the cause of inconsistency (task size and focus) rather than filtering outputs.
- "Hard-code a fixed pipeline for an exploratory task": it cannot adapt to discoveries. Rule: open-ended investigation needs adaptive decomposition.
- "Let the agent decide everything dynamically for a predictable multi-aspect review": gives up reliability and repeatability for no gain. Rule: predictable work suits prompt chaining.
- "Only per-file reviews, since they are more thorough": misses cross-file defects. Rule: add the integration pass.
- Starting to write tests immediately on a legacy codebase: effort lands on whatever was seen first. Rule: map and prioritise by impact first.

## Quick check

- A 14-file PR review flags a missing null check in one file and approves the identical pattern in another, and misses an API contract change between two modules. What restructure fits? Per-file local passes for consistent depth, plus a separate integration pass over the combined findings for cross-file concerns.
- A team must add tests to an unfamiliar legacy system. Why is a fixed task list a poor fit? The structure and dependencies are unknown until explored; the plan should be built after mapping and revised as new dependencies surface.
- A nightly job always performs the same three review aspects on every change. Which decomposition style suits it? Prompt chaining, because the aspects are known in advance and the sequence benefits from predictability.
