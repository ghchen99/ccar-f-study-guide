# 1.7 Manage session state, resumption, and forking

## At a glance

- Named session resumption using `--resume <session-name>` to continue a specific prior conversation.
- `fork_session` for creating independent branches from a shared analysis baseline to explore divergent approaches.
- The importance of informing the agent about changes to previously analyzed files when resuming sessions after code modifications.
- Why starting a new session with a structured summary is more reliable than resuming with stale tool results.

## Example

### Capture the session ID, then resume

```python
import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage

TOOLS = ["Read", "Grep", "Glob"]


async def run(prompt: str, **opts) -> str | None:
    session_id = None
    try:
        async for message in query(prompt=prompt, options=ClaudeAgentOptions(allowed_tools=TOOLS, **opts)):
            if isinstance(message, ResultMessage):
                session_id = message.session_id  # present on success and error results
    except Exception as error:
        print(f"Session ended with an error: {error}")  # single-shot query() raises after an error result
    return session_id


async def main():
    session_id = await run("Analyze the auth module and suggest improvements")

    # Resume when prior context is mostly valid; tell it what changed
    await run(
        "auth/session.py and auth/tokens.py changed since your analysis (expiry moved to config). "  # the session cannot see edits made outside it; stale tool results look current to the model
        "Re-read only those two files and update your findings.",  # targeted re-analysis is cheaper than re-exploring everything
        resume=session_id,
    )


asyncio.run(main())
```

### Fork: two approaches from one shared baseline

Forking copies the history into a new session; the original is untouched. It branches the conversation, not the filesystem, so edits made by a fork are real.

```python
async def compare_approaches(baseline_id: str):
    oauth_id = await run(
        "Outline how OAuth2 would work for the auth module",
        resume=baseline_id, fork_session=True, max_turns=5,  # fork: the baseline stays untouched, so the other branch starts from the same analysis
    )
    jwt_id = await run("Continue with the JWT approach", resume=baseline_id)  # a plain resume would continue the baseline itself
    return oauth_id, jwt_id
```

Standalone helpers also exist:

```python
from claude_agent_sdk import fork_session, list_sessions, rename_session

forked = fork_session(baseline_id, title="Try the OAuth approach")
rename_session(baseline_id, "auth-investigation")  # human-readable name
```

### Start fresh with an injected summary when tool results are stale

```python
# Pinning a commit in the summary makes its validity checkable
summary = """Prior findings (verified against commit abc123):
- Token refresh lives in auth/tokens.py
- Session store is Redis-backed
The following files have since changed: auth/tokens.py. Re-check only those."""
await run(f"{summary}\n\nNow design the migration plan.")
```

### CLI

```bash
claude --resume auth-investigation   # continue a named session
```

In Python, `ClaudeSDKClient` keeps one session across `client.query()` calls with no ID handling (`async with ClaudeSDKClient(options) as client:`), which suits multi-turn work in a single process. Use `resume=` / `fork_session=True` when IDs must survive across processes. `resume_session_at=<message uuid>` with `fork_session=True`, or `fork_session(session_id, up_to_message_id=...)`, branches from an earlier point.

## Why this matters

> [!IMPORTANT]
> **The principle**

A session is accumulated context, and context is only as trustworthy as the world it describes. Resume when the prior context is still mostly true; fork when several futures should grow from one shared, valid baseline; start fresh with a distilled summary when the old tool results can no longer be trusted. The principle is to treat stale context as a reliability risk, not a free asset, and to tell the model explicitly what changed instead of hoping it notices.

**The flow**

- Capturing `session_id` from the result (on success and on error) is what makes continuation possible across runs. Without an identifier there is nothing to resume.
- The resume prompt names the changed files and asks for a targeted re-read. The model cannot see edits made outside the session, and its earlier `Read` results still sit in history looking current. Unprompted, it may reason confidently from outdated file contents.
- Naming only the changed files avoids a full re-exploration, which keeps cost and latency down while correcting exactly what is stale.
- Forking copies history into a new session and leaves the original untouched, so two approaches (OAuth vs JWT) start from identical analysis and diverge without contaminating each other. Two sequential turns in one session would let the second approach be influenced by the first.
- Forking branches the conversation, not the filesystem. If a fork edits files, those edits are real and visible to every other branch, so exploratory forks should stay read-only or work in isolated copies.
- The fresh-start pattern carries forward only verified conclusions, pinned to a commit, plus an explicit list of what changed. The model gets a clean context containing no obsolete tool output, which is more reliable than a long history whose early parts may be wrong.
- A named session (CLI `--resume <name>`) is a convenience for humans continuing an investigation across days; the underlying mechanism is the same.

## Trade-offs

- **Resume vs fresh start:** resuming preserves detailed context and saves re-discovery, but it carries stale results and accumulated tokens. A fresh start with a summary is cheaper per turn and cleaner, but loses nuance and depends on the quality of the summary. Resume when little has changed; start fresh when much has.
- **Fork vs parallel fresh sessions:** a fork inherits the shared analysis, so comparisons are fair and the baseline cost is not paid twice. Fresh sessions are independent but each must redo the baseline.
- **Fork vs sequential exploration in one session:** sequential work pollutes later steps with earlier conclusions and makes it hard to return to the baseline.
- **Long-lived sessions:** history grows, raising cost and the risk of context degradation. Periodic summarise-and-restart keeps a long investigation sharp.
- **Single-process continuation:** keeping one client session across turns avoids ID handling; persisting IDs is only needed when work crosses processes.
- **Informing the model of changes vs relying on re-exploration:** targeted notes are cheaper and faster; a full re-read is safer when the change set is large or unknown.

> [!WARNING]
> **Exam traps**

- "Resume the session and carry on; the model will notice file changes": it will not see edits made outside the session. Rule: stale tool results are a hazard; tell the agent what changed or start fresh.
- "Always resume, to preserve context": ignores staleness. Rule: choose by validity of prior context, not by convenience.
- "Always restart and re-explore everything after any change": wastes work when most findings still hold. Rule: targeted re-analysis of changed files when the rest is valid.
- "Use fork to explore alternatives, and expect file changes to be isolated": forks isolate conversation, not the filesystem. Rule: know what a mechanism isolates.
- "Explore both approaches in sequence in the same session": the second is biased by the first. Rule: use forks for independent branches from a shared baseline.
- "Copy the whole old transcript into the new session as the summary": reintroduces the stale results. Rule: summarise verified conclusions, flag changed areas.

## Quick check

- A developer resumes yesterday's investigation after a teammate refactored two modules, and the agent keeps citing the old structure. What was missed? The resumed session held stale tool results and was not told about the changes; inform it of the modified files for targeted re-analysis, or start fresh with a summary.
- Two refactoring strategies need to be compared starting from the same codebase analysis. Which mechanism fits? Fork the analysed session once per strategy so each branch begins from the identical baseline and neither affects the other.
- A fork was used to "try" a change and the repository now contains its edits. Why? Forking copies conversation history, not files; exploratory branches that write to the working tree change shared state.
