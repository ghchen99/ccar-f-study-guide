# 1.7 Manage session state, resumption, and forking

> [!NOTE]
> **At a glance**
>
> - **Resume:** `--resume <session-name>` continues a specific prior conversation.
> - **Fork:** `fork_session` branches independent paths from a shared analysis baseline.
> - **Staleness:** tell a resumed agent which files changed since its analysis.
> - **Fresh start:** a structured summary beats resuming with stale tool results.

## Example

### Capture the session ID, then resume

```python
import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage

TOOLS = ["Read", "Grep", "Glob"]


async def run(prompt: str, **opts) -> str | None:
    session_id = None
    try:
        async for message in query(prompt=prompt, options=ClaudeAgentOptions(allowed_tools=TOOLS, **opts)):
            if isinstance(message, ResultMessage):
                session_id = message.session_id  # present on success and error results
    except Exception as error:
        print(f"Session ended with an error: {error}")  # single-shot query() raises after an error result
    return session_id


async def main():
    session_id = await run("Analyze the auth module and suggest improvements")

    # Resume when prior context is mostly valid; tell it what changed
    await run(
        "auth/session.py and auth/tokens.py changed since your analysis (expiry moved to config). "  # the session cannot see edits made outside it; stale tool results look current to the model
        "Re-read only those two files and update your findings.",  # targeted re-analysis is cheaper than re-exploring everything
        resume=session_id,
    )


asyncio.run(main())
```

### Fork: two approaches from one shared baseline

Forking copies the history into a new session; the original is untouched. It branches the conversation, not the filesystem, so edits made by a fork are real.

```python
async def compare_approaches(baseline_id: str):
    oauth_id = await run(
        "Outline how OAuth2 would work for the auth module",
        resume=baseline_id, fork_session=True, max_turns=5,  # fork: the baseline stays untouched, so the other branch starts from the same analysis
    )
    jwt_id = await run("Continue with the JWT approach", resume=baseline_id)  # a plain resume would continue the baseline itself
    return oauth_id, jwt_id
```

Standalone helpers also exist:

```python
from claude_agent_sdk import fork_session, list_sessions, rename_session

forked = fork_session(baseline_id, title="Try the OAuth approach")
rename_session(baseline_id, "auth-investigation")  # human-readable name
```

### Start fresh with an injected summary when tool results are stale

```python
# Pinning a commit in the summary makes its validity checkable
summary = """Prior findings (verified against commit abc123):
- Token refresh lives in auth/tokens.py
- Session store is Redis-backed
The following files have since changed: auth/tokens.py. Re-check only those."""
await run(f"{summary}\n\nNow design the migration plan.")
```

### CLI

```bash
claude --resume auth-investigation   # continue a named session
```

In Python, `ClaudeSDKClient` keeps one session across `client.query()` calls with no ID handling (`async with ClaudeSDKClient(options) as client:`), which suits multi-turn work in one process; use `resume=` / `fork_session=True` when IDs must survive across processes. `resume_session_at=<message uuid>` with `fork_session=True`, or `fork_session(session_id, up_to_message_id=...)`, branches from an earlier point.

## How it works

> [!IMPORTANT]
> **Context is only as trustworthy as the world it describes.** Resume when it is mostly still true, fork when several futures should grow from one valid baseline, and start fresh with a distilled summary when old tool results can no longer be trusted.

1. **Capture `session_id`.** Take it from the result, on success and error, or there is nothing to resume.
2. **Name what changed.** The model cannot see outside edits and its earlier `Read` results look current, so it may reason confidently from outdated contents.
3. **Re-read only changed files.** Targeted correction fixes exactly what is stale, keeping cost and latency down.
4. **Fork for alternatives.** History is copied and the original untouched, so OAuth and JWT start from identical analysis; sequential turns in one session would bias the second.
5. **Remember forks branch the conversation, not the filesystem.** A fork's file edits are real and visible to every branch, so keep exploratory forks read-only or in isolated copies.
6. **Start fresh with verified conclusions.** Pin them to a commit and list what changed; clean context beats a long history whose early parts may be wrong.

A named session (CLI `--resume <name>`) is a convenience for humans continuing across days; the mechanism is the same.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Resume | Keeps detailed context, saves re-discovery | Carries stale results and accumulated tokens; use when little has changed |
| Fresh start with summary | Cheaper per turn, cleaner | Loses nuance; depends on summary quality; use when much has changed |
| Fork | Inherits shared analysis, fair comparison, baseline paid once | Shares the filesystem |
| Parallel fresh sessions | Fully independent | Each redoes the baseline |
| Sequential exploration in one session | Simple | Earlier conclusions pollute later steps; hard to return to baseline |
| Long-lived session | Continuity | Growing cost and context degradation; summarise and restart periodically |
| Targeted change notes | Cheaper and faster | A full re-read is safer when the change set is large or unknown |

Persist IDs only when work crosses processes; a single `ClaudeSDKClient` session needs none.

> [!WARNING]
> **Exam traps**
>
> - **"Resume and carry on; the model will notice file changes"** → it will not see outside edits. Tell the agent what changed or start fresh.
> - **"Always resume, to preserve context"** → ignores staleness. Choose by validity of prior context, not convenience.
> - **"Always restart and re-explore after any change"** → wastes work when most findings hold. Re-analyse only changed files.
> - **"Fork to explore, and file changes stay isolated"** → forks isolate conversation, not the filesystem. Know what a mechanism isolates.
> - **"Explore both approaches in sequence in one session"** → the second is biased by the first. Use forks from a shared baseline.
> - **"Copy the whole old transcript in as the summary"** → reintroduces stale results. Summarise verified conclusions and flag changed areas.

## Check yourself

<details>
<summary>A developer resumes yesterday's investigation after a teammate refactored two modules, and the agent cites the old structure. What was missed?</summary>

The resumed session held stale tool results and was not told about the changes. Inform it of the modified files for targeted re-analysis, or start fresh with a summary.
</details>

<details>
<summary>Two refactoring strategies must be compared from the same codebase analysis. Which mechanism fits?</summary>

Fork the analysed session once per strategy, so each branch begins from the identical baseline and neither affects the other.
</details>

<details>
<summary>A fork was used to "try" a change and the repository now contains its edits. Why?</summary>

Forking copies conversation history, not files. Branches that write to the working tree change shared state.
</details>
