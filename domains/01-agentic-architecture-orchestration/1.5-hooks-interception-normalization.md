# 1.5 Apply Agent SDK hooks for tool call interception and data normalization

> [!NOTE]
> **At a glance**
>
> - **`PostToolUse`:** intercepts results to transform them before the model sees them.
> - **`PreToolUse`:** intercepts outgoing calls to enforce rules, such as blocking refunds above a threshold.
> - **`input_data`:** always has `session_id`, `cwd`, `hook_event_name`, plus `tool_name`/`tool_input` or `tool_response`; tool contents follow the tool's own schema.
> - **Hooks vs prompts:** hooks give deterministic guarantees; prompts give probabilistic compliance.

## Example

The `amount` field comes from the tool's schema, defined on the MCP server (see [scenario 01](../../scenarios/01-customer-support-resolution-agent/README.md)):

```python
@tool("process_refund", "Refund an order.", {"order_id": str, "amount": float})
async def process_refund(args): ...
```

### PreToolUse: block refunds over a threshold and redirect to escalation

```python
from claude_agent_sdk import ClaudeAgentOptions, HookMatcher

REFUND_LIMIT_USD = 500


async def block_large_refunds(input_data, tool_use_id, context):
    # tool_input comes from the model; the schema is not enforced here, so check the type
    amount = (input_data.get("tool_input") or {}).get("amount")
    is_number = isinstance(amount, (int, float)) and not isinstance(amount, bool)
    if is_number and amount <= REFUND_LIMIT_USD:
        return {}  # empty result = allow; only a confirmed, in-limit amount passes
    return {
        "hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",
            # The reason is what Claude reads, so it names the alternative workflow
            "permissionDecisionReason": (
                f"Refunds over ${REFUND_LIMIT_USD}, or refunds with a missing or non-numeric amount, "
                "need human approval. Call escalate_to_human with the full case summary instead."
            ),
        }
    }
```

### PostToolUse: normalise heterogeneous formats before the model sees them

```python
from datetime import datetime, timezone

STATUS_NAMES = {0: "pending", 1: "shipped", 2: "delivered", 3: "returned"}


def normalise(payload: dict) -> dict:
    out = dict(payload)
    for key, value in payload.items():
        if key.endswith("_at") and isinstance(value, (int, float)):  # Unix timestamp; one canonical format stops the model mis-comparing dates across tools
            out[key] = datetime.fromtimestamp(value, tz=timezone.utc).isoformat()
    if isinstance(payload.get("status"), int):  # numeric status code; an unmapped code would otherwise be guessed at
        out["status"] = STATUS_NAMES.get(payload["status"], "unknown")
    return out


async def normalise_tool_output(input_data, tool_use_id, context):
    response = input_data.get("tool_response")
    if not isinstance(response, dict):  # log tool_response once to see your tool's real shape
        return {}
    return {
        "hookSpecificOutput": {
            "hookEventName": "PostToolUse",
            "updatedToolOutput": normalise(response),
        }
    }


options = ClaudeAgentOptions(
    hooks={
        "PreToolUse": [HookMatcher(matcher="mcp__support__process_refund", hooks=[block_large_refunds], on_failure="block")],  # before execution: can prevent the action; a crashing hook blocks instead of allowing
        "PostToolUse": [HookMatcher(matcher="mcp__support__lookup_order", hooks=[normalise_tool_output])],  # after execution: can only reshape the result
    }
)
```

Hooks run in your process, outside the context window, and are deterministic: use them when the rule must always hold.

## How it works

> [!IMPORTANT]
> **Hooks put deterministic code at the boundary between the model and the outside world.** A pre-hook can veto or redirect an action; a post-hook can reshape what the model sees. Rules and data hygiene then never depend on the model remembering them.

1. **Block before execution.** `block_large_refunds` stops over-limit calls reaching the backend however the model reasoned; a prompt rule would fail rarely, as an unauthorised payment.
2. **Fail closed.** Allow only when `amount` is confirmed as a number within the limit; a missing key, `"500"` or `None` falls through to deny.
3. **Redirect on denial.** The reason names `escalate_to_human` with a full summary; a bare "denied" leaves the agent to improvise.
4. **Intervene only on violations.** Returning `{}` means allow, keeping the happy path fast.
5. **Normalise after execution.** `normalise_tool_output` turns Unix timestamps into ISO 8601 and status codes into names, so the model need not infer `2` means delivered or do epoch arithmetic.
6. **Choose hooks for third-party tools.** Normalising in a hook fixes MCP servers you do not own, or tools that disagree on format, in one place.
7. **Mind pre versus post.** Only a pre-hook prevents an action; a post-hook runs after the side effect. Hooks cost no tokens and cannot be talked out of a decision.

### Reading `input_data` safely

- **Shape:** every event has `session_id`, `cwd`, `hook_event_name`; `PreToolUse` adds `tool_name`, `tool_input`; `PostToolUse` adds `tool_input`, `tool_response`. Python gives a plain dict, so a wrong key is a runtime `KeyError`, not a compile error.
- **Do not trust the schema:** it is declared on the tool, but a `PreToolUse` hook runs before the handler, and `tool_response` from a third-party MCP server may change between versions.
- **Read defensively:** use `.get()` with a default (`(input_data.get("tool_input") or {}).get("amount")`), never `input_data["tool_input"]["amount"]`, then check the type; `"500" <= 500` raises and `True` passes as an `int`.
- **Enforce the shape:** for must-hold rules, validate and deny when unsure. `on_failure="block"` (`onFailure: "block"` in TypeScript) makes a raising hook block the action. For normalisation, return `{}` rather than guess.
- **Inspect first:** log `input_data` once on a real run. A schema model such as Pydantic can formalise the check, but the hook must still handle failures.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Hook | Exact, testable without the model, immune to prompt drift | Code to maintain; a wrong rule fails on every call, though deterministically. Use for hard limits |
| Prompt rule | Flexible for judgement calls | Probabilistic; use for soft guidance |
| Tool-internal validation | Also guarantees compliance | Hides policy in each tool; errors after dispatch. Hooks centralise policy and can steer |
| Hook normalisation | Right for third-party or heterogeneous tools | Extra code; if you own the tool, clean data at source |
| Normalising | Changes representation | Different problem from trimming fields to save context ([5.1](../05-context-management-reliability/5.1-context-preservation.md)); can be combined |
| Hard block | Suits unambiguous policy | Routing to a human suits cases needing judgement |

> [!WARNING]
> **Exam traps**
>
> - **"Add the refund threshold to the system prompt"** → probabilistic. Enforce must-hold rules in code.
> - **"Run a second model call to check each refund"** → latency, cost and another probabilistic step where a comparison is exact. Do not use a model for a deterministic check.
> - **"Fine-tune or few-shot the model on date formats"** → treats a data-format problem as behaviour. Fix it at the boundary with a `PostToolUse` hook.
> - **"Use `PostToolUse` to stop a refund"** → the action has already happened. Prevention needs pre-execution interception.
> - **"Return only 'denied'"** → no path forward. Pair a block with a redirect, such as human escalation.
> - **"Have the model convert Unix timestamps"** → unreliable arithmetic on every call. Exact transformations belong in code.
> - **`input_data["tool_input"]["amount"]` unchecked** → a missing or string amount raises, or with `.get(..., 0)` passes as zero. Use `.get()`, check types, fail closed.

## Check yourself

<details>
<summary>Orders over $500 occasionally get auto-refunded though the prompt forbids it. What is the most reliable fix?</summary>

A pre-execution hook that denies <code>process_refund</code> above the threshold and points the model to the escalation tool.
</details>

<details>
<summary>Two MCP tools return dates as epoch integers and ISO strings, and the agent miscomputes the return window. Where is the fix?</summary>

A post-execution hook that normalises both to one format before the model sees the output.
</details>

<details>
<summary>A team proposes a <code>PostToolUse</code> hook to reject unauthorised refunds. Why does it fail?</summary>

Post hooks run after the tool executes, so the refund has already been issued. The check must run before execution.
</details>

<details>
<summary>A refund hook uses <code>input_data["tool_input"].get("amount", 0)</code>, and a call with no amount gets through. Why?</summary>

The default of <code>0</code> makes a missing value look like a valid small refund. Type-check the value and deny anything not confirmed as a number within the limit.
</details>

> [!TIP]
> `updatedToolOutput` replaces a tool's output before Claude sees it.
