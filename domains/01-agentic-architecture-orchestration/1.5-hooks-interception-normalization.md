# 1.5 Apply Agent SDK hooks for tool call interception and data normalization

## Knowledge of

- Hook patterns (e.g., `PostToolUse`) that intercept tool results for transformation before the model processes them.
- Hook patterns that intercept outgoing tool calls to enforce compliance rules (e.g., blocking refunds above a threshold).
- The distinction between using hooks for deterministic guarantees versus relying on prompt instructions for probabilistic compliance.

## Skills in

- Implementing `PostToolUse` hooks to normalize heterogeneous data formats (Unix timestamps, ISO 8601, numeric status codes) from different MCP tools before the agent processes them.
- Implementing tool call interception hooks that block policy-violating actions (e.g., refunds exceeding $500) and redirect to alternative workflows (e.g., human escalation).
- Choosing hooks over prompt-based enforcement when business rules require guaranteed compliance.

## Code snippets

### PreToolUse: block refunds over a threshold and redirect to escalation

```python
from claude_agent_sdk import ClaudeAgentOptions, HookMatcher

REFUND_LIMIT_USD = 500


async def block_large_refunds(input_data, tool_use_id, context):
    amount = input_data["tool_input"].get("amount", 0)
    if amount <= REFUND_LIMIT_USD:
        return {}  # empty result = allow; the hook only intervenes on violations
    return {
        "hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",
            # The reason is what Claude reads, so it names the alternative workflow
            "permissionDecisionReason": (
                f"Refunds over ${REFUND_LIMIT_USD} need human approval. "
                "Call escalate_to_human with the full case summary instead."
            ),
        }
    }
```

### PostToolUse: normalise heterogeneous formats before the model sees them

```python
from datetime import datetime, timezone

STATUS_NAMES = {0: "pending", 1: "shipped", 2: "delivered", 3: "returned"}


def normalise(payload: dict) -> dict:
    out = dict(payload)
    for key, value in payload.items():
        if key.endswith("_at") and isinstance(value, (int, float)):  # Unix timestamp; one canonical format stops the model mis-comparing dates across tools
            out[key] = datetime.fromtimestamp(value, tz=timezone.utc).isoformat()
    if isinstance(payload.get("status"), int):  # numeric status code; an unmapped code would otherwise be guessed at
        out["status"] = STATUS_NAMES.get(payload["status"], "unknown")
    return out


async def normalise_tool_output(input_data, tool_use_id, context):
    response = input_data["tool_response"]
    if not isinstance(response, dict):  # log tool_response once to see your tool's real shape
        return {}
    return {
        "hookSpecificOutput": {
            "hookEventName": "PostToolUse",
            "updatedToolOutput": normalise(response),
        }
    }


options = ClaudeAgentOptions(
    hooks={
        "PreToolUse": [HookMatcher(matcher="mcp__support__process_refund", hooks=[block_large_refunds])],  # before execution: can prevent the action
        "PostToolUse": [HookMatcher(matcher="mcp__support__lookup_order", hooks=[normalise_tool_output])],  # after execution: can only reshape the result
    }
)
```

Hooks run in your process, outside the context window, and are deterministic. Use them when the rule must always hold.

## Commentary: the concepts behind the code

SDK names are illustrative; know the concept, not the exact parameter.

### The design decision

Hooks place deterministic code at the boundary between the model and the outside world. A pre-execution hook can veto or redirect an action; a post-execution hook can reshape what the model sees. Both exist so that rules and data hygiene do not depend on the model remembering them. The principle: deterministic enforcement beats probabilistic prompt guidance when failure has a financial or compliance cost, and cleaning data once in code beats asking the model to cope with every format in every conversation.

### Walk-through

- `block_large_refunds` runs before `process_refund` executes. If the amount exceeds the limit, the call never reaches the backend, regardless of how persuasive the customer or how the model reasoned. A prompt saying "never refund more than $500" would work most of the time, and the rare failure would be an unauthorised payment.
- The denial reason names the alternative (`escalate_to_human` with a full summary). The model reads the reason, so a block that also redirects turns a dead end into the intended workflow. A bare "denied" leaves the agent to improvise.
- Returning `{}` means allow. The hook intervenes only on violations, which keeps the happy path fast.
- `normalise_tool_output` runs after the tool and replaces what the model sees: Unix timestamps become ISO 8601 and numeric status codes become names. Without it, the model must infer that `2` means delivered or compute "days since" from an epoch integer, and different tools using different formats invites inconsistent reasoning.
- Normalisation sits in a hook, not in the tool, when the tools come from MCP servers you do not own or when several tools disagree on format; one place then fixes all of them.
- The `isinstance` guard on `tool_response` reflects a practical point: the hook must handle the real output shape, so inspect it before assuming a structure.
- Pre and post matter: only a pre-hook can prevent an action; a post-hook runs after the side effect has happened and can only change what the model sees.
- Hooks run in your process, outside the context window. They cost no tokens and cannot be talked out of a decision.

### Trade-offs and alternatives

- **Hook vs prompt rule:** a hook is exact, testable without calling the model and immune to prompt drift, but it needs code and is only as good as the rule you wrote. Prompts are flexible for judgement calls. Use hooks for hard limits (amounts, identity, permissions) and prompts for soft guidance.
- **Hook vs tool-internal validation:** validating inside the tool also guarantees compliance, but it hides policy in each tool and returns an error after dispatch. Hooks centralise cross-cutting policy and can steer the model to an alternative workflow.
- **PostToolUse normalisation vs a better tool contract:** if you own the tool, returning clean data at the source is simpler. A hook is the right choice for third-party or heterogeneous tools.
- **Normalise vs trim:** normalisation changes representation; trimming drops irrelevant fields to save context (see 5.1). They can be combined, but they solve different problems.
- **Blocking vs asking for confirmation:** a hard block suits unambiguous policy; routing to a human suits cases needing judgement.
- **Maintenance:** every hook is code to test; a hook with a wrong rule fails deterministically, which is easier to diagnose than a probabilistic failure but affects every call.

### Exam traps

- "Add the refund threshold to the system prompt": compliance is probabilistic. Rule: when a business rule must always hold, enforce it in code.
- "Run a second model call to check each refund": adds latency, cost and another probabilistic step where a simple comparison is exact. Rule: do not use a model for what a deterministic check can do.
- "Fine-tune or few-shot the model on date formats": treats a data-format problem as a behaviour problem. Rule: fix data quality at the boundary with a `PostToolUse` hook.
- Using `PostToolUse` to stop a refund: the action has already happened. Rule: preventing actions needs a pre-execution interception.
- A block that returns only "denied": the model has no path forward. Rule: pair a block with a redirect to the correct workflow (human escalation).
- Asking the model to convert Unix timestamps itself: unreliable arithmetic repeated on every call. Rule: transformations with exact answers belong in code.

### Check yourself

- Orders over $500 occasionally get auto-refunded even though the prompt forbids it. What is the most reliable fix? A pre-execution hook that denies `process_refund` above the threshold and points the model to the escalation tool.
- Two MCP tools return dates as epoch integers and ISO strings respectively, and the agent miscomputes the return window. Where should the fix go? A post-execution hook that normalises both to one format before the model sees the output.
- A team proposes a `PostToolUse` hook to reject unauthorised refunds. Why does it not work? Post hooks run after the tool has executed, so the refund has already been issued; the check must run before execution.
