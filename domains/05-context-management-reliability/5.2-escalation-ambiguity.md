# 5.2 Design effective escalation and ambiguity resolution patterns

## At a glance

- Appropriate escalation triggers: customer requests for a human, policy exceptions/gaps (not just complex cases), and inability to make meaningful progress.
- The distinction between escalating immediately when a customer explicitly demands it versus offering to resolve when the issue is straightforward.
- Why sentiment-based escalation and self-reported confidence scores are unreliable proxies for actual case complexity.
- How multiple customer matches require clarification (requesting additional identifiers) rather than heuristic selection.

## Example

### Escalation criteria with few-shot examples in the system prompt

```text
ESCALATE (call escalate_to_human) when:
1. The customer explicitly asks for a human. Escalate immediately; do not investigate first.
2. Policy is silent or ambiguous about the request (e.g. a competitor price match when
   policy only covers our own price adjustments).
3. You cannot make meaningful progress after trying the tools available.

RESOLVE YOURSELF when the issue is within policy and your tools, even if the customer is upset.
Acknowledge the frustration, offer the fix, and escalate only if they repeat that they want a human.

<example>
Customer: "Just get me a human."
-> escalate_to_human immediately with a case summary. No lookups.
</example>
<example>
Customer: "This is ridiculous, my replacement arrived cracked again!" (photo attached, in-policy damage)
-> "I'm sorry, that's frustrating. I can send another replacement right now." Resolve via tools.
   Escalate only if they say they still want a person.
</example>
<example>
Customer: "Another store sells this for $20 less. Can you match it?"
-> Policy only covers our own price adjustments. Escalate: policy gap.
</example>
<example>
Customer: "I want a refund for order 5521."  (damaged item, photo evidence, in return window)
-> Standard case. Verify the customer, check the order, process the refund. Do not escalate.
</example>
```

### What not to use as the trigger

| Proxy | Why it fails |
| - | - |
| Self-reported confidence (1-10) | Poorly calibrated; the agent is already confidently wrong on hard cases |
| Sentiment score | Frustration does not correlate with case complexity |
| Separate trained classifier | Over-engineered before prompt criteria are tried |

### Multiple matches: ask, do not guess

```text
If get_customer returns more than one match, do NOT pick one by heuristics (most recent,
closest name). Ask for another identifier: email on the account, last 4 digits of the
phone, or a recent order number. Proceed only with a single verified match.
```

```python
def handle_customer_result(matches: list[dict]) -> str:
    # Zero and many matches both stop here; guessing risks acting on another customer's account.
    if len(matches) == 1:
        return f"verified:{matches[0]['id']}"
    return "NEED_MORE_INFO: multiple accounts match; ask the customer for an additional identifier."
```

Handoff payload for `escalate_to_human`: see [1.4](../01-agentic-architecture-orchestration/1.4-workflow-enforcement-handoff.md).

## Why this matters

> [!IMPORTANT]
> **The principle**

Escalation is decided by explicit, observable criteria: the customer asked for a human, policy is silent or ambiguous, or no meaningful progress is possible. It is not decided by proxies such as sentiment or the model's self-reported confidence, because neither tracks case complexity or the model's actual chance of being right. The criteria are taught with few-shot examples that mark the boundary between "resolve yourself" and "escalate". Ambiguous identity is handled the same way: when evidence does not single out one answer, the agent asks for more information instead of choosing.

**The flow**

- Trigger 1 (explicit request for a human) says "escalate immediately; do not investigate first". The customer has stated a preference; running lookups first delays the handoff and overrides the customer's choice.
- Trigger 2 (policy silent or ambiguous) covers cases like a competitor price match when policy only addresses own-site adjustments. The case may be simple to understand yet is outside the agent's authority; "complex" is the wrong test, "not covered by policy" is the right one.
- Trigger 3 (no meaningful progress) is the backstop for dead ends after tools have been tried, so users are not left looping.
- The "resolve yourself" clause exists because the failure mode in the scenario is over-escalating standard cases (damage replacement with photo evidence) while attempting policy exceptions autonomously. The criteria correct both directions.
- The cracked-replacement example shows the nuance for frustration: acknowledge it, offer the fix, and escalate only if the customer repeats the wish for a human. An upset customer with an in-policy issue is still a resolvable case.
- The competitor price-match example is a pure policy gap, contrasted with the standard damaged-item example. Few-shot pairs teach the decision boundary by contrast, which a bare rule does not.
- The table of rejected proxies records why each fails: self-reported confidence is poorly calibrated (the agent is already confidently wrong on hard cases), sentiment does not correlate with complexity, and a trained classifier is infrastructure to build before prompt-level criteria have been tried.
- `handle_customer_result` returns "need more info" for any result other than exactly one match. Choosing the most recent or closest name is a heuristic that can attach a refund to the wrong person; asking for an email, phone digits or an order number is cheap and removes the ambiguity.

## Trade-offs

- **Explicit criteria vs a trained classifier:** criteria are fast to write and easy to audit, but they need maintenance as policy changes. A classifier can capture patterns humans miss but needs labelled data, adds a component, and is premature before the prompt has been tuned. Sensible order: criteria first, measure, then consider more machinery.
- **Immediate escalation vs offering resolution:** immediate escalation honours an explicit request. Offering a fix is right for in-policy issues where the customer has not asked for a person. The line is whether the customer explicitly demanded a human.
- **Self-reported confidence:** cheap but unreliable as a routing signal on its own. Confidence becomes useful only after calibration against labelled outcomes (see 5.5).
- **Clarifying question vs best guess:** a question costs one turn; a wrong guess costs a wrong action. For actions touching money or identity, ask.
- **Over- vs under-escalation:** over-escalation wastes human capacity and lowers first-contact resolution; under-escalation produces unauthorised decisions. Few-shot examples should include both directions.
- **Sentiment as a secondary signal:** it can inform tone, but it is not a routing rule.

> [!WARNING]
> **Exam traps**

- "Escalate when sentiment score is negative": frustration is not complexity. Rule: sentiment is a poor trigger for escalation.
- "Have the agent rate its confidence 1-10 and escalate below a threshold": the agent is already wrongly confident on hard cases. Rule: self-reported confidence is poorly calibrated.
- "Train a classifier on historical tickets first": over-engineered when prompt criteria have not been tried. Rule: apply the proportionate fix first (the sample question's correct answer is explicit criteria with few-shot examples).
- "Investigate first, then hand over, so the human gets more context": ignores an explicit request. Rule: honour a request for a human immediately.
- "If two customers match, pick the most recent account": a heuristic selection. Rule: multiple matches require an additional identifier.
- "Escalate every complex case": complexity is not the criterion; policy gaps and lack of progress are. Rule: escalate on authority and capability limits, not difficulty alone.

## Quick check

- The customer writes "Just get me a human" about a simple return. What does the agent do? Escalate immediately with a case summary, without running lookups or offering a fix first.
- A customer asks the agent to match a competitor's lower price, and policy covers only own-site adjustments. Resolve or escalate? Escalate as a policy gap; the agent has no authority or guidance for this request.
- `get_customer` returns two accounts for "Jane Doe". What next? Ask for another identifier (account email, last phone digits, recent order number) and continue only with a single verified match.
