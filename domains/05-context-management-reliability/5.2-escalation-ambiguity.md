# 5.2 Design effective escalation and ambiguity resolution patterns

> [!NOTE]
> **At a glance**
>
> - **Triggers:** explicit request for a human, policy gap or ambiguity, or no meaningful progress; not mere complexity.
> - **Immediate vs offer:** escalate at once when the customer demands a person; otherwise offer a fix for in-policy issues.
> - **Bad proxies:** sentiment and self-reported confidence do not track case complexity.
> - **Ambiguity:** multiple customer matches need another identifier, never a heuristic pick.

## Example

### Escalation criteria with few-shot examples in the system prompt

```text
ESCALATE (call escalate_to_human) when:
1. The customer explicitly asks for a human. Escalate immediately; do not investigate first.
2. Policy is silent or ambiguous about the request (e.g. a competitor price match when
   policy only covers our own price adjustments).
3. You cannot make meaningful progress after trying the tools available.

RESOLVE YOURSELF when the issue is within policy and your tools, even if the customer is upset.
Acknowledge the frustration, offer the fix, and escalate only if they repeat that they want a human.

<example>
Customer: "Just get me a human."
-> escalate_to_human immediately with a case summary. No lookups.
</example>
<example>
Customer: "This is ridiculous, my replacement arrived cracked again!" (photo attached, in-policy damage)
-> "I'm sorry, that's frustrating. I can send another replacement right now." Resolve via tools.
   Escalate only if they say they still want a person.
</example>
<example>
Customer: "Another store sells this for $20 less. Can you match it?"
-> Policy only covers our own price adjustments. Escalate: policy gap.
</example>
<example>
Customer: "I want a refund for order 5521."  (damaged item, photo evidence, in return window)
-> Standard case. Verify the customer, check the order, process the refund. Do not escalate.
</example>
```

### What not to use as the trigger

| Proxy | Why it fails |
| - | - |
| Self-reported confidence (1-10) | Poorly calibrated; the agent is already confidently wrong on hard cases |
| Sentiment score | Frustration does not correlate with case complexity |
| Separate trained classifier | Over-engineered before prompt criteria are tried |

### Multiple matches: ask, do not guess

```text
If get_customer returns more than one match, do NOT pick one by heuristics (most recent,
closest name). Ask for another identifier: email on the account, last 4 digits of the
phone, or a recent order number. Proceed only with a single verified match.
```

```python
def handle_customer_result(matches: list[dict]) -> str:
    # Zero and many matches both stop here; guessing risks acting on another customer's account.
    if len(matches) == 1:
        return f"verified:{matches[0]['id']}"
    return "NEED_MORE_INFO: multiple accounts match; ask the customer for an additional identifier."
```

Handoff payload for `escalate_to_human`: see [1.4](../01-agentic-architecture-orchestration/1.4-workflow-enforcement-handoff.md).

## How it works

> [!IMPORTANT]
> **Escalate on observable criteria, not proxies.** Sentiment and self-reported confidence do not track complexity or the chance of being right. Few-shot examples mark the line between "resolve yourself" and "escalate"; ambiguous identity gets a question, not a guess.

1. **Explicit request.** Escalate immediately with no lookups first; investigating overrides the customer's stated choice.
2. **Policy gap.** A competitor price match is simple to understand but outside the agent's authority. "Not covered by policy" is the test, not "complex".
3. **No progress.** The backstop for dead ends after tools have been tried, so users are not left looping.
4. **Resolve in-policy cases.** Over-escalating standard cases (photo-evidenced damage) is the failure mode; acknowledge frustration, offer the fix, escalate only if the customer repeats the wish for a person.
5. **Teach by contrast.** Paired examples (price match vs damaged item) convey the boundary better than a bare rule.
6. **Ask on multiple matches.** `handle_customer_result` returns "need more info" unless exactly one match exists; guessing can attach a refund to the wrong person.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Explicit criteria | Fast to write and audit | Needs maintenance as policy changes |
| Trained classifier | Can capture patterns humans miss | Needs labelled data and a new component; premature before prompt tuning |
| Immediate escalation | Honours an explicit request | Wrong when the customer has not asked for a person |
| Offer resolution | Right for in-policy issues | Wrong if the customer demanded a human |
| Self-reported confidence | Cheap | Unreliable unless calibrated against labelled outcomes ([5.5](5.5-human-review-confidence.md)) |
| Clarifying question | One turn | Wrong guesses cost a wrong action; ask when money or identity is involved |

Sentiment may inform tone but is not a routing rule. Over-escalation wastes human capacity and lowers first-contact resolution; under-escalation yields unauthorised decisions, so include both directions in few-shot examples. Order: criteria first, measure, then add machinery.

> [!WARNING]
> **Exam traps**
>
> - **"Escalate when sentiment score is negative"** → frustration is not complexity. Sentiment is a poor trigger.
> - **"Rate confidence 1-10 and escalate below a threshold"** → the agent is already confidently wrong on hard cases. Self-reported confidence is poorly calibrated.
> - **"Train a classifier on historical tickets first"** → over-engineered. Apply the proportionate fix first: explicit criteria with few-shot examples.
> - **"Investigate first so the human gets more context"** → ignores an explicit request. Honour it immediately.
> - **"If two customers match, pick the most recent"** → heuristic selection. Request an additional identifier.
> - **"Escalate every complex case"** → complexity is not the criterion. Escalate on authority and capability limits.

## Check yourself

<details>
<summary>The customer writes "Just get me a human" about a simple return. What does the agent do?</summary>

Escalate immediately with a case summary, without running lookups or offering a fix first.
</details>

<details>
<summary>A customer asks the agent to match a competitor's lower price; policy covers only own-site adjustments. Resolve or escalate?</summary>

Escalate as a policy gap; the agent has no authority or guidance for this request.
</details>

<details>
