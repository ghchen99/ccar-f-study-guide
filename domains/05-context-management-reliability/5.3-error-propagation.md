# 5.3 Implement error propagation strategies across multi-agent systems

## Knowledge of

- Structured error context (failure type, attempted query, partial results, alternative approaches) as enabling intelligent coordinator recovery decisions.
- The distinction between access failures (timeouts needing retry decisions) and valid empty results (successful queries with no matches).
- Why generic error statuses ("search unavailable") hide valuable context from the coordinator.
- Why silently suppressing errors (returning empty results as success) or terminating entire workflows on single failures are both anti-patterns.

## Skills in

- Returning structured error context including failure type, what was attempted, partial results, and potential alternatives to enable coordinator recovery.
- Distinguishing access failures from valid empty results in error reporting so the coordinator can make appropriate decisions.
- Having subagents implement local recovery for transient failures and only propagate errors they cannot resolve, including what was attempted and partial results.
- Structuring synthesis output with coverage annotations indicating which findings are well-supported versus which topic areas have gaps due to unavailable sources.

## Code snippets

### Structured error context from a subagent

```python
from typing import Literal, TypedDict


class SubagentError(TypedDict):
    status: Literal["error"]   # distinct from "ok" so an access failure is never read as "no results"
    failure_type: Literal["timeout", "rate_limit", "auth", "source_unavailable"]  # drives the coordinator's choice: retry, reroute or accept the gap
    attempted_query: str
    attempts: int                  # retries already done locally
    partial_results: list[dict]    # whatever was gathered before failing
    alternatives: list[str]        # what the coordinator could try next
```

```python
def web_search_agent(query: str) -> dict:
    # Local retry absorbs transient faults; only what the subagent cannot fix reaches the coordinator.
    results: list[dict] = []
    for attempt in range(1, 4):
        try:
            results = search(query)                    # transient failures retried locally
            return {"status": "ok", "results": results}
        except TimeoutError:
            continue
    return {
        "status": "error", "failure_type": "timeout", "attempted_query": query,
        "attempts": 3, "partial_results": results,
        "alternatives": ["retry with a narrower query", "use the document-analysis agent"],
    }
```

### Access failure vs valid empty result

```python
{"status": "ok", "results": []}          # searched fine, nothing matches: coverage statement, not an error
{"status": "error", "failure_type": "timeout", ...}   # could not search: coordinator must decide
```

### Anti-patterns

```python
return {"status": "ok", "results": []}       # swallowed timeout: looks like "no results", hides the gap
return {"status": "error", "message": "search unavailable"}   # generic: nothing to recover with
raise                                         # kills the whole research run for one subagent failure
```

### Coordinator recovery and coverage annotations

```python
def synthesize(topic_results: dict[str, dict]) -> str:
    # One failed topic degrades the report with a stated gap; it does not abort the run.
    well_supported = [t for t, r in topic_results.items() if r["status"] == "ok" and r["results"]]
    gaps = {t: r for t, r in topic_results.items() if r["status"] == "error"}
    report = ["## Findings", *render_findings(well_supported)]
    if gaps:
        report.append("## Coverage gaps")
        for topic, err in gaps.items():
            # Readers see what is missing and why, so absence is not mistaken for "nothing exists".
            report.append(f"- {topic}: not covered ({err['failure_type']} on '{err['attempted_query']}'). "
                          f"Partial: {len(err['partial_results'])} items.")
    return "\n".join(report)
```

The report states which areas are well supported and which have gaps from unavailable sources.

## Commentary: the concepts behind the code

SDK names are illustrative; know the concept, not the exact parameter.

### The design decision

A failure is information, and it belongs to whoever can decide what to do about it. A subagent absorbs transient faults locally and reports only what it cannot resolve, with enough structure (failure type, what was attempted, partial results, alternatives) for the coordinator to choose between retrying, rerouting and proceeding with a declared gap. Failures are neither hidden (an empty result marked successful) nor escalated to the maximum (aborting the workflow). The final output states what is well supported and what is not.

### Walk-through

- `SubagentError` carries four things the coordinator needs to act. `failure_type` distinguishes a timeout (retry may help) from an auth failure (retry will not). `attempted_query` shows what was tried so the coordinator can change it. `partial_results` preserves work already done. `alternatives` suggests a next route.
- The local loop in `web_search_agent` retries transient failures up to three times. This keeps the coordinator's context free of noise and puts recovery at the lowest level that can handle it. `attempts` records that this was done so the coordinator does not simply repeat it.
- `{"status": "ok", "results": []}` and `{"status": "error", ...}` are deliberately different shapes. An empty success is a coverage statement ("searched, nothing matches"); an error is "could not search". Merging them makes a broken source look like a topic with no literature, and the coordinator draws the wrong conclusion.
- The anti-pattern block names three failures: a swallowed timeout (silent gap in the report), a generic "search unavailable" (no basis for recovery) and an unhandled raise (one failure kills the whole run).
- `synthesize` partitions topics into well supported and gaps, and renders gaps with the failure type and query. The reader learns that music was not covered because of a timeout, not that music has no findings.
- Partial results are counted in the gap line, so usable material is not discarded just because the full query failed.

### Trade-offs and alternatives

- **Local retry vs immediate propagation:** local retry cuts coordinator traffic for transient faults but delays reporting and can hide a flaky source; the `attempts` field keeps it visible. Propagate at once for non-retryable errors (auth, validation).
- **Structured error vs generic status:** structure costs a schema and discipline in every subagent, and buys intelligent recovery. A generic status is easy and leaves the coordinator guessing.
- **Proceeding with partial results vs failing the task:** a report with a stated gap is usually more useful than none, but when a missing source invalidates the conclusion (for example, the only authoritative source), the coordinator should stop or escalate. This judgement belongs to the coordinator, which is why it needs the details.
- **Coordinator retry policy:** unbounded retry risks cost and loops; cap attempts and track alternatives already tried.
- **Coverage annotations vs a clean report:** annotations make the report less tidy and more honest. For decisions that depend on completeness, honesty wins.

### Exam traps

- "Catch the timeout in the subagent and return an empty result marked successful": suppresses the error and prevents recovery. Rule: do not mark a failure as an empty success.
- "Propagate the exception to a top-level handler that terminates the workflow": one subagent failure should not end the whole run. Rule: contain and report, let the coordinator decide.
- "Retry with backoff and return a generic 'search unavailable' only when exhausted": hides failure type, query and partial results. Rule: generic statuses throw away the context recovery needs (the sample question's correct answer is structured error context).
- "Treat empty results as errors so the coordinator retries": a valid empty result is information, not a fault. Rule: separate access failures from empty results.
- "Hide gaps in the report to keep it clean": readers will assume coverage that does not exist. Rule: annotate gaps and their cause.

### Check yourself

- A subagent's source times out three times. What should the coordinator receive? A structured error with failure type, attempted query, attempts made, any partial results and suggested alternatives, so it can retry differently, reroute or note the gap.
- A search succeeds and returns zero matches. Is this an error? No; it is a valid empty result and a coverage statement, reported as a success so it is not confused with an access failure.
- Two of five topics could not be searched. Should the report be withheld? Usually no; produce the report with the three supported topics and an explicit coverage-gaps section, unless the missing topics make the conclusion unreliable.
