# 5.1 Manage conversation context to preserve critical information across long interactions

> [!NOTE]
> **At a glance**
>
> - **Summarisation loss:** progressive summaries blur amounts, dates and stated expectations; keep them in a persistent facts block.
> - **Lost in the middle:** models read the start and end of long inputs best; put key findings there.
> - **Tool bloat:** trim results (40+ fields, 5 relevant) before they enter history.
> - **Full history:** the API is stateless, so send the whole conversation on every request.

## Example

### Persistent "case facts" block outside summarised history

Amounts, dates, order numbers and statuses live in a structured block rebuilt into every request, so summarisation cannot blur "$84.50 refund, requested 2026-03-02" into "a refund".

```python
from dataclasses import dataclass, field


@dataclass
class CaseFacts:
    customer_id: str | None = None
    issues: list[dict] = field(default_factory=list)   # one entry per concern in a multi-issue session

    # Typed fields are rendered verbatim each turn; a summary can only paraphrase, these cannot be blurred.
    def render(self) -> str:
        lines = [f"customer_id: {self.customer_id}"]
        for i in self.issues:
            lines.append(f"- {i['type']} | order {i['order_id']} | ${i['amount']:.2f} | "
                         f"status {i['status']} | opened {i['opened']}")
        return "<case_facts>\n" + "\n".join(lines) + "\n</case_facts>"


def build_request(facts: CaseFacts, summarised_history: list[dict], new_user_msg: str) -> dict:
    # Only the history is lossy; the facts are rebuilt from state, so compaction cannot erase them.
    return {
        "system": SYSTEM_PROMPT + "\n\n" + facts.render(),    # facts first, never summarised
        "messages": summarised_history + [{"role": "user", "content": new_user_msg}],
    }
```

### Trim verbose tool output to the fields that matter

A 40-field order lookup becomes the five fields relevant to returns before it is appended to history.

```python
RETURN_FIELDS = ("order_id", "status", "items", "total", "delivered_at")


def trim_order(raw: dict) -> dict:
    # Allow-list, not block-list: new backend fields never leak into context by default.
    return {k: raw[k] for k in RETURN_FIELDS if k in raw}


# in the agent loop, before returning the tool_result (trim before append: every later turn re-sends it)
content = json.dumps(trim_order(execute_tool(name, args)))
```

With the Agent SDK the same trimming can be done in a `PostToolUse` hook via `updatedToolOutput` (see [1.5](../01-agentic-architecture-orchestration/1.5-hooks-interception-normalization.md)).

### Mitigate "lost in the middle" when aggregating

Put the key findings summary first, then detail under explicit headers.

```python
def aggregate(findings: list[dict], summary: str) -> str:
    # Summary first and headed sections: start and end of a long input are read most reliably, the middle is not.
    sections = "\n\n".join(f"## {f['topic']}\n{f['detail']}\nSource: {f['source']} ({f['date']})" for f in findings)
    return f"## Key findings (read first)\n{summary}\n\n{sections}"
```

### Upstream agents return structured data, not transcripts

```json
{
  "claim": "Streaming revenue grew 14% in 2025",
  "evidence_excerpt": "revenue from streaming rose 14%",
  "source_url": "https://example.com/report",
  "published": "2026-01-10",
  "relevance": 0.9
}
```

A downstream agent with a limited context budget needs key facts, citations and relevance scores, not verbose content or reasoning chains.

### Keep the full history in each request

The Messages API is stateless: send the full conversation (tool calls and results included) on every call.

## How it works

> [!IMPORTANT]
> **Exact facts live in structure; narrative lives in history.** Neither is trusted to do the other's job: amounts and dates survive in a rebuilt block, while bulky output is trimmed and long inputs are laid out to beat position effects.

1. **Render facts verbatim.** `CaseFacts.render()` keeps `$84.50` and `opened 2026-03-02`, which a summary would reduce to "a refund was requested". It is rebuilt from state, so it is never summarised.
2. **Split lossy from exact.** `build_request` puts the block in the system prompt and passes only the history through summarisation. One `issues` entry per concern keeps amounts on the right order.
3. **Trim before appending.** `trim_order` is an allow-list; a verbose result in history is re-sent and paid for on every later request.
4. **Lead with the summary.** `aggregate` puts key findings first, with headed sections carrying source and date, so nothing critical sits mid-document.
5. **Return structure upstream.** Claim, excerpt, URL, date and relevance give a small-budget downstream agent facts and citations instead of reasoning chains.
6. **Send every turn.** Full history is a correctness requirement of a stateless API; shrink content by trimming and summarising, never by arbitrarily omitting turns.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Facts block | Small constant token cost; exact values survive | Needs extraction logic and a schema to maintain |
| Summarise everything | Cheap to build | Fails silently on the numbers that matter |
| Larger context window | More room | Does not remove position effects, re-send cost or compaction rewording |
| Trim at tool, hook or loop | Tool is simplest if owned; hook suits third-party tools; loop is the fallback | Over-trimming forces a second lookup; choose fields by task |
| Structured upstream output | Saves downstream context | Loses nuance; keep an excerpt and a source pointer |

> [!WARNING]
> **Exam traps**
>
> - **"Summarise the whole conversation periodically"** → lossy for exactly the values that matter. Keep exact facts in a persistent block outside summarised history.
> - **"Drop older messages from the request"** → breaks coherence and loses commitments. Keep the conversation; trim tool output and structure facts.
> - **"Put key findings in the middle under a clear heading"** → position effects still apply. Put the summary at the start (or end) with explicit headers.
> - **"Return the full order record so the model has everything"** → costs tokens every turn. Filter to task-relevant fields before they enter context.
> - **"Have subagents return their full reasoning"** → overloads a limited downstream budget. Return key facts, citations and relevance scores.
> - **"Use a bigger model or window instead"** → does not address summarisation loss or position effects.
