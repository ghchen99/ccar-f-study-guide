# 5.1 Manage conversation context to preserve critical information across long interactions

## Knowledge of

- Progressive summarization risks: condensing numerical values, percentages, dates, and customer-stated expectations into vague summaries.
- The "lost in the middle" effect: models reliably process information at the beginning and end of long inputs but may omit findings from middle sections.
- How tool results accumulate in context and consume tokens disproportionately to their relevance (e.g., 40+ fields per order lookup when only 5 are relevant).
- The importance of passing complete conversation history in subsequent API requests to maintain conversational coherence.

## Skills in

- Extracting transactional facts (amounts, dates, order numbers, statuses) into a persistent "case facts" block included in each prompt, outside summarized history.
- Extracting and persisting structured issue data (order IDs, amounts, statuses) into a separate context layer for multi-issue sessions.
- Trimming verbose tool outputs to only relevant fields before they accumulate in context (e.g., keeping only return-relevant fields from order lookups).
- Placing key findings summaries at the beginning of aggregated inputs and organizing detailed results with explicit section headers to mitigate position effects.
- Requiring subagents to include metadata (dates, source locations, methodological context) in structured outputs to support accurate downstream synthesis.
- Modifying upstream agents to return structured data (key facts, citations, relevance scores) instead of verbose content and reasoning chains when downstream agents have limited context budgets.

## Code snippets

### Persistent "case facts" block outside summarised history

Amounts, dates, order numbers and statuses live in a structured block rebuilt into every request, so summarisation cannot blur "$84.50 refund, requested 2026-03-02" into "a refund".

```python
from dataclasses import dataclass, field


@dataclass
class CaseFacts:
    customer_id: str | None = None
    issues: list[dict] = field(default_factory=list)   # one entry per concern in a multi-issue session

    # Typed fields are rendered verbatim each turn; a summary can only paraphrase, these cannot be blurred.
    def render(self) -> str:
        lines = [f"customer_id: {self.customer_id}"]
        for i in self.issues:
            lines.append(f"- {i['type']} | order {i['order_id']} | ${i['amount']:.2f} | "
                         f"status {i['status']} | opened {i['opened']}")
        return "<case_facts>\n" + "\n".join(lines) + "\n</case_facts>"


def build_request(facts: CaseFacts, summarised_history: list[dict], new_user_msg: str) -> dict:
    # Only the history is lossy; the facts are rebuilt from state, so compaction cannot erase them.
    return {
        "system": SYSTEM_PROMPT + "\n\n" + facts.render(),    # facts first, never summarised
        "messages": summarised_history + [{"role": "user", "content": new_user_msg}],
    }
```

### Mitigate "lost in the middle" when aggregating

Put the key findings summary first, then detail under explicit headers.

```python
def # Summary first and headed sections: start and end of a long input are read most reliably, the middle is not.
    aggregate(findings: list[dict], summary: str) -> str:
    sections = "\n\n".join(f"## {f['topic']}\n{f['detail']}\nSource: {f['source']} ({f['date']})" for f in findings)
    return f"## Key findings (read first)\n{summary}\n\n{sections}"
```

### Upstream agents return structured data, not transcripts

```json
{
  "claim": "Streaming revenue grew 14% in 2025",
  "evidence_excerpt": "revenue from streaming rose 14%",
  "source_url": "https://example.com/report",
  "published": "2026-01-10",
  "relevance": 0.9
}
```

When a downstream agent has a limited context budget, return key facts, citations and relevance scores rather than verbose content and reasoning chains.

### Keep the full history in each request

The Messages API is stateless: send the full conversation (including tool calls and results) on every call to keep it coherent.

## Commentary: the concepts behind the code

SDK names are illustrative; know the concept, not the exact parameter.

### The design decision

Context is a finite, lossy resource. Anything that must survive exactly (amounts, dates, order numbers, statuses, customer-stated expectations) is kept in a persistent structured block that is rebuilt into every request and sits outside any summarised history. Everything else is treated as disposable: verbose tool output is trimmed before it accumulates, and aggregated inputs are laid out so that position effects do not bury findings. The principle: exact facts live in structure, narrative lives in history, and neither is trusted to do the other's job.

### Walk-through

- `CaseFacts.render()` produces typed, verbatim lines such as `$84.50` and `opened 2026-03-02`. Progressive summarisation compresses "refund of $84.50 requested on 2 March" into "a refund was requested"; once the number is gone it cannot be recovered from the summary. The facts block is regenerated from state, so it is never summarised.
- `build_request` puts the block in the system prompt and passes only the history through summarisation. The split matters: the lossy part and the exact part are different objects.
- `issues` is a list, one entry per concern. In a multi-issue session (refund plus billing dispute) a single blob of facts would blend the two cases; per-issue entries keep amounts attached to the right order.
- `trim_order` is an allow-list of return-relevant fields. A 40-field lookup costs tokens on every later turn because the full history is re-sent each call, and irrelevant fields dilute attention. An allow-list is safer than a block-list because new backend fields stay out by default.
- Trimming happens before the result is appended, not afterwards. Once a verbose result is in history it is paid for on every subsequent request.
- `aggregate` places a key-findings summary first and gives each section a header, with source and date kept on each section. Models handle the start and end of a long input more reliably than the middle ("lost in the middle"), so critical findings should never rely on sitting mid-document.
- The structured upstream JSON (claim, excerpt, URL, date, relevance) lets a downstream agent with a small context budget receive facts and citations instead of reasoning chains.
- Sending the full history each call is a correctness requirement of a stateless API, not an optimisation target: dropping turns breaks coherence, so reduce size by trimming and summarising content, not by omitting turns arbitrarily.

### Trade-offs and alternatives

- **Facts block vs summarising everything:** a facts block costs a small, constant number of tokens and needs extraction logic (what counts as a fact). Summarising everything is cheaper to build and fails silently on the numbers that matter.
- **Facts block vs relying on a larger context window:** more room does not remove position effects or the cost of re-sending bulk, and it does not stop later compaction from rewording content. It delays the problem.
- **Trim at the tool, in a hook, or in the agent loop:** trimming at the tool is simplest when the tool is owned; a hook suits third-party tools; the loop is the fallback. All achieve the same end: the model never sees the bulk.
- **Over-trimming:** an allow-list that omits a field needed later forces a second lookup. Choose fields by the task (returns need status, items, total, delivery date).
- **Structured upstream output vs full content:** structured findings save downstream context but lose nuance; keep an excerpt and a pointer to the source so detail can be fetched when needed.
- **Maintenance:** the facts schema is a contract. Adding a new fact type means updating extraction and rendering.

### Exam traps

- "Summarise the whole conversation periodically to stay within limits": summarisation is lossy for exactly the values that matter. Rule: exact transactional facts go in a persistent block outside summarised history.
- "Drop older messages from the request": breaks coherence and loses commitments. Rule: keep the conversation, trim tool output and keep facts structured.
- "Put key findings in the middle under a clear heading": position effects still apply. Rule: put the summary at the start (or end) and use explicit section headers.
- "Return the full order record so the model has everything": costs tokens every turn with little relevance. Rule: filter tool output to the task-relevant fields before it enters context.
- "Have subagents return their full reasoning for completeness": overloads a downstream agent with a limited budget. Rule: return structured key facts, citations and relevance scores.
- "Use a bigger model or window instead of restructuring": does not address summarisation loss or position effects.

### Check yourself

- A customer disputes a refund amount late in a long chat and the agent quotes a rounded figure from its summary. What design change prevents this? Keep amounts, dates and order numbers in a structured case-facts block included in every request, outside the summarised history.
- An order lookup returns 40 fields and the agent slows and starts to miss details after a few lookups. What is the fix? Trim the result to the handful of relevant fields before it is appended to context.
- A synthesis agent consistently omits findings that appeared in the middle of a long aggregated input. What mitigates it? Put a key-findings summary at the start and organise the detail under explicit headers.
