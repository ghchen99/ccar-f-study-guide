# 2.2 Implement structured error responses for MCP tools

## At a glance

- The MCP `isError` flag pattern for communicating tool failures back to the agent.
- The distinction between transient errors (timeouts, service unavailability), validation errors (invalid input), business errors (policy violations), and permission errors.
- Why uniform error responses (generic "Operation failed") prevent the agent from making appropriate recovery decisions.
- The difference between retryable and non-retryable errors, and how returning structured metadata prevents wasted retry attempts.

## Example

### Structured error result from an in-process tool

Return `is_error: True` and put the structure in the text. An uncaught exception also becomes an error result, but Claude only sees the raw message, so catch and compose it yourself.

```python
import json
from typing import Any
from claude_agent_sdk import tool


def tool_error(category: str, message: str, retryable: bool, **extra) -> dict[str, Any]:
    # Category + retryability let the model choose retry, rephrase, escalate or explain instead of guessing from prose
    payload = {"errorCategory": category, "isRetryable": retryable, "message": message, **extra}
    return {"content": [{"type": "text", "text": json.dumps(payload)}], "is_error": True}


@tool("process_refund", "Refund an order. Requires a verified customer_id.", {"order_id": str, "amount": float})
async def process_refund(args: dict[str, Any]) -> dict[str, Any]:
    try:
        result = await refund_api(args["order_id"], args["amount"])  # your backend call
    except TimeoutError:
        return tool_error("transient", "Refund service timed out.", True)  # only this case is worth retrying
    except PermissionError:
        return tool_error("permission", "This agent may not issue refunds.", False)  # retrying cannot change authorisation
    except ValueError as e:  # malformed input
        return tool_error("validation", f"Invalid input: {e}", False)  # the model should correct the input, not repeat it

    if result.status == "outside_return_window":
        return tool_error(
            "business", "Order is outside the 30-day return window.", False,
            # Customer-safe wording keeps the agent from improvising or leaking internal policy detail
            customerExplanation="This order is past our 30-day return window, so I can't refund it directly.",
        )
    return {"content": [{"type": "text", "text": json.dumps({"refund_id": result.id})}]}
```

### Valid empty result is not an error

```python
@tool("lookup_order", "Fetch an order by order number.", {"order_number": str})
async def lookup_order(args):
    order = await find_order(args["order_number"])
    if order is None:
        # Successful query, no match: no is_error, so Claude does not retry
        # Distinguishing "nothing found" from "could not look" keeps the agent from retrying or fabricating
        return {"content": [{"type": "text", "text": json.dumps({"found": False, "matches": []})}]}
    return {"content": [{"type": "text", "text": json.dumps(order)}]}
```

### Local recovery in a subagent, propagate what remains

```python
async def search_with_recovery(query: str, retries: int = 2) -> dict:
    last_error = None  # bounded: unbounded retries hide an outage and burn latency
    for _ in range(retries + 1):
        try:
            return {"status": "ok", "results": await web_search(query)}
        except TimeoutError as e:  # transient: retry locally
            last_error = e
    return {  # unrecoverable here: give the coordinator context, not "search unavailable"
        "status": "error",
        "failureType": "timeout",
        "attemptedQuery": query,
        "partialResults": [],
        "alternatives": ["narrower query", "different source type"],
    }
```

## Why this matters

> [!IMPORTANT]
> **The principle**

An error is information the agent needs in order to decide what to do next. Failures differ in what the correct next move is: retry, correct the input, stop and explain, or escalate. A tool that returns a uniform "Operation failed" collapses those cases and forces the model to guess. The principle: classify failures at the layer that understands them, return the classification in a machine-readable form, and resolve locally whatever can be resolved locally so that only unrecoverable problems travel upward, together with their context.

**The flow**

- `tool_error` wraps every failure in the same shape: category, retryability, message and optional extras. The model learns one contract and can branch on it. The flag marking the call as failed is what tells the model the call did not succeed; the structured text is what tells it how to respond.
- Each `except` branch maps a distinct cause to a category. `transient` plus retryable means trying again is sensible. `permission`, `validation` and `business` are non-retryable: a retry repeats the same failure, wastes turns and, for permission errors, can look like probing.
- `isRetryable` prevents wasted attempts. Without it, the model either retries everything (burning latency) or retries nothing (abandoning recoverable work).
- The business error carries `customerExplanation`. The agent needs wording it can pass on, otherwise it may paraphrase an internal policy badly or expose detail that should stay private.
- Validation errors say what was wrong, so the model can fix the argument and call again rather than repeat it.
- `lookup_order` returns `found: False` as a normal result. "No such order" is a successful query with an empty answer. Marking it as an error would trigger retries and recovery logic for a situation that has no recovery; the agent should instead tell the user or ask for a different identifier.
- The inverse failure is worse: reporting an outage as an empty result. The agent then confidently tells the user nothing exists. Access failure and valid empty result must remain distinguishable.
- `search_with_recovery` retries transient failures in place, a bounded number of times, because the subagent has the context to do so cheaply. Only after that does it propagate, and it includes the failure type, the attempted query, partial results and alternatives, so the coordinator can retry differently, route elsewhere or proceed with a stated gap.

## Trade-offs

- **Structured error vs raw exception text:** an uncaught exception still reaches the model as an error, but as an unstructured message. Structured metadata costs a few lines per tool and removes guesswork.
- **Local retry vs propagate immediately:** local retry reduces coordinator round trips and context churn for brief outages, at the price of added latency when the failure is not transient. Bound the retries.
- **Propagate with context vs suppress:** suppressing (returning empty success) looks tidy but destroys the signal the coordinator needs; returning a generic status after retries hides what was tried.
- **Failing the whole workflow:** terminates work that could have continued with partial results; reserve it for failures where no useful output is possible.
- **Category granularity:** more categories give finer decisions but more to maintain; four or five that map to distinct recovery actions are usually enough.
- **Where `isRetryable` is decided:** the tool knows the cause best, so it should set the flag rather than leave the model to infer it from message text.

> [!WARNING]
> **Exam traps**

- "Return a generic 'Operation failed' or 'search unavailable'": hides the failure type and attempted action. Rule: error responses must carry enough context for recovery decisions.
- "Catch the timeout and return an empty successful result": suppresses the error, so recovery cannot happen and the report silently has a gap. Rule: never convert a failure into a success.
- "Propagate every exception to a top-level handler that stops the workflow": discards partial results and recoverable work. Rule: recover locally first, then propagate the remainder with context.
- "Retry everything with exponential backoff": wasteful for validation, permission and business errors. Rule: retry only errors marked retryable.
- "Treat an empty search result as an error": misclassifies a valid outcome and causes pointless retries. Rule: distinguish access failures from valid empty results.
- Sample question 8 (scenario 3) is the canonical case: the correct answer returns failure type, attempted query, partial results and alternatives.

## Quick check

- A refund tool rejects an order outside the return window. Should the agent retry? No; the business error is non-retryable, and the agent should relay the customer-facing explanation or escalate.
- A subagent's search times out twice, then succeeds on the third try. What does the coordinator see? Only the successful result; transient failures are resolved locally and are not propagated.
- A query for order 99999 matches nothing. How should the tool respond? As a successful result with `found: false`, not an error, so the agent reports the absence instead of retrying.

Source: [Give Claude custom tools, Handle errors](https://code.claude.com/docs/en/agent-sdk/custom-tools.md). The MCP `isError` flag marks a failed call; the category, retryability and explanation fields above are a convention you define in the payload.
