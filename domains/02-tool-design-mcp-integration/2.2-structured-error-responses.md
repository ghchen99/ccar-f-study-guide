# 2.2 Implement structured error responses for MCP tools

> [!NOTE]
> **At a glance**
>
> - **Flag:** the MCP `isError` flag tells the agent a call failed; the payload says how to respond.
> - **Categories:** transient (timeouts, outages), validation, business (policy) and permission errors need different recovery.
> - **Metadata:** generic "Operation failed" blocks recovery decisions; retryable vs non-retryable metadata prevents wasted retries.

## Example

### Structured error result from an in-process tool

Return `is_error: True` and put the structure in the text. An uncaught exception also becomes an error result, but Claude sees only the raw message, so catch and compose it yourself.

```python
import json
from typing import Any
from claude_agent_sdk import tool


def tool_error(category: str, message: str, retryable: bool, **extra) -> dict[str, Any]:
    # Category + retryability let the model choose retry, rephrase, escalate or explain instead of guessing from prose
    payload = {"errorCategory": category, "isRetryable": retryable, "message": message, **extra}
    return {"content": [{"type": "text", "text": json.dumps(payload)}], "is_error": True}


@tool("process_refund", "Refund an order. Requires a verified customer_id.", {"order_id": str, "amount": float})
async def process_refund(args: dict[str, Any]) -> dict[str, Any]:
    try:
        result = await refund_api(args["order_id"], args["amount"])  # your backend call
    except TimeoutError:
        return tool_error("transient", "Refund service timed out.", True)  # only this case is worth retrying
    except PermissionError:
        return tool_error("permission", "This agent may not issue refunds.", False)  # retrying cannot change authorisation
    except ValueError as e:  # malformed input
        return tool_error("validation", f"Invalid input: {e}", False)  # the model should correct the input, not repeat it

    if result.status == "outside_return_window":
        return tool_error(
            "business", "Order is outside the 30-day return window.", False,
            # Customer-safe wording keeps the agent from improvising or leaking internal policy detail
            customerExplanation="This order is past our 30-day return window, so I can't refund it directly.",
        )
    return {"content": [{"type": "text", "text": json.dumps({"refund_id": result.id})}]}
```

### Valid empty result is not an error

```python
@tool("lookup_order", "Fetch an order by order number.", {"order_number": str})
async def lookup_order(args):
    order = await find_order(args["order_number"])
    if order is None:
        # Successful query, no match: no is_error, so Claude does not retry
        # Distinguishing "nothing found" from "could not look" keeps the agent from retrying or fabricating
        return {"content": [{"type": "text", "text": json.dumps({"found": False, "matches": []})}]}
    return {"content": [{"type": "text", "text": json.dumps(order)}]}
```

### Local recovery in a subagent, propagate what remains

```python
async def search_with_recovery(query: str, retries: int = 2) -> dict:
    last_error = None  # bounded: unbounded retries hide an outage and burn latency
    for _ in range(retries + 1):
        try:
            return {"status": "ok", "results": await web_search(query)}
        except TimeoutError as e:  # transient: retry locally
            last_error = e
    return {  # unrecoverable here: give the coordinator context, not "search unavailable"
        "status": "error",
        "failureType": "timeout",
        "attemptedQuery": query,
        "partialResults": [],
        "alternatives": ["narrower query", "different source type"],
    }
```

## How it works

> [!IMPORTANT]
> **An error is information the agent needs to decide what to do next.** Classify failures where they are understood, return the classification in machine-readable form, and resolve locally what can be resolved so only unrecoverable problems travel upward, with context.

1. **One error shape.** `tool_error` returns category, retryability, message and extras. The failure flag says the call failed; the structured text says how to respond.
2. **Map each cause to a category.** `transient` is retryable. `permission`, `validation` and `business` are not: a retry repeats the failure, wastes turns and, for permission errors, can look like probing.
3. **Set `isRetryable` in the tool.** Without it the model retries everything or nothing. Validation errors say what was wrong so the model can fix the argument.
4. **Give business errors customer-safe wording** (`customerExplanation`), so the agent doesn't paraphrase policy badly or leak internal detail.
5. **Keep empty results successful.** `found: False` is a valid answer with no recovery to trigger. The inverse is worse: reporting an outage as empty makes the agent say nothing exists. Keep the two distinguishable.
6. **Recover locally, then propagate.** `search_with_recovery` retries transient failures a bounded number of times, then returns failure type, attempted query, partial results and alternatives so the coordinator can retry differently, route elsewhere or proceed with a stated gap.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Structured error | Removes guesswork | A few lines per tool; raw exception text still reaches the model, but unstructured |
| Local retry | Fewer coordinator round trips and less context churn | Added latency if the failure is not transient; bound the retries |
| Propagate with context | Coordinator can recover or flag a gap | Needs a richer payload |
| Suppress (empty success) | Looks tidy | Destroys the signal; a generic status after retries hides what was tried |
| Fail the whole workflow | Simple | Discards partial results; reserve for cases with no useful output |
| Category granularity | Finer decisions | More to maintain; four or five mapping to distinct recovery actions is usually enough |

> [!WARNING]
> **Exam traps**
>
> - **"Return a generic 'Operation failed' or 'search unavailable'"** → hides failure type and attempted action. Errors must carry enough context for recovery decisions.
> - **"Catch the timeout and return an empty successful result"** → suppresses the error and leaves a silent gap. Never convert a failure into a success.
> - **"Propagate every exception to a top-level handler that stops the workflow"** → discards partial results. Recover locally first, then propagate the remainder with context.
> - **"Retry everything with exponential backoff"** → wasteful for validation, permission and business errors. Retry only errors marked retryable.
> - **"Treat an empty search result as an error"** → misclassifies a valid outcome and causes pointless retries. Distinguish access failures from valid empty results.
>
> Sample question 8 (scenario 3) is the canonical case: the correct answer returns failure type, attempted query, partial results and alternatives.

## Check yourself

<details>
<summary>A refund tool rejects an order outside the return window. Should the agent retry?</summary>

No. The business error is non-retryable; the agent should relay the customer-facing explanation or escalate.
</details>

<details>
<summary>A subagent's search times out twice, then succeeds on the third try. What does the coordinator see?</summary>

Only the successful result. Transient failures are resolved locally and not propagated.
</details>

<details>
<summary>A query for order 99999 matches nothing. How should the tool respond?</summary>

As a successful result with <code>found: false</code>, not an error, so the agent reports the absence instead of retrying.
</details>

> [!NOTE]
> The MCP `isError` flag marks a failed call; the category, retryability and explanation fields are a convention you define in the payload.
