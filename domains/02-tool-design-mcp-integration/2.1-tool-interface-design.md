# 2.1 Design effective tool interfaces with clear descriptions and boundaries

## Knowledge of

- Tool descriptions are the primary mechanism LLMs use for tool selection; minimal descriptions lead to unreliable selection among similar tools.
- The importance of including input formats, example queries, edge cases, and boundary explanations in tool descriptions.
- How ambiguous or overlapping tool descriptions cause misrouting (e.g., `analyze_content` vs `analyze_document` with near-identical descriptions).
- The impact of system prompt wording on tool selection: keyword-sensitive instructions can create unintended tool associations.

## Skills in

- Writing tool descriptions that clearly differentiate each tool's purpose, expected inputs, outputs, and when to use it versus similar alternatives.
- Renaming tools and updating descriptions to eliminate functional overlap (e.g., renaming `analyze_content` to `extract_web_results` with a web-specific description).
- Splitting generic tools into purpose-specific tools with defined input/output contracts (e.g., splitting a generic `analyze_document` into `extract_data_points`, `summarize_content`, and `verify_claim_against_source`).
- Reviewing system prompts for keyword-sensitive instructions that might override well-written tool descriptions.

## Code snippets

### Minimal vs differentiated descriptions

Both tools take similar identifiers, so the description is the only thing separating them.

```python
# Minimal: Claude guesses, and picks get_customer for "check my order #12345"
BAD = [
    {"name": "get_customer", "description": "Retrieves customer information", "input_schema": {...}},
    {"name": "lookup_order", "description": "Retrieves order details", "input_schema": {...}},
]

GOOD = [
    {
        "name": "get_customer",
        # Purpose, accepted inputs, outputs, a negative boundary and ambiguity handling: what the model selects on
        "description": (
            "Look up a customer account by email address or phone number. Returns the "
            "verified customer ID, name and account status. Use this FIRST to identify "
            "who you are talking to. Do NOT use it to look up an order: it does not accept "
            "order numbers (#12345) and returns no order data. If several customers match, "
            "it returns all of them; ask the user for another identifier."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "email": {"type": "string", "description": "e.g. jane@example.com"},
                "phone": {"type": "string", "description": "E.164 format, e.g. +14155550123"},
            },
        },
    },
    {
        "name": "lookup_order",
        "description": (
            "Fetch one order's status, items, dates and shipping details by order number. "
            "Use when the user mentions an order number like #12345 or ORD-98765. Requires a "
            "customer_id from get_customer. Returns nothing about the customer's account "
            "or other orders."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "order_number": {"type": "string", "description": "e.g. 12345 (digits only, no #)"},
                "customer_id": {"type": "string", "description": "From get_customer"},
            },
            # Required customer_id makes the get_customer-first order structural, not just advised in prose
            "required": ["order_number", "customer_id"],
        },
    },
]
```

### `input_examples` for format-sensitive inputs

Each example must validate against `input_schema`.

```python
{
    "name": "lookup_order",
    "description": "...",
    "input_schema": {...},
    # Concrete examples teach value formats that prose describes poorly; they cost prompt tokens, so use them where formats are ambiguous
    "input_examples": [
        {"order_number": "12345", "customer_id": "cus_123"},
        {"order_number": "98765", "customer_id": "cus_456"},
    ],
}
```

### Rename and split to remove overlap

```text
analyze_content  + analyze_document          (near-identical descriptions, misrouted)
        ->
extract_web_results                          (web pages only; returns claims + URLs)
extract_data_points | summarize_content | verify_claim_against_source   (split by purpose)
```

### Check the system prompt too

Keyword-sensitive wording such as "always check the customer first" can pull Claude toward `get_customer` and override a good tool description. Review it after rewriting descriptions.

## Commentary: the concepts behind the code

SDK names are illustrative; know the concept, not the exact parameter.

### The design decision

A tool's name, description and schema form the only interface the model sees when choosing between actions. The model has no access to the implementation, so selection quality is bounded by how well that text states purpose, inputs, outputs and boundaries. The principle: when selection is unreliable, improve the interface text first, because it is the root cause, the cheapest fix and the one that generalises to every future request.

### Walk-through

- The minimal pair ("Retrieves customer information" / "Retrieves order details") gives the model almost nothing to separate two tools that take similar identifiers. "check my order #12345" contains a customer-flavoured request and an identifier, so the model guesses, and it guesses wrong a predictable fraction of the time. The error is systematic, not random, which is why it shows up in production logs.
- The differentiated `get_customer` description states what it accepts (email, phone), what it returns, when to use it (first) and when not to (order numbers). The negative boundary matters as much as the positive one: it directly addresses the confusing input.
- Ambiguity handling ("if several customers match, ask the user") belongs in the description because it is tool-specific behaviour; putting it in the description keeps the knowledge next to the tool.
- `lookup_order` names its dependency on `get_customer` and makes `customer_id` a required parameter. The schema forces the model to obtain an ID before it can call the tool, but only a hook or gate guarantees the call happens; the required field is a strong nudge, not enforcement.
- Parameter descriptions with example values (`+14155550123`, digits only, no `#`) prevent format errors that otherwise surface as validation failures at runtime.
- `input_examples` is for formats that prose describes poorly. Each example must validate against the schema, otherwise the examples teach a contract the tool rejects.
- Rename-and-split removes overlap at the source. `analyze_content` and `analyze_document` with near-identical descriptions cannot be disambiguated by any amount of prompting; distinct names and single-purpose contracts can.
- The closing system-prompt note reflects a second source of misrouting: an instruction such as "always check the customer first" is keyword-sensitive and can create an association with `get_customer` that overrides a well-written description.

### Trade-offs and alternatives

- **Longer descriptions vs prompt size:** detailed descriptions cost tokens on every request. The cost is small relative to misrouted calls, but descriptions should be dense, not padded.
- **Few-shot examples in the system prompt:** can help, but they add tokens, do not fix the unclear interface and leave the confusing description in place. Use them after descriptions are good, for judgement-style behaviour.
- **Consolidating tools:** merging into one `lookup_entity` removes the choice but moves complexity inside the tool and makes its contract harder to describe. It is valid architecture, but heavier than a first step.
- **Splitting generic tools:** purpose-specific tools (`extract_data_points`, `summarize_content`, `verify_claim_against_source`) give clean contracts and allow per-tool scoping and permissions, at the cost of more tools in the list (see 2.3).
- **Routing layer or keyword pre-selection:** deterministic, but it duplicates the model's language understanding, needs maintenance as phrasing changes and bypasses the mechanism the model is designed to use.
- **Renaming vs rewriting:** a rename helps when the name itself suggests overlap; a description rewrite is enough when names are already distinct.

### Exam traps

- "Add 5-8 few-shot examples of correct routing": treats symptoms and adds token overhead. Rule: tool descriptions are the primary selection mechanism; fix them before adding anything else.
- "Build a routing layer that pre-selects tools by keyword": over-engineered and bypasses the model. Rule: do not add infrastructure that does not address the diagnosed cause.
- "Merge both tools into one": plausible but disproportionate for a first step. Rule: choose the lowest-effort fix that targets the root cause.
- "Expand the system prompt with more tool rules": can create keyword associations that make misrouting worse. Rule: check the system prompt for keyword-sensitive wording whenever tool selection is odd.
- "Fine-tune or retrain": never the first response to ambiguous interface text.
- Sample question 2 (scenario 1) is the canonical form: minimal descriptions, similar identifiers, "most effective first step". The answer is richer descriptions with formats, examples, edge cases and boundaries.

### Check yourself

- Two tools, `search_docs` and `find_documents`, are called interchangeably and sometimes wrongly. What is the first step? Rewrite the descriptions to state distinct purposes, inputs, outputs and when not to use each; rename or merge if they truly overlap.
- After rewriting descriptions, an agent still prefers `get_customer` for order questions. What else should be checked? The system prompt, for keyword-sensitive instructions that create an unintended association.
- Why must an `input_examples` entry validate against the schema? An invalid example teaches the model a call shape the tool will reject, defeating the purpose.
