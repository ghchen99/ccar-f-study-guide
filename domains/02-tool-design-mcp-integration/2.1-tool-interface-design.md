# 2.1 Design effective tool interfaces with clear descriptions and boundaries

> [!NOTE]
> **At a glance**
>
> - **Selection:** descriptions are the primary signal for choosing a tool; minimal ones make similar tools unreliable.
> - **Content:** state inputs, formats, examples, edge cases and boundaries (when not to use it).
> - **Overlap:** near-identical descriptions (`analyze_content` vs `analyze_document`) cause misrouting.
> - **System prompt:** keyword-sensitive wording can create unintended tool associations.

## Example

### Minimal vs differentiated descriptions

Both tools take similar identifiers, so the description is the only thing separating them.

```python
# Minimal: Claude guesses, and picks get_customer for "check my order #12345"
BAD = [
    {"name": "get_customer", "description": "Retrieves customer information", "input_schema": {...}},
    {"name": "lookup_order", "description": "Retrieves order details", "input_schema": {...}},
]

GOOD = [
    {
        "name": "get_customer",
        # Purpose, accepted inputs, outputs, a negative boundary and ambiguity handling: what the model selects on
        "description": (
            "Look up a customer account by email address or phone number. Returns the "
            "verified customer ID, name and account status. Use this FIRST to identify "
            "who you are talking to. Do NOT use it to look up an order: it does not accept "
            "order numbers (#12345) and returns no order data. If several customers match, "
            "it returns all of them; ask the user for another identifier."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "email": {"type": "string", "description": "e.g. jane@example.com"},
                "phone": {"type": "string", "description": "E.164 format, e.g. +14155550123"},
            },
        },
    },
    {
        "name": "lookup_order",
        "description": (
            "Fetch one order's status, items, dates and shipping details by order number. "
            "Use when the user mentions an order number like #12345 or ORD-98765. Requires a "
            "customer_id from get_customer. Returns nothing about the customer's account "
            "or other orders."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "order_number": {"type": "string", "description": "e.g. 12345 (digits only, no #)"},
                "customer_id": {"type": "string", "description": "From get_customer"},
            },
            # Required customer_id makes the get_customer-first order structural, not just advised in prose
            "required": ["order_number", "customer_id"],
        },
    },
]
```

### `input_examples` for format-sensitive inputs

Each example must validate against `input_schema`.

```python
{
    "name": "lookup_order",
    "description": "...",
    "input_schema": {...},
    # Concrete examples teach value formats that prose describes poorly; they cost prompt tokens, so use them where formats are ambiguous
    "input_examples": [
        {"order_number": "12345", "customer_id": "cus_123"},
        {"order_number": "98765", "customer_id": "cus_456"},
    ],
}
```

### Rename and split to remove overlap

```text
analyze_content  + analyze_document          (near-identical descriptions, misrouted)
        ->
extract_web_results                          (web pages only; returns claims + URLs)
extract_data_points | summarize_content | verify_claim_against_source   (split by purpose)
```

### Check the system prompt too

Keyword-sensitive wording such as "always check the customer first" can pull Claude toward `get_customer` and override a good description. Review it after rewriting descriptions.

## How it works

> [!IMPORTANT]
> **The model sees only the tool's name, description and schema.** When selection is unreliable, fix that text first: it is the root cause, the cheapest fix and it generalises to every future request.

1. **Separate near-identical tools.** "Retrieves customer information" / "Retrieves order details" leaves the model guessing on "check my order #12345". The error is systematic, not random.
2. **State the boundary both ways.** `get_customer` says what it accepts, returns, when to use it (first) and when not to (order numbers).
3. **Keep tool-specific behaviour in the description,** such as "if several customers match, ask the user".
4. **Nudge ordering with the schema.** A required `customer_id` forces an ID before the call, but only a hook or gate guarantees it ([1.4](../01-agentic-architecture-orchestration/1.4-workflow-enforcement-handoff.md)).
5. **Show formats.** Parameter descriptions (`+14155550123`, digits only) and `input_examples` prevent runtime validation failures; examples must validate against the schema.
6. **Rename and split at the source.** No prompting disambiguates identical descriptions; distinct names and single-purpose contracts can. Then check the system prompt for keyword-sensitive wording.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Longer descriptions | Fewer misrouted calls | Tokens on every request; keep them dense, not padded |
| Few-shot routing examples | Help judgement-style behaviour | Add tokens and leave the unclear interface in place; use after descriptions are good |
| Consolidate into one `lookup_entity` | Removes the choice | Complexity moves inside the tool; heavier than a first step |
| Split generic tools by purpose | Clean contracts, per-tool scoping and permissions | More tools in the list ([2.3](2.3-tool-distribution-tool-choice.md)) |
| Keyword routing layer | Deterministic | Duplicates model understanding, needs upkeep, bypasses the designed mechanism |
| Rename vs rewrite | Rename when the name suggests overlap | Rewrite is enough when names are already distinct |

> [!WARNING]
> **Exam traps**
>
> - **"Add 5-8 few-shot examples of correct routing"** → treats symptoms and adds tokens. Descriptions are the primary selection mechanism; fix them first.
> - **"Build a routing layer that pre-selects tools by keyword"** → over-engineered; bypasses the model. Don't add infrastructure that misses the diagnosed cause.
> - **"Merge both tools into one"** → disproportionate as a first step. Pick the lowest-effort fix that targets the root cause.
> - **"Expand the system prompt with more tool rules"** → can create keyword associations that worsen misrouting. Check it for keyword-sensitive wording.
> - **"Fine-tune or retrain"** → never the first response to ambiguous interface text.
>
> Sample question 2 (scenario 1) is the canonical form: minimal descriptions, similar identifiers, "most effective first step". Answer: richer descriptions with formats, examples, edge cases and boundaries.

## Check yourself

<details>
<summary>Two tools, <code>search_docs</code> and <code>find_documents</code>, are called interchangeably and sometimes wrongly. What is the first step?</summary>

Rewrite the descriptions to state distinct purposes, inputs, outputs and when not to use each. Rename or merge if they truly overlap.
</details>

<details>
<summary>After rewriting descriptions, an agent still prefers <code>get_customer</code> for order questions. What else should be checked?</summary>

The system prompt, for keyword-sensitive instructions that create an unintended association.
</details>

<details>
<summary>Why must an <code>input_examples</code> entry validate against the schema?</summary>

An invalid example teaches a call shape the tool will reject, defeating its purpose.
</details>

> [!TIP]
> Per the docs, detailed descriptions are the most important factor: what the tool does, when to use it and when not, what each parameter means, and caveats. Consolidate related operations and namespace names, e.g. `github_list_prs`.
