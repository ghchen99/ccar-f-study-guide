# 2.1 Design effective tool interfaces with clear descriptions and boundaries

## Knowledge of

- Tool descriptions are the primary mechanism LLMs use for tool selection; minimal descriptions lead to unreliable selection among similar tools.
- The importance of including input formats, example queries, edge cases, and boundary explanations in tool descriptions.
- How ambiguous or overlapping tool descriptions cause misrouting (e.g., `analyze_content` vs `analyze_document` with near-identical descriptions).
- The impact of system prompt wording on tool selection: keyword-sensitive instructions can create unintended tool associations.

## Skills in

- Writing tool descriptions that clearly differentiate each tool's purpose, expected inputs, outputs, and when to use it versus similar alternatives.
- Renaming tools and updating descriptions to eliminate functional overlap (e.g., renaming `analyze_content` to `extract_web_results` with a web-specific description).
- Splitting generic tools into purpose-specific tools with defined input/output contracts (e.g., splitting a generic `analyze_document` into `extract_data_points`, `summarize_content`, and `verify_claim_against_source`).
- Reviewing system prompts for keyword-sensitive instructions that might override well-written tool descriptions.

## Code snippets

### Minimal vs differentiated descriptions

Both tools take similar identifiers, so the description is the only thing separating them.

```python
# Minimal: Claude guesses, and picks get_customer for "check my order #12345"
BAD = [
    {"name": "get_customer", "description": "Retrieves customer information", "input_schema": {...}},
    {"name": "lookup_order", "description": "Retrieves order details", "input_schema": {...}},
]

GOOD = [
    {
        "name": "get_customer",
        "description": (
            "Look up a customer account by email address or phone number. Returns the "
            "verified customer ID, name and account status. Use this FIRST to identify "
            "who you are talking to. Do NOT use it to look up an order: it does not accept "
            "order numbers (#12345) and returns no order data. If several customers match, "
            "it returns all of them; ask the user for another identifier."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "email": {"type": "string", "description": "e.g. jane@example.com"},
                "phone": {"type": "string", "description": "E.164 format, e.g. +14155550123"},
            },
        },
    },
    {
        "name": "lookup_order",
        "description": (
            "Fetch one order's status, items, dates and shipping details by order number. "
            "Use when the user mentions an order number like #12345 or ORD-98765. Requires a "
            "customer_id from get_customer. Returns nothing about the customer's account "
            "or other orders."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "order_number": {"type": "string", "description": "e.g. 12345 (digits only, no #)"},
                "customer_id": {"type": "string", "description": "From get_customer"},
            },
            "required": ["order_number", "customer_id"],
        },
    },
]
```

### `input_examples` for format-sensitive inputs

Each example must validate against `input_schema`.

```python
{
    "name": "lookup_order",
    "description": "...",
    "input_schema": {...},
    "input_examples": [
        {"order_number": "12345", "customer_id": "cus_123"},
        {"order_number": "98765", "customer_id": "cus_456"},
    ],
}
```

### Rename and split to remove overlap

```text
analyze_content  + analyze_document          (near-identical descriptions, misrouted)
        ->
extract_web_results                          (web pages only; returns claims + URLs)
extract_data_points | summarize_content | verify_claim_against_source   (split by purpose)
```

### Check the system prompt too

Keyword-sensitive wording such as "always check the customer first" can pull Claude toward `get_customer` and override a good tool description. Review it after rewriting descriptions.

Source: [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools). Its guidance: detailed descriptions are the most important factor (what it does, when to use it and when not, what each parameter means, caveats); consolidate related operations; namespace names such as `github_list_prs`.
