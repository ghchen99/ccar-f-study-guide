# 2.4 Integrate MCP servers into Claude Code and agent workflows

> [!NOTE]
> **At a glance**
>
> - **Scope:** project `.mcp.json` for shared team tooling; user `~/.claude.json` for personal or experimental servers.
> - **Secrets:** `${GITHUB_TOKEN}` expansion in `.mcp.json` keeps credentials out of git.
> - **Discovery:** tools from all configured servers load at connection time and are available together.
> - **Resources:** expose content catalogues (issues, docs, schemas) to cut exploratory tool calls.

## Example

### Project scope: `.mcp.json` committed to the repo, secrets via env expansion

```json
{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": { "Authorization": "Bearer ${GITHUB_TOKEN}" }
    },
    "db": {
      "command": "npx",
      "args": ["-y", "@bytebase/dbhub", "--config", "dbhub.toml"],
      "env": { "DATABASE_URL": "${DATABASE_URL}" }
    },
    "api-server": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp"
    }
  }
}
```

`${VAR}` expands to the variable; `${VAR:-default}` falls back when it is unset. Expansion works in `command`, `args`, `env`, `url` and `headers`, so the token never lands in version control.

### CLI scopes

```bash
claude mcp add --transport http github --scope project https://api.githubcopilot.com/mcp/   # .mcp.json, shared
claude mcp add --transport http hubspot --scope user https://mcp.hubspot.com/anthropic       # ~/.claude.json, all my projects
claude mcp add --transport http stripe https://mcp.stripe.com                                 # local (default), ~/.claude.json, this project only
claude mcp list
```

| Scope | Loads in | Shared | Stored in |
| - | - | - | - |
| local (default) | current project | no | `~/.claude.json` |
| project | current project | yes, via git | `.mcp.json` |
| user | all projects | no | `~/.claude.json` |

Precedence when a name repeats: local, then project, then user. The whole entry from the winning scope is used; fields are not merged. Tools from all configured servers are available at once.

### Agent SDK: servers in code, tool naming and allow-listing

```python
import os
from claude_agent_sdk import ClaudeAgentOptions

options = ClaudeAgentOptions(
    mcp_servers={
        "github": {
            "type": "http",
            "url": "https://api.githubcopilot.com/mcp/",
            "headers": {"Authorization": f"Bearer {os.environ['GITHUB_TOKEN']}"},  # read from the environment at runtime, never hard-coded
        }
    },
    # mcp__<server>__<tool>; MCP tools need explicit permission
    # Wildcard per server grants a trusted server wholesale; list single tools to apply least privilege
    allowed_tools=["mcp__github__list_issues", "mcp__db__*"],
)
```

Project `.mcp.json` is picked up when the `project` setting source is enabled (the default).

### Make MCP tools win over built-ins by describing them well

```python
{
    "name": "search_code_semantic",
    # The built-in Grep is familiar and well-described; an MCP tool with a vague description loses to it by default
    "description": (
        "Semantic code search across the indexed monorepo. Finds code by meaning "
        "(e.g. 'where do we retry failed payments') and returns ranked file paths with "
        "snippets. Prefer this over Grep when you don't know the exact identifier; use "
        "Grep for exact strings."
    ),
}
```

### MCP resources: expose a catalogue so the agent does not explore blindly

```text
Can you analyze @github:issue://123 and suggest a fix?
Compare @postgres:schema://users with @docs:file://database/user-model
```

Claude Code lists and reads resources through built-in `ListMcpResources` and `ReadMcpResource` tools when servers expose them.

## How it works

> [!IMPORTANT]
> **MCP integration is a configuration and trust problem as much as a tool problem.** Scope configuration to its audience, keep secrets out of version control, reuse standard servers, and treat descriptions and resources as how the agent learns what is available.

1. **Scope by audience.** Project scope (committed `.mcp.json`) gives the team identical tooling from a fresh clone; user scope holds personal or experimental servers; local is the private per-project default.
2. **Expand, never embed.** `${GITHUB_TOKEN}` resolves from each developer's environment. A literal token would leak to everyone with repo access and survive in history. Use `${VAR:-default}` only for non-secret settings such as a base URL.
3. **Expect whole-entry precedence.** When a name repeats, the winning scope's entry is used with no field merging, so a personal override replaces a shared definition entirely.
4. **Limit what you connect.** All servers' tools are offered at once, and each enlarges the list the model chooses from ([2.3](2.3-tool-distribution-tool-choice.md)). Names are `mcp__<server>__<tool>` and need explicit permission; wildcards grant a whole server, single tools are least privilege.
5. **Describe MCP tools to beat built-ins.** Built-ins are familiar and well described, so a thin MCP description loses even if the tool is more capable. State what it does better than Grep and when to still use Grep.
6. **Expose resources.** A catalogue (issue summaries, schemas, doc hierarchies) lets the agent read what exists instead of spending several exploratory calls finding out.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Community server | Saves build and upkeep; quicker to adopt | Covers only standard integrations |
| Custom server | Fits team-specific workflows | You own auth, errors and versioning |
| Project scope | Consistency and fast onboarding | Exposes configuration to the whole team |
| User scope | Experiment without side effects | Not shared |
| Wildcard allow-list | Simple | Per-tool lists reduce blast radius if a server exposes destructive tools |
| Resources vs tools | Resources avoid exploratory calls for read-mostly catalogues | Must stay reasonably small; tools suit parameterised actions or queries |
| Many servers | Broader coverage | Competes with selection reliability and context cost |
| Env expansion | Enough for per-developer tokens | Stricter environments may need a central secret store feeding the environment |

> [!WARNING]
> **Exam traps**
>
> - **"Put the API token directly in `.mcp.json` so teammates can use it"** → leaks a secret into version control. Use environment variable expansion.
> - **"Put the shared server in `~/.claude.json`"** → every teammate configures it by hand and setups drift. Shared tooling belongs in project scope.
> - **"Put a personal experiment in `.mcp.json`"** → affects the whole team. Personal or experimental servers belong in user scope.
> - **"Build a custom Jira server"** → reinvents a standard integration. Prefer community servers; reserve custom ones for team-specific workflows.
> - **"The agent keeps using Grep instead of the MCP tool, so remove Grep"** → heavy-handed. Improve the MCP tool description; descriptions drive selection.
> - **"Add more search tools so the agent can find the data"** → doesn't address visibility. Expose a content catalogue as an MCP resource.
> - **"Each server loads only when needed"** → all configured servers' tools are available together, so selection needs care.

## Check yourself

<details>
<summary>A team wants a shared GitHub server whose token differs per developer. How is it configured?</summary>

In project <code>.mcp.json</code> with the token referenced as <code>${GITHUB_TOKEN}</code>, each developer supplying the variable locally.
</details>

<details>
<summary>A capable semantic-search MCP tool is ignored in favour of Grep. What is the first fix?</summary>

Rewrite its description to state what it does, what it returns and when it beats Grep.
</details>

<details>
<summary>An agent burns many calls discovering which database tables exist. What reduces this?</summary>

Expose the schema as an MCP resource so the agent can read the catalogue directly.
</details>
