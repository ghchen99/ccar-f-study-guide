# 2.4 Integrate MCP servers into Claude Code and agent workflows

## At a glance

- MCP server scoping: project-level (`.mcp.json`) for shared team tooling vs user-level (`~/.claude.json`) for personal/experimental servers.
- Environment variable expansion in `.mcp.json` (e.g., `${GITHUB_TOKEN}`) for credential management without committing secrets.
- Tools from all configured MCP servers are discovered at connection time and available simultaneously to the agent.
- MCP resources as a mechanism for exposing content catalogs (e.g., issue summaries, documentation hierarchies, database schemas) to reduce exploratory tool calls.

## Example

### Project scope: `.mcp.json` committed to the repo, secrets via env expansion

```json
{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": { "Authorization": "Bearer ${GITHUB_TOKEN}" }
    },
    "db": {
      "command": "npx",
      "args": ["-y", "@bytebase/dbhub", "--config", "dbhub.toml"],
      "env": { "DATABASE_URL": "${DATABASE_URL}" }
    },
    "api-server": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp"
    }
  }
}
```

`${VAR}` expands to the variable; `${VAR:-default}` falls back when it is unset. Expansion works in `command`, `args`, `env`, `url` and `headers`. The token never lands in version control.

### CLI scopes

```bash
claude mcp add --transport http github --scope project https://api.githubcopilot.com/mcp/   # .mcp.json, shared
claude mcp add --transport http hubspot --scope user https://mcp.hubspot.com/anthropic       # ~/.claude.json, all my projects
claude mcp add --transport http stripe https://mcp.stripe.com                                 # local (default), ~/.claude.json, this project only
claude mcp list
```

| Scope | Loads in | Shared | Stored in |
| - | - | - | - |
| local (default) | current project | no | `~/.claude.json` |
| project | current project | yes, via git | `.mcp.json` |
| user | all projects | no | `~/.claude.json` |

Precedence when a name repeats: local, then project, then user. The whole entry from the winning scope is used; fields are not merged. Tools from all configured servers are available at once.

### Agent SDK: servers in code, tool naming and allow-listing

```python
import os
from claude_agent_sdk import ClaudeAgentOptions

options = ClaudeAgentOptions(
    mcp_servers={
        "github": {
            "type": "http",
            "url": "https://api.githubcopilot.com/mcp/",
            "headers": {"Authorization": f"Bearer {os.environ['GITHUB_TOKEN']}"},  # read from the environment at runtime, never hard-coded
        }
    },
    # mcp__<server>__<tool>; MCP tools need explicit permission
    # Wildcard per server grants a trusted server wholesale; list single tools to apply least privilege
    allowed_tools=["mcp__github__list_issues", "mcp__db__*"],
)
```

Project `.mcp.json` is picked up when the `project` setting source is enabled (the default).

### Make MCP tools win over built-ins by describing them well

```python
{
    "name": "search_code_semantic",
    # The built-in Grep is familiar and well-described; an MCP tool with a vague description loses to it by default
    "description": (
        "Semantic code search across the indexed monorepo. Finds code by meaning "
        "(e.g. 'where do we retry failed payments') and returns ranked file paths with "
        "snippets. Prefer this over Grep when you don't know the exact identifier; use "
        "Grep for exact strings."
    ),
}
```

### MCP resources: expose a catalogue so the agent does not explore blindly

```text
Can you analyze @github:issue://123 and suggest a fix?
Compare @postgres:schema://users with @docs:file://database/user-model
```

Claude Code lists and reads resources through built-in `ListMcpResources` and `ReadMcpResource` tools when servers expose them.

## Why this matters

SDK names are illustrative; know the concept, not the exact parameter. JSON has no comment syntax, so the reasoning for `.mcp.json` is given here instead.

> [!IMPORTANT]
> **The principle**

MCP integration is a configuration and trust problem as much as a tool problem: which servers are shared with the team, which are personal, where credentials live, and how the agent is steered toward the capable tool rather than the familiar one. The principle: scope configuration to the audience that needs it, keep secrets out of version control, reuse standard servers instead of building them, and treat descriptions and resources as the way the agent learns what is available.

**The flow**

- Project scope (`.mcp.json`, committed) gives the whole team the same tooling from a fresh clone, so shared integrations behave consistently. User scope (`~/.claude.json`) holds personal or experimental servers that should not affect teammates. Local scope is the default for one project, privately.
- `${GITHUB_TOKEN}` and `${DATABASE_URL}` in the committed file are placeholders resolved from each developer's environment. The file can be reviewed and shared while the credential never enters git history. A literal token in `.mcp.json` would leak to everyone with repository access and survive in history even after removal.
- `${VAR:-default}` gives a fallback for non-secret settings such as a base URL; it should not be used to hide a real secret default.
- When a name repeats across scopes, the winning scope's whole entry is used with no field merging. A personal override therefore replaces a shared definition completely, which is a source of confusing "why is my config ignored" problems.
- Tools from all configured servers are discovered at connection time and offered simultaneously. This is convenient, but every added server enlarges the tool list the model chooses from (see 2.3), so connect what the task needs.
- Names take the form `mcp__<server>__<tool>`, and MCP tools need explicit permission. The wildcard grants a whole server; naming individual tools is least privilege.
- Credentials in the SDK example come from the environment at runtime, the in-code equivalent of env expansion.
- The `search_code_semantic` description says what the tool does better than Grep and when to still use Grep. Built-in tools are familiar and well described; an MCP tool with a thin description loses to them even when it is more capable. The fix is a better description, not removing the built-in.
- Resources expose a catalogue (issue summaries, schemas, documentation hierarchies) the agent can read directly. Without them the agent spends several exploratory calls working out what exists before doing the task.

## Trade-offs

- **Community server vs custom:** a maintained server (Jira, GitHub) saves build and upkeep cost and is quicker to adopt; a custom server is justified for team-specific workflows no standard server covers, at the cost of owning auth, errors and versioning.
- **Project vs user scope:** project scope maximises consistency and onboarding speed but exposes the configuration to the whole team; user scope allows experimentation without side effects but is not shared.
- **Wildcard vs per-tool allow-listing:** wildcards are simple, while per-tool lists reduce blast radius when a server exposes destructive tools.
- **Resources vs tools:** resources suit read-mostly catalogues the agent should see up front; tools suit parameterised actions or queries. A resource avoids exploratory calls but must stay reasonably small to be worth including.
- **Many servers vs few:** broader coverage competes with selection reliability and context cost.
- **Env expansion vs a secrets manager:** expansion is enough for per-developer tokens; stricter environments may need a central secret store feeding the environment.

> [!WARNING]
> **Exam traps**

- "Put the API token directly in `.mcp.json` so teammates can use it": leaks a secret into version control. Rule: use environment variable expansion; never commit credentials.
- "Put the shared server in `~/.claude.json`": every teammate must configure it by hand and the setups drift. Rule: shared team tooling belongs in project scope.
- "Put a personal experiment in `.mcp.json`": affects the whole team. Rule: personal or experimental servers belong in user scope.
- "Build a custom Jira server": reinvents a standard integration. Rule: prefer existing community servers for standard integrations and reserve custom ones for team-specific workflows.
- "The agent keeps using Grep instead of the MCP tool, so remove Grep": heavy-handed. Rule: improve the MCP tool description so its capabilities and outputs are clear; descriptions drive selection.
- "Add more search tools so the agent can find the data": does not address visibility. Rule: expose a content catalogue as an MCP resource so exploration is unnecessary.
- Assuming each server loads only when needed: tools from all configured servers are available together, so tool selection needs care.

## Quick check

- A team wants a shared GitHub server whose token differs per developer. How is it configured? In project `.mcp.json` with the token referenced as `${GITHUB_TOKEN}`, each developer supplying the variable locally.
- A capable semantic-search MCP tool is ignored in favour of Grep. What is the first fix? Rewrite its description to state what it does, what it returns and when it beats Grep.
- An agent burns many calls discovering which database tables exist. What reduces this? Expose the schema as an MCP resource so the agent can read the catalogue directly.
