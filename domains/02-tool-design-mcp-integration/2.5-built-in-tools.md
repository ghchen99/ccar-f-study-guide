# 2.5 Select and apply built-in tools (Read, Write, Edit, Bash, Grep, Glob) effectively

## Knowledge of

- Grep for content search (searching file contents for patterns like function names, error messages, or import statements).
- Glob for file path pattern matching (finding files by name or extension patterns).
- Read/Write for full file operations; Edit for targeted modifications using unique text matching.
- When Edit fails due to non-unique text matches, using Read + Write as a fallback for reliable file modifications.

## Skills in

- Selecting Grep for searching code content across a codebase (e.g., finding all callers of a function, locating error messages).
- Selecting Glob for finding files matching naming patterns (e.g., `**/*.test.tsx`).
- Using Read to load full file contents followed by Write when Edit cannot find unique anchor text.
- Building codebase understanding incrementally: starting with Grep to find entry points, then using Read to follow imports and trace flows, rather than reading all files upfront.
- Tracing function usage across wrapper modules by first identifying all exported names, then searching for each name across the codebase.

## Code snippets

### Which tool for which question

| Need | Tool | Example input |
| - | - | - |
| Find code by content (callers, error strings, imports) | `Grep` | `{"pattern": "def process_refund", "output_mode": "content", "-n": True}` |
| Find files by name | `Glob` | `{"pattern": "**/*.test.tsx"}` |
| Read a whole file | `Read` | `{"file_path": "/repo/src/refunds.py"}` |
| Targeted change at a unique spot | `Edit` | `{"file_path": ..., "old_string": ..., "new_string": ...}` |
| Create or fully rewrite a file | `Write` | `{"file_path": ..., "content": ...}` |
| Run commands | `Bash` | `{"command": "pytest -q"}` |

Input shapes are from the [Python SDK reference](https://code.claude.com/docs/en/agent-sdk/python.md). `Grep` also takes `glob`, `type`, `-i`, `-A/-B/-C`, `head_limit` and `output_mode` (`content`, `files_with_matches`, `count`).

### Edit with non-unique text: add context, or fall back to Read + Write

```python
# Fails when old_string appears more than once
# Ambiguity is rejected rather than guessed, so the tool never edits the wrong spot silently
{"file_path": "/repo/a.py", "old_string": "return None", "new_string": "return default"}

# Option 1: include enough surrounding lines to be unique
{"file_path": "/repo/a.py",
 "old_string": "    if not order:\n        return None",
 "new_string": "    if not order:\n        return default"}

# Option 2: replace every occurrence deliberately
# Only correct when every occurrence is meant to change
{"file_path": "/repo/a.py", "old_string": "return None", "new_string": "return default", "replace_all": True}

# Option 3 (the exam's fallback): Read the full file, then Write the modified content
# Reliable because it needs no unique anchor, but rewrites the whole file, so review the diff
```

### Build understanding incrementally

```text
1. Grep  "def process_refund"                      -> find the entry point
2. Read  refunds.py                                -> see what it imports and calls
3. Grep  "from payments import|import payments"    -> follow one dependency
4. Read  only the files the trace points to
```

Do not Read every file up front.

### Trace usage through wrapper modules

```text
1. Read  utils/http.py; list the exported names: fetch_json, post_json, retry
2. Grep each name separately across the repo: "fetch_json", "post_json", "retry"
   (a caller may import the wrapper under a different name or re-export it)
```

### Restrict which built-ins an agent can use

```python
from claude_agent_sdk import ClaudeAgentOptions

# Availability: only these built-ins exist for Claude. Permission: these are auto-approved.
# A read-only toolset makes mutation impossible, which is stronger than asking the agent not to edit
ClaudeAgentOptions(tools=["Read", "Grep", "Glob"], allowed_tools=["Read", "Grep", "Glob"])
```

## Commentary: the concepts behind the code

SDK names are illustrative; know the concept, not the exact parameter.

### The design decision

Built-in tools are specialised instruments, and the skill is matching the question to the instrument: content search, name search, whole-file read, surgical edit, full rewrite. Using the right one keeps context small and results reliable. The principle: explore incrementally and on demand, starting narrow and following evidence, rather than loading everything up front, and know the fallback when a precise tool cannot be applied.

### Walk-through

- The tool table maps question type to tool. "Who calls this function" is a content question (Grep); "which files are tests" is a name question (Glob). Mixing them up (globbing for a function name, grepping for a file extension) returns noise or nothing.
- Grep returns matches, not whole files, so it is the cheap way to locate entry points; Read then loads only the files the matches point to. This keeps the context window for relevant material.
- Edit works by matching unique text. If `old_string` appears more than once, the edit is ambiguous and fails rather than guess. Enlarging the match with surrounding lines makes it unique, `replace_all` is right only when every occurrence should change, and Read plus Write is the fallback that needs no anchor.
- Read-then-Write has a cost: the whole file is regenerated, so unrelated lines can be altered by mistake and the diff should be checked. It is a reliability fallback, not the default.
- The incremental exploration sequence (Grep for the entry point, Read, Grep for one dependency, Read only what the trace points to) follows one flow at a time. Reading every file up front fills the context with irrelevant code and degrades later reasoning.
- Wrapper modules hide usage: a caller may import a function under another name or re-export it. Listing the exported names first, then searching for each, finds callers a single search for the original name would miss.
- Restricting `tools` to read-only built-ins makes an investigator agent incapable of modifying anything. Separating availability (what exists) from permission (what is auto-approved) matters: allowing a tool is not the same as making it available.

### Trade-offs and alternatives

- **Grep vs Glob vs Bash `grep` or `find`:** dedicated tools return structured, bounded output and are the intended mechanism; shell commands work but are less controlled and harder to permission.
- **Edit vs Read + Write:** Edit sends minimal change and preserves the rest of the file; Read + Write is robust to non-unique anchors but heavier and riskier for large files.
- **Incremental exploration vs reading everything:** incremental is cheaper and focuses reasoning, but can miss distant dependencies if the trace is careless; targeted follow-up searches mitigate this.
- **Broad Read of large files vs search first:** a search narrows what to read; a full read is justified once the file is known relevant.
- **Subagent exploration vs in-context exploration:** delegating verbose discovery keeps the main context clean (see 5.4); doing it inline is simpler for small questions.
- **Restrictive toolset vs trust in prompts:** removing tools is deterministic, instructions are not.

### Exam traps

- "Use Grep to find all `*.test.tsx` files": Grep searches contents, not names. Rule: file-name patterns are Glob's job.
- "Use Glob to find every caller of `process_refund`": Glob matches paths only. Rule: content questions need Grep.
- "Read all source files first to build a complete picture": floods context. Rule: build understanding incrementally from Grep entry points.
- "Edit failed because the text is not unique, so retry the same Edit": it fails again. Rule: add surrounding context, use `replace_all` deliberately, or fall back to Read + Write.
- "Search once for the function name to find all usages": misses aliases and re-exports. Rule: enumerate the exported names of wrapper modules and search for each.
- "Use Write for a one-line change": rewrites the entire file and risks unrelated changes. Rule: use Edit for targeted changes at a unique spot.
- "Ask the agent not to modify files": probabilistic. Rule: limit the tool set.

### Check yourself

- You need every file named `*.config.ts` under the repo. Which tool? Glob, since it matches file path patterns, not contents.
- An Edit fails because `return None` appears eleven times, and only one should change. What are the options? Expand `old_string` with unique surrounding lines; failing that, Read the file and Write the modified version.
- A utility module re-exports `fetch_json` as `get`. How is every caller found? Read the module to list its exports and aliases, then Grep each name separately.
