# 2.3 Distribute tools appropriately across agents and configure tool choice

## Knowledge of

- Giving an agent too many tools (e.g., 18 instead of 4-5) degrades tool selection reliability by increasing decision complexity.
- Agents with tools outside their specialization tend to misuse them (e.g., a synthesis agent attempting web searches).
- Scoped tool access: giving agents only the tools needed for their role, with limited cross-role tools for specific high-frequency needs.
- `tool_choice` configuration options: `"auto"`, `"any"`, and forced tool selection (`{"type": "tool", "name": "..."}`).

## Skills in

- Restricting each subagent's tool set to those relevant to its role, preventing cross-specialization misuse.
- Replacing generic tools with constrained alternatives (e.g., replacing `fetch_url` with `load_document` that validates document URLs).
- Providing scoped cross-role tools for high-frequency needs (e.g., a `verify_fact` tool for the synthesis agent) while routing complex cases through the coordinator.
- Using `tool_choice` forced selection to ensure a specific tool is called first (e.g., forcing `extract_metadata` before enrichment tools), then processing subsequent steps in follow-up turns.
- Setting `tool_choice: "any"` to guarantee the model calls a tool rather than returning conversational text.

## Code snippets

### Scoped tools per subagent

```python
from claude_agent_sdk import AgentDefinition

agents = {
    "web-searcher": AgentDefinition(
        description="Searches the web and returns claims with sources.",
        prompt="Search the web for the assigned sub-topic.",
        tools=["WebSearch", "WebFetch"],  # search tools live only with the role that needs them
    ),
    "synthesizer": AgentDefinition(
        description="Merges supplied findings into a report.",
        prompt="Combine the findings. For a simple fact-check use verify_fact; "
               "for anything deeper, say so and the coordinator will delegate.",
        # No WebSearch/WebFetch: only the narrow, scoped cross-role tool
        tools=["Read", "mcp__research__verify_fact"],
    ),
}
```

### Replace a generic tool with a constrained one

```python
# fetch_url(url) accepts anything; load_document validates first
# The constraint lives in code, not in a prompt asking the agent to behave; it also narrows what the agent can reach
@tool("load_document", "Load a document from an approved document store URL (https://docs.example.com/...).", {"url": str})
async def load_document(args):
    if not args["url"].startswith("https://docs.example.com/"):
        return {"content": [{"type": "text", "text": "URL is not in the approved document store."}], "is_error": True}
    ...
```

### `tool_choice` on the Messages API

```python
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-opus-5"  # see the model note below

# auto (default): Claude may answer in text instead of calling a tool
client.messages.create(model=MODEL, max_tokens=1024, tools=tools, messages=msgs,
                       tool_choice={"type": "auto"})

# any: must call one of the tools, Claude picks which. No conversational text instead.
# Use when the output must be structured and the right tool depends on the input
client.messages.create(model=MODEL, max_tokens=1024, tools=tools, messages=msgs,
                       tool_choice={"type": "any"})

# tool: must call this exact tool
client.messages.create(model=MODEL, max_tokens=1024, tools=tools, messages=msgs,
                       tool_choice={"type": "tool", "name": "extract_metadata"})
```

### Force `extract_metadata` first, then continue with `auto`

```python
first = client.messages.create(
    model=MODEL, max_tokens=1024, tools=tools, messages=msgs,  # guarantees the first step; forcing it every turn would prevent the loop from ever finishing
    tool_choice={"type": "tool", "name": "extract_metadata"},
)
msgs += [
    {"role": "assistant", "content": first.content},
    {"role": "user", "content": [{"type": "tool_result",
                                  "tool_use_id": first.content[0].id,
                                  "content": run_extract_metadata(first.content[0].input)}]},
]
second = client.messages.create(model=MODEL, max_tokens=1024, tools=tools, messages=msgs,
                                tool_choice={"type": "auto"})  # enrichment tools from here
```

Notes from [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools):

- With `any` or `tool` the API prefills the assistant turn, so there is no text before the `tool_use` block. Use `auto` plus an instruction in the user message if you want explanation first.
- Changing `tool_choice` invalidates cached message blocks.
- **Model caveat:** forced tool use is not supported everywhere. With manual extended thinking (`thinking: {type: "enabled"}`), `any` and `tool` error. Newer models listed in the docs (e.g. Claude Opus 5.5, Sonnet 5.5) return a 400 for them; use `auto` with `strict: true` tool definitions or structured outputs there. The exam still tests the `auto` / `any` / forced semantics.

## Commentary: the concepts behind the code

SDK names are illustrative; know the concept, not the exact parameter.

### The design decision

Every tool an agent can see is a candidate in every decision it makes, so the tool set is part of the agent's reliability budget. Tools should be distributed by role (least privilege), and `tool_choice` should be used to remove model discretion exactly where discretion is not wanted. The principle: constrain the choice space by design, using scoped tool sets for who may do what and `tool_choice` for whether and which tool is called, rather than relying on instructions to keep the model in its lane.

### Walk-through

- Each subagent receives only the tools of its role. A synthesis agent holding web search will use it, because the tool is available and the task looks like it could use it; this blurs the separation between gathering and combining and makes behaviour harder to predict. Removing the tool removes the failure mode.
- Giving an agent many tools (the sources contrast 18 with 4-5) raises decision complexity and lowers selection reliability. Fewer, role-relevant tools mean fewer near-misses between similar options.
- The synthesizer receives one narrow cross-role tool, `verify_fact`, for the common case (simple date, name or statistic checks) while its prompt routes anything deeper back through the coordinator. This removes most round trips without handing over the full search capability.
- `load_document` replaces a generic fetch with a validated, purpose-specific tool. The URL restriction is enforced in code and appears in the description, so the agent can neither wander to arbitrary URLs nor be talked into it.
- `auto` allows a plain text answer, which is right for conversational agents. `any` guarantees some tool call, right when the output must be structured and the tool depends on the input. A forced tool guarantees a specific call.
- Forcing `extract_metadata` first guarantees the ordering for that single step. The follow-up call returns to `auto`, because a forced tool on every turn would never let the model finish. This is a pragmatic way to guarantee a first step without a full state machine.
- Forced selection prefills the assistant turn, so no explanatory text precedes the tool call, and changing `tool_choice` invalidates cached message blocks. These are practical costs of forcing.
- Forced tool use is not available in every configuration (the model caveat above); the semantic distinction is what matters for the exam.

### Trade-offs and alternatives

- **Scoped tools vs convenience:** broad access reduces round trips but increases misuse and attack surface. Scope tightly and add narrow cross-role tools only for high-frequency needs.
- **Cross-role tool vs routing via coordinator:** a scoped tool such as `verify_fact` cuts latency for the frequent simple case; the coordinator path stays for the infrequent complex one. Giving the full toolset trades safety and clarity for speed.
- **Batching verification needs to the end:** reduces trips but creates blocking dependencies, since later synthesis steps may depend on earlier verified facts.
- **Speculative caching of extra context:** cannot predict what will need verifying and bloats context.
- **Forced tool vs prompt instruction:** a forced `tool_choice` guarantees one call; a prompt says "call this first" and is probabilistic. For multi-step ordering that must always hold across many calls, programmatic gates (see 1.4) are stronger.
- **`any` vs `auto` with strict schemas or structured outputs:** where forced selection is unavailable, structured output achieves a similar guarantee by another route.
- **Maintainability:** per-role tool lists are easy to audit; one shared global list is simple but drifts.

### Exam traps

- "Give the synthesis agent all the web search tools": removes round trips but violates separation of concerns and over-provisions. Rule: least privilege; add only the narrow capability that covers the common case.
- "Batch all verifications and return them at the end": introduces blocking dependencies. Rule: do not trade correctness of dependent steps for fewer round trips.
- "Have the search agent pre-cache extra context": speculative and unreliable. Rule: do not build on predictions of what will be needed.
- "Tell the agent in the prompt not to use tools outside its role": probabilistic. Rule: restrict the tool set rather than instruct restraint.
- "Use `any` to make sure one particular tool runs first": `any` lets the model choose which. Rule: forcing a specific tool needs the explicit tool form.
- "Keep `tool_choice` forced for the whole conversation": prevents a final answer. Rule: force the step that needs a guarantee, then return to `auto`.
- Sample question 9 (scenario 3) is the canonical form: 85% simple checks, 15% complex; the answer is a scoped `verify_fact` plus the existing coordinator path for the rest.

### Check yourself

- A report agent keeps issuing web searches although it should only format findings. What is the structural fix? Remove search tools from its tool list rather than adding prompt warnings.
- An extraction pipeline must always call `classify_document` before anything else, and then proceed normally. Which `tool_choice` settings are used? Forced `classify_document` on the first request, then `auto` for later turns.
- When is `any` better than `auto`? When the response must always be a tool call (for example structured output) and the model should pick the right tool for the input.
