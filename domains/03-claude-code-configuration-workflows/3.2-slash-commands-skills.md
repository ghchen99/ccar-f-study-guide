# 3.2 Create and configure custom slash commands and skills

> [!NOTE]
> **At a glance**
>
> - **Location:** `.claude/commands/` or `.claude/skills/` is shared via git; `~/.claude/...` is personal.
> - **Frontmatter:** `SKILL.md` supports `context: fork`, `allowed-tools`, `argument-hint`.
> - **Isolation:** `context: fork` runs the skill in a subagent so verbose output stays out of the main conversation.
> - **Personal variants:** use a different name in `~/.claude/skills/` so teammates are unaffected.

## Example

### Project command shared via git

`.claude/commands/review.md` creates `/review` for everyone who clones the repo. Commands were merged into skills, so it behaves like `.claude/skills/review/SKILL.md`. A personal command goes in `~/.claude/commands/`.

```markdown
---
description: Run the team code review checklist on the current changes
argument-hint: [branch-or-path]
---

Review $ARGUMENTS against our checklist:
1. Error handling on every external call
2. No secrets or credentials in code
3. Tests cover new branches
Report each finding as: location, issue, severity, suggested fix.
```

### Skill with `context: fork` and restricted tools

Runs in an isolated subagent so verbose output stays out of the main conversation. The subagent does not see your conversation, so the skill must stand alone.

```text
.claude/skills/codebase-analysis/SKILL.md     # committed, so every teammate gets the same isolated analysis workflow
```

```yaml
---
name: codebase-analysis
description: Analyse the structure of a module and summarise dependencies. Use when asked how an area of the codebase is organised.
context: fork
agent: Explore
argument-hint: [module-path]
allowed-tools: Read Grep Glob
---

Analyse $ARGUMENTS:

1. Find entry points with Grep
2. Read the files they import
3. Return a summary: purpose, public API, dependencies, risks, with file references
```

### Restrict tools and require arguments

```yaml
---
name: scaffold-component
description: Create a new React component with tests
argument-hint: [ComponentName]
disable-model-invocation: true
allowed-tools: Write Read
---

Create src/components/$ARGUMENTS/$ARGUMENTS.tsx and $ARGUMENTS.test.tsx ...
```

- `allowed-tools` pre-approves tools for the invoking turn; it does not remove others (use `disallowed-tools`).
- `argument-hint` is the autocomplete hint shown when you invoke the skill without arguments.
- `disable-model-invocation: true` stops Claude running it on its own (use for deploys, commits).

### Personal variant without affecting teammates

```text
~/.claude/skills/my-review/SKILL.md      different name from the project's `review`   # a shared name would shadow the team version only on your machine
```

If a personal and a project skill share a name, the personal one wins (`/deploy` runs `~/.claude/skills/deploy`), so use a different name.

### Skill or CLAUDE.md?

| Use | When |
| - | - |
| CLAUDE.md / rules | Universal standards that should always be in context |
| Skill | Task-specific workflow loaded on demand (body loads only when used) |

## How it works

> [!IMPORTANT]
> **Package workflows where their audience finds them, and run them in the context that suits their output.** Scope follows [3.1](3.1-claude-md-hierarchy.md): project files are shared, user files personal. Verbose, exploratory work runs in a fork and returns only a summary.

1. **Share by location.** `.claude/commands/review.md` gives every developer the same `/review`; the same file in `~/.claude/commands/` is personal. Commands and skills are merged, so location matters, not format.
2. **Document input.** `argument-hint` shows the parameter when invoked without arguments; the body reads it via `$ARGUMENTS`. It prompts, it does not validate.
3. **Fork for verbose work.** `context: fork` with `agent: Explore` keeps many file reads and greps out of the main conversation; only the final summary returns.
4. **Make forks self-contained.** The subagent cannot see the conversation, so the body states the whole task, not "continue from above".
5. **Narrow capabilities.** `allowed-tools` pre-approves a few tools but does not remove others and is not a security boundary; `disable-model-invocation: true` keeps side-effecting skills human-triggered.
6. **Rename personal variants.** A same-named personal skill silently wins on your machine, diverging from the team.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| CLAUDE.md rule | Shapes every interaction | Always spends tokens |
| Skill | Tokens spent only when needed | Must be invoked or chosen |
| Forked skill | Protects main context; suits discovery and large analyses | Extra subagent round trip and a lossy summary (ask for file references) |
| Inline skill | Steps can see the conversation | Output fills the main context |
| Broad pre-approval | Convenient | Larger blast radius; keep mutating workflows manual |
| Personal skill | Safe experimentation under a unique name | Promote to the project once teammates should rely on it |

> [!WARNING]
> **Exam traps**
>
> - **"Put the command in `~/.claude/commands/`"** → personal, not shared. Team-wide availability needs a committed project location.
> - **"Define the command in CLAUDE.md"** → CLAUDE.md holds instructions and context, not command definitions.
> - **"Use a `.claude/config.json` commands array"** → does not exist; distractors invent plausible config files or flags.
> - **"Edit the shared skill locally to customise it"** → affects one clone or, if committed, everyone. Create a personal skill with a different name.
> - **"Run the verbose analysis inline and `/compact` afterwards"** → cleanup after the fact. Isolate verbose output with a fork.
> - **"Skills run automatically, so use one for universal standards"** → standards that must always apply belong in always-loaded context.

## Check yourself

<details>
<summary>Every developer should have a <code>/review</code> checklist after pulling the repo. Where does the file go?</summary>

In the project's `.claude/commands/` directory, committed to version control.
</details>

<details>
<summary>A codebase-analysis skill floods the conversation with file contents and the later task loses focus. What addresses the cause?</summary>

Run it with `context: fork` so the exploration happens in an isolated subagent and only a summary returns.
</details>

<details>
<summary>A developer wants a tweaked version of the team's review skill without affecting anyone else. What should they do?</summary>

Create a personal skill under a different name in `~/.claude/skills/`.
</details>
