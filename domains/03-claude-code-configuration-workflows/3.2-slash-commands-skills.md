# 3.2 Create and configure custom slash commands and skills

## Knowledge of

- Project-scoped commands in `.claude/commands/` (shared via version control) vs user-scoped commands in `~/.claude/commands/` (personal).
- Skills in `.claude/skills/` with `SKILL.md` files that support frontmatter configuration including `context: fork`, `allowed-tools`, and `argument-hint`.
- The `context: fork` frontmatter option for running skills in an isolated sub-agent context, preventing skill outputs from polluting the main conversation.
- Personal skill customization: creating personal variants in `~/.claude/skills/` with different names to avoid affecting teammates.

## Skills in

- Creating project-scoped slash commands in `.claude/commands/` for team-wide availability via version control.
- Using `context: fork` to isolate skills that produce verbose output (e.g., codebase analysis) or exploratory context (e.g., brainstorming alternatives) from the main session.
- Configuring `allowed-tools` in skill frontmatter to restrict tool access during skill execution (e.g., limiting to file write operations to prevent destructive actions).
- Using `argument-hint` frontmatter to prompt developers for required parameters when they invoke the skill without arguments.
- Choosing between skills (on-demand invocation for task-specific workflows) and CLAUDE.md (always-loaded universal standards).

## Code snippets

### Project command shared via git

`.claude/commands/review.md` creates `/review` for everyone who clones the repo. Commands were merged into skills, so this and `.claude/skills/review/SKILL.md` behave the same. A personal command goes in `~/.claude/commands/`.

```markdown
---
description: Run the team code review checklist on the current changes
argument-hint: [branch-or-path]
---

Review $ARGUMENTS against our checklist:
1. Error handling on every external call
2. No secrets or credentials in code
3. Tests cover new branches
Report each finding as: location, issue, severity, suggested fix.
```

### Skill with `context: fork` and restricted tools

Runs in an isolated subagent so verbose output stays out of the main conversation. The subagent does not see your conversation, so the skill must stand alone.

```text
.claude/skills/codebase-analysis/SKILL.md
```

```yaml
---
name: codebase-analysis
description: Analyse the structure of a module and summarise dependencies. Use when asked how an area of the codebase is organised.
context: fork
agent: Explore
argument-hint: [module-path]
allowed-tools: Read Grep Glob
---

Analyse $ARGUMENTS:

1. Find entry points with Grep
2. Read the files they import
3. Return a summary: purpose, public API, dependencies, risks, with file references
```

### Restrict tools and require arguments

```yaml
---
name: scaffold-component
description: Create a new React component with tests
argument-hint: [ComponentName]
disable-model-invocation: true
allowed-tools: Write Read
---

Create src/components/$ARGUMENTS/$ARGUMENTS.tsx and $ARGUMENTS.test.tsx ...
```

- `allowed-tools` pre-approves tools for the turn that invokes the skill. It does not remove other tools. To remove tools use `disallowed-tools`.
- `argument-hint` is the autocomplete hint shown when you invoke the skill without arguments.
- `disable-model-invocation: true` stops Claude running it on its own (use for deploys, commits).

### Personal variant without affecting teammates

```text
~/.claude/skills/my-review/SKILL.md      different name from the project's `review`
```

If a personal and a project skill share a name, the personal one wins (`/deploy` runs `~/.claude/skills/deploy`), so use a different name to avoid shadowing.

### Skill or CLAUDE.md?

| Use | When |
| - | - |
| CLAUDE.md / rules | Universal standards that should always be in context |
| Skill | Task-specific workflow loaded on demand (body loads only when used) |
