# 3.2 Create and configure custom slash commands and skills

## At a glance

- Project-scoped commands in `.claude/commands/` (shared via version control) vs user-scoped commands in `~/.claude/commands/` (personal).
- Skills in `.claude/skills/` with `SKILL.md` files that support frontmatter configuration including `context: fork`, `allowed-tools`, and `argument-hint`.
- The `context: fork` frontmatter option for running skills in an isolated sub-agent context, preventing skill outputs from polluting the main conversation.
- Personal skill customization: creating personal variants in `~/.claude/skills/` with different names to avoid affecting teammates.

## Example

### Project command shared via git

`.claude/commands/review.md` creates `/review` for everyone who clones the repo. Commands were merged into skills, so this and `.claude/skills/review/SKILL.md` behave the same. A personal command goes in `~/.claude/commands/`.

```markdown
---
description: Run the team code review checklist on the current changes
argument-hint: [branch-or-path]
---

Review $ARGUMENTS against our checklist:
1. Error handling on every external call
2. No secrets or credentials in code
3. Tests cover new branches
Report each finding as: location, issue, severity, suggested fix.
```

### Skill with `context: fork` and restricted tools

Runs in an isolated subagent so verbose output stays out of the main conversation. The subagent does not see your conversation, so the skill must stand alone.

```text
.claude/skills/codebase-analysis/SKILL.md     # committed, so every teammate gets the same isolated analysis workflow
```

```yaml
---
name: codebase-analysis
description: Analyse the structure of a module and summarise dependencies. Use when asked how an area of the codebase is organised.
context: fork
agent: Explore
argument-hint: [module-path]
allowed-tools: Read Grep Glob
---

Analyse $ARGUMENTS:

1. Find entry points with Grep
2. Read the files they import
3. Return a summary: purpose, public API, dependencies, risks, with file references
```

### Restrict tools and require arguments

```yaml
---
name: scaffold-component
description: Create a new React component with tests
argument-hint: [ComponentName]
disable-model-invocation: true
allowed-tools: Write Read
---

Create src/components/$ARGUMENTS/$ARGUMENTS.tsx and $ARGUMENTS.test.tsx ...
```

- `allowed-tools` pre-approves tools for the turn that invokes the skill. It does not remove other tools. To remove tools use `disallowed-tools`.
- `argument-hint` is the autocomplete hint shown when you invoke the skill without arguments.
- `disable-model-invocation: true` stops Claude running it on its own (use for deploys, commits).

### Personal variant without affecting teammates

```text
~/.claude/skills/my-review/SKILL.md      different name from the project's `review`   # a shared name would shadow the team version only on your machine
```

If a personal and a project skill share a name, the personal one wins (`/deploy` runs `~/.claude/skills/deploy`), so use a different name to avoid shadowing.

### Skill or CLAUDE.md?

| Use | When |
| - | - |
| CLAUDE.md / rules | Universal standards that should always be in context |
| Skill | Task-specific workflow loaded on demand (body loads only when used) |

## Why this matters

Names and flags are illustrative; know the concept, not the exact parameter.

> [!IMPORTANT]
> **The principle**

Reusable workflows should be packaged where their audience can find them, and run in the context that suits their output. Scope follows the same logic as 3.1: project-level files are committed and shared, user-level files are personal. Execution context follows the output: a workflow that produces verbose, exploratory material runs in a forked, isolated context and returns only a summary, so the main conversation stays focused. Capabilities and invocation are then narrowed to what the workflow needs.

**The flow**

- `.claude/commands/review.md` sits in the repository, so cloning or pulling gives every developer the same `/review` and the same checklist. The same file in `~/.claude/commands/` would be a personal command that teammates never see. Commands and skills have been merged, so the exam-relevant point is the location (shared vs personal), not the file format.
- `argument-hint` documents the parameter shown to the developer when the command is invoked without arguments; the body consumes the value through `$ARGUMENTS`. It prompts and documents input; it does not validate it.
- `context: fork` with `agent: Explore` runs the analysis in a separate subagent. A module analysis reads many files and greps repeatedly; without isolation those tool results accumulate in the main conversation and crowd out the actual task. The fork returns only the final summary.
- The forked skill must be self-contained because the subagent does not see the main conversation. The body therefore states the whole task, not "continue from above".
- `allowed-tools` pre-approves a narrow set (read-style tools for analysis, write for scaffolding) for the turn. It reduces permission prompts and signals intent, but it does not remove other tools; removal uses a separate deny list. Treat it as pre-approval, not a security boundary.
- `disable-model-invocation: true` on `scaffold-component` keeps Claude from running a side-effecting skill on its own initiative. Deploys and commits should be human-triggered.
- The personal variant uses a different name. If a personal and a project skill share a name, the personal one wins on that machine, silently diverging from the team's behaviour.
- The skill-vs-CLAUDE.md table captures cost: skill bodies load only when used, while CLAUDE.md content is always in context.

## Trade-offs

- **Skill vs CLAUDE.md:** put a rule in CLAUDE.md when it should shape every interaction; put a multi-step workflow in a skill so its tokens are spent only when needed.
- **Forked vs inline skill:** a fork protects the main context and suits discovery, brainstorming and large analyses; inline suits short workflows whose steps benefit from seeing the conversation, since a fork cannot use it.
- **Fork cost:** a fork adds a subagent round trip and returns a lossy summary; if the details matter, ask for file references in the summary.
- **Pre-approval vs prompting:** broad pre-approval is convenient but increases blast radius; narrow tools suit analysis, while mutating workflows deserve manual invocation.
- **Project vs personal:** promote a personal skill to the project once teammates should rely on it; keep experimental variants personal under unique names.

> [!WARNING]
> **Exam traps**

- "Put the command in `~/.claude/commands/`": personal, not shared through version control. Rule: team-wide availability comes from a committed project location.
- "Define the command in CLAUDE.md": CLAUDE.md holds instructions and context, not command definitions.
- "Use a `.claude/config.json` commands array": a mechanism that does not exist; distractors often invent plausible config files or flags.
- "Edit the shared skill locally to customise it": changes only affect one clone or, if committed, everyone. Rule: create a personal skill with a different name.
- "Run the verbose analysis inline and `/compact` afterwards": cleanup after the fact instead of isolating the work. Rule: isolate verbose output with a fork.
- "Skills run automatically, so use one for universal standards": standards that must always apply belong in always-loaded context, not in a skill that has to be chosen or invoked.

## Quick check

- Every developer should have a `/review` checklist after pulling the repo. Where does the file go? In the project's `.claude/commands/` directory, committed to version control.
- A codebase-analysis skill floods the conversation with file contents and the later task loses focus. What change addresses the cause? Run it with `context: fork` so the exploration happens in an isolated subagent and only a summary returns.
- A developer wants a tweaked version of the team's review skill without affecting anyone else. What should they do? Create a personal skill under a different name in `~/.claude/skills/`.
