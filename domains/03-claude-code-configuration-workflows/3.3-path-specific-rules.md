# 3.3 Apply path-specific rules for conditional convention loading

> [!NOTE]
> **At a glance**
>
> - **Mechanism:** `.claude/rules/` files with a `paths` frontmatter glob load only when matching files are touched.
> - **Benefit:** unrelated work pays no context or token cost.
> - **Versus directory CLAUDE.md:** globs cover conventions that follow a file type across many directories, such as tests.

## Example

### Rule scoped by glob

`paths` is the only frontmatter field Claude Code reads from a rule. The rule loads when Claude reads, writes or edits a matching file.

```markdown
<!-- .claude/rules/api-conventions.md -->
<!-- loads only when matching files are touched, so unrelated work pays no context cost -->
---
paths:
  - "src/api/**/*.ts"
---

# API Development Rules

- All endpoints validate input
- Use the standard error response format
- async/await with try/catch in every handler
```

### Conventions for files spread across the codebase

```markdown
<!-- .claude/rules/testing.md -->
<!-- glob matches the file type, not a directory: tests sit beside their code in dozens of folders -->
---
paths:
  - "**/*.test.tsx"
  - "**/*.test.ts"
---

# Test conventions

- Colocate tests as Component.test.tsx next to Component.tsx
- Use React Testing Library; no snapshot tests
- Arrange / Act / Assert with one behaviour per test
```

```markdown
<!-- .claude/rules/terraform.md -->
---
paths: ["terraform/**/*"]
---

- Pin provider versions; no inline credentials
```

Brace expansion works: `"src/**/*.{ts,tsx}"`.

| Pattern | Matches |
| - | - |
| `**/*.ts` | `.ts` anywhere under the base directory |
| `src/**/*` | everything under `src/` |
| `src/components/*.tsx` | `.tsx` directly in that folder, not subfolders |

### Why not subdirectory CLAUDE.md for this?

A directory-level `CLAUDE.md` is bound to one directory, but `Button.test.tsx` sits beside `Button.tsx` in dozens of them. Only a glob rule applies the same conventions to all, and it loads only on matching files.

### Debug

```bash
claude --debug        # shows a frontmatter parse error; bad YAML loads the rule with no paths, so it applies to everything
```

An `InstructionsLoaded` hook can log which rule files load and why.

## How it works

> [!IMPORTANT]
> **Attach conventions to what they describe.** Pattern-based conventions get a glob rule, single-directory ones a directory file, universal ones always-loaded project context; each applies automatically without paying for unrelated work.

1. **Scope by location.** `paths: ["src/api/**/*.ts"]` keeps handler conventions out of UI editing.
2. **Scope by file type.** `**/*.test.tsx` matches tests wherever they sit: one file to maintain, identical conventions in dozens of directories.
3. **Activate mechanically.** A rule loads when Claude reads, writes or edits a matching file; nothing relies on the model recognising "this looks like a test".
4. **Check pattern reach.** `src/components/*.tsx` misses nested folders, `src/**/*` does not; a too-narrow pattern means the rule silently never loads.
5. **Debug quiet failures.** Invalid frontmatter loads the rule without `paths`; check the frontmatter before rewriting the rule.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Glob rules | Follow file types across the tree; no cost when irrelevant | Overlapping patterns can load together, so keep rules complementary |
| Directory CLAUDE.md ([3.1](3.1-claude-md-hierarchy.md)) | Simple for self-contained package conventions | Bound to one directory |
| Root CLAUDE.md with headers | Easy to find | Always loaded; the model must infer which section applies |
| Skills ([3.2](3.2-slash-commands-skills.md)) | Suit explicit workflows | Invoked or chosen, so poor for conventions needed on every edit |
| Many narrow rules | Precise | Harder to keep consistent |
| Rules generally | Guide generation | Do not guarantee compliance; use a linter or hook for must-hold rules |

> [!WARNING]
> **Exam traps**
>
> - **"Consolidate everything in the root CLAUDE.md under headers"** → relies on inference and loads everything every time. Use automatic scoping when conventions differ by area.
> - **"A CLAUDE.md in each subdirectory"** → cannot cover files scattered across many directories. A glob rule can; a directory file cannot.
> - **"Create a skill per code type"** → skills need invocation or model selection, contradicting automatic application.
> - **"Ask developers to mention the conventions in each prompt"** → manual and inconsistent. Configuration should apply without human action.
> - **"Add a rule file without `paths`"** → loads at launch like project context; the token saving is lost.
> - **"`src/components/*.tsx` for a nested component tree"** → misses subfolders. Use `**` for recursion.

## Check yourself

<details>
<summary>Test files live beside source files in 40 directories and should all follow one style. What is the most maintainable setup?</summary>

One rule file with `paths` globs matching `**/*.test.ts` and `**/*.test.tsx`.
</details>

<details>
<summary>A rule meant only for Terraform files seems to influence unrelated edits. What is the likely cause?</summary>

Its frontmatter failed to parse or lacks `paths`, so it loads unconditionally. Verify with debug output.
</details>

<details>
<summary>API handler conventions apply only to files under one <code>src/api</code> folder. Is a glob rule mandatory?</summary>

No. A directory-level CLAUDE.md also fits a single location; the glob rule is better when files are spread out or defined by type.
</details>
