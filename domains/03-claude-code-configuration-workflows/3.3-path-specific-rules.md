# 3.3 Apply path-specific rules for conditional convention loading

## At a glance

- `.claude/rules/` files with YAML frontmatter `paths` fields containing glob patterns for conditional rule activation.
- Path-scoped rules load only when editing matching files, reducing irrelevant context and token usage.
- The advantage of glob-pattern rules over directory-level CLAUDE.md files for conventions that span multiple directories (e.g., test files spread throughout a codebase).

## Example

### Rule scoped by glob

`paths` is the only frontmatter field Claude Code reads from a rule. The rule loads when Claude reads, writes or edits a matching file.

```markdown
<!-- .claude/rules/api-conventions.md -->
<!-- loads only when matching files are touched, so unrelated work pays no context cost -->
---
paths:
  - "src/api/**/*.ts"
---

# API Development Rules

- All endpoints validate input
- Use the standard error response format
- async/await with try/catch in every handler
```

### Conventions for files spread across the codebase

```markdown
<!-- .claude/rules/testing.md -->
<!-- glob matches the file type, not a directory: tests sit beside their code in dozens of folders -->
---
paths:
  - "**/*.test.tsx"
  - "**/*.test.ts"
---

# Test conventions

- Colocate tests as Component.test.tsx next to Component.tsx
- Use React Testing Library; no snapshot tests
- Arrange / Act / Assert with one behaviour per test
```

```markdown
<!-- .claude/rules/terraform.md -->
---
paths: ["terraform/**/*"]
---

- Pin provider versions; no inline credentials
```

Brace expansion works: `"src/**/*.{ts,tsx}"`.

| Pattern | Matches |
| - | - |
| `**/*.ts` | `.ts` anywhere under the base directory |
| `src/**/*` | everything under `src/` |
| `src/components/*.tsx` | `.tsx` directly in that folder, not subfolders |

### Why not subdirectory CLAUDE.md for this?

A directory-level `CLAUDE.md` is bound to one directory. `Button.test.tsx` sits next to `Button.tsx` in dozens of directories, so only a glob rule applies the same test conventions to all of them. Rules also load only on matching files, which saves tokens.

### Debug

```bash (it then applies to everything)
claude --debug        # shows a frontmatter parse error; bad YAML loads the rule with no paths
```

An `InstructionsLoaded` hook can log which rule files load and why.

## Why this matters

Names and flags are illustrative; know the concept, not the exact parameter.

> [!IMPORTANT]
> **The principle**

Conventions should be attached to what they describe. When a convention follows a file type or path pattern, it should be scoped by pattern and loaded automatically only when matching files are in play. When it follows a single directory, a directory-level file is enough. When it is universal, it belongs in always-loaded project context. Matching the scoping mechanism to the shape of the convention gives deterministic, automatic application without paying context cost for unrelated work.

**The flow**

- `paths: ["src/api/**/*.ts"]` ties the API rules to a location pattern. Editing a React component does not load them, so the model is not given handler conventions while writing UI code.
- `**/*.test.tsx` and `**/*.test.ts` match by file type wherever the file sits. `Button.test.tsx` beside `Button.tsx` in dozens of directories receives identical conventions with one file to maintain. This is the case the exam builds around.
- Activation is mechanical: a rule loads when Claude reads, writes or edits a matching file. Nothing relies on the model recognising "this looks like a test", which is why this is more reliable than headers in a monolithic file.
- The table of patterns exists because the boundary matters: `src/components/*.tsx` does not match nested folders, `src/**/*` does. A pattern that is too narrow silently misses files; the rule never loads and the convention is simply not applied.
- The `--debug` note covers a quiet failure: invalid frontmatter loads the rule without `paths`, so it no longer applies selectively. Misbehaviour from a rule that should be scoped is a prompt to check the frontmatter, not to rewrite the rule.
- The reason for rules over per-directory files is repeated deliberately: a directory file is bound to a directory, so covering test files spread across the tree would mean copying it into every one.

## Trade-offs

- **Glob rules vs directory CLAUDE.md:** globs follow file types across the tree; directory files are simpler when a package has self-contained conventions and everything relevant lives there. Choose by whether the convention is organised by location or by file type.
- **Glob rules vs root CLAUDE.md with headers:** one file is easy to find, but every section is always loaded and the model must infer which applies. Scoped rules cost nothing when irrelevant and apply without inference.
- **Glob rules vs skills:** skills are invoked or chosen, so conventions that must apply automatically on every edit are poorly served by them. Skills suit explicit workflows.
- **Granularity:** many narrow rules are precise but harder to keep consistent; a few broader globs are easier to maintain. Overlapping patterns can load several rules together, so keep rules complementary rather than contradictory.
- **Enforcement:** rules guide generation but do not guarantee compliance; a linter or hook enforces what must hold.

> [!WARNING]
> **Exam traps**

- "Consolidate everything in the root CLAUDE.md under headers": relies on inference and loads everything every time. Rule: use automatic, deterministic scoping when conventions differ by area.
- "A CLAUDE.md in each subdirectory": cannot cover files scattered across many directories, which is the stated condition in the sample question. Rule: a glob-scoped rule can, a directory file cannot.
- "Create a skill per code type": skills need invocation or model selection, contradicting the requirement for automatic application.
- "Ask developers to mention the conventions in each prompt": manual and inconsistent. Rule: configuration should apply without human action.
- "Add a rule file without `paths`": it loads at launch like project context, so it is always present and the token saving is lost.
- A glob like `src/components/*.tsx` for a nested component tree: misses subfolders. Rule: check pattern reach, using `**` for recursion.

## Quick check

- Test files live beside source files in 40 directories and should all follow one style. What is the most maintainable setup? One rule file with `paths` globs matching `**/*.test.ts` and `**/*.test.tsx`.
- A rule meant only for Terraform files seems to influence unrelated edits. What is the likely cause? Its frontmatter failed to parse or lacks `paths`, so it loads unconditionally; verify with debug output.
- API handler conventions apply only to files under one `src/api` folder. Is a glob rule mandatory? No; a directory-level CLAUDE.md also fits a single location, and the glob rule becomes the better choice when the files are spread out or defined by type.
