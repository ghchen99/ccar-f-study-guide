# 3.6 Integrate Claude Code into CI/CD pipelines

## Knowledge of

- The `-p` (or `--print`) flag for running Claude Code in non-interactive mode in automated pipelines.
- `--output-format json` and `--json-schema` CLI flags for enforcing structured output in CI contexts.
- CLAUDE.md as the mechanism for providing project context (testing standards, fixture conventions, review criteria) to CI-invoked Claude Code.
- Session context isolation: the same Claude session that generated code is less effective at reviewing its own changes than an independent review instance.

## Skills in

- Running Claude Code in CI with the `-p` flag to prevent interactive input hangs.
- Using `--output-format json` with `--json-schema` to produce machine-parseable structured findings for automated posting as inline PR comments.
- Including prior review findings in context when re-running reviews after new commits, instructing Claude to report only new or still-unaddressed issues to avoid duplicate comments.
- Providing existing test files in context so test generation avoids suggesting duplicate scenarios already covered by the test suite.
- Documenting testing standards, valuable test criteria, and available fixtures in CLAUDE.md to improve test generation quality and reduce low-value test output.

## Code snippets

### Non-interactive run: `-p`

```bash
claude -p "Analyze this pull request for security issues"      # processes the prompt, prints, exits
# piping gives the model the exact change under review instead of leaving it to find it
git diff origin/main...HEAD | claude -p "Review this diff for security issues"
```

Without `-p` the job waits for interactive input and hangs. `CLAUDE_HEADLESS` and `--batch` do not exist.

### Machine-parseable findings

```bash
# the schema, not prose, guarantees a parseable shape; a downstream script posts the comments
claude -p "Review the staged changes. Report bugs and security issues only." \
  --output-format json \
  --json-schema '{
    "type": "object",
    "properties": {
      "findings": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "file": {"type": "string"},
            "line": {"type": "integer"},
            "severity": {"enum": ["critical", "high", "medium", "low"]},
            "issue": {"type": "string"},
            "suggested_fix": {"type": "string"}
          },
          "required": ["file", "line", "severity", "issue"]
        }
      }
    },
    "required": ["findings"]
  }' | jq '.structured_output.findings'
```

The response carries `structured_output`. If the run ends without valid structured output the field is absent, so check for it before posting inline PR comments.

### Reproducible CI runs

```bash
# --bare skips hooks, skills, MCP, auto memory and CLAUDE.md from the host machine
claude --bare -p "Summarize README.md" --allowedTools "Read"     # needs ANTHROPIC_API_KEY
```

Bare mode skips CLAUDE.md, so if you want the project's review criteria and test standards, do not use it, or pass them with `--append-system-prompt-file`. Without `--bare`, `claude -p` loads the project's CLAUDE.md like an interactive session.

### Pre-approve only what the job needs

```bash
# least privilege: an unattended job should hold only the tools its task needs
claude -p "Run the test suite and fix any failures" --allowedTools "Bash,Read,Edit"
claude -p "..." --permission-mode dontAsk   # deny anything not pre-approved; locked-down CI
```

### Context for CI-invoked Claude lives in CLAUDE.md

```markdown
# Testing standards
- Framework: pytest; fixtures in tests/conftest.py (db_session, fake_clock, api_client)
- A valuable test checks behaviour or an edge case, not a getter
- Skip: trivial property tests, tests duplicating existing coverage

# Review criteria
Report: bugs, security issues. Skip: formatting, naming style, minor local patterns.
```

### Re-review after new commits without duplicate comments

```bash
# prior findings in context stop the same comment being posted again on every push
claude -p "Review this diff. Prior findings are below. Report only NEW issues or ones still unaddressed.

<prior_findings>
$(cat prior_findings.json)
</prior_findings>

$(git diff origin/main...HEAD)" --output-format json --json-schema "$SCHEMA"
```

### Test generation without duplicates

```bash
# naming the existing test file lets the model skip covered scenarios instead of regenerating them
claude -p "Generate tests for src/refunds.py. Existing tests are in tests/test_refunds.py; \
do not repeat scenarios already covered." --allowedTools "Read,Write"
```

### Independent reviewer, not the generating session

Run the review as a separate `claude -p` invocation (a new session with no memory of the generation), not by continuing the session that wrote the code. The generator retains its reasoning context and is less likely to question its own decisions.

```bash
claude -p "Implement the feature in ISSUE.md"            # session A
claude -p "Review the uncommitted changes" --output-format json   # new session B, no --continue/--resume; fresh context can question the author's choices
```

## Commentary: the concepts behind the code

Names and flags are illustrative; know the concept, not the exact parameter.

### The design decision

An automated pipeline has no human to answer prompts, so it must run non-interactively, receive its context from committed configuration, return machine-parseable output and hold only the permissions its job needs. Beyond plumbing, two reliability principles apply: a review should come from an independent session rather than the one that wrote the code, and each run should know what earlier runs already reported so feedback stays actionable rather than repetitive.

### Walk-through

- `-p` runs a single prompt, prints and exits. Without it Claude Code waits for interactive input, and the job hangs indefinitely; the fix addresses the diagnosed cause (an interactive session), not the symptoms. Variables or flags that sound plausible but are not part of the tool do nothing.
- `--output-format json` with `--json-schema` makes findings a data structure (file, line, severity, issue) so a script can post inline PR comments. The schema guarantees shape, not truth: the content can still be wrong. If a run ends without valid structured output the field is absent, so the script must check before posting or the pipeline posts garbage or crashes.
- Review criteria and testing standards live in CLAUDE.md because CI-invoked Claude reads project context like any session. This keeps the criteria versioned with the code and shared by every run. Bare mode skips CLAUDE.md, which is useful for reproducibility but removes exactly this context unless it is passed explicitly.
- Explicit report/skip criteria and a definition of a "valuable test" reduce false positives and low-value output. Vague instructions such as "be thorough" or "only high-confidence findings" do not tell the model what to omit.
- `--allowedTools` and `dontAsk` apply least privilege to an unattended job. No human is present to approve prompts, so anything not pre-approved is denied rather than waiting forever.
- Prior findings in the prompt, with the instruction to report only new or unaddressed issues, prevent duplicate comments on every push. Without them each commit re-reports old problems and developers learn to ignore the bot.
- Existing tests in context prevent the model suggesting scenarios the suite already covers.
- Session B has no `--continue` or `--resume`. The generating session retains its reasoning and is predisposed to defend its choices; a fresh session sees only the output.

### Trade-offs and alternatives

- **Synchronous CLI vs Batches API:** a blocking pre-merge check needs an immediate result, so it uses the synchronous path; batches trade latency (no guaranteed turnaround) for cost and suit non-blocking work such as nightly reports (see 4.5).
- **Bare mode vs project context:** bare mode gives reproducible runs independent of the host machine, but loses CLAUDE.md; choose it for generic tasks and the normal mode when project criteria matter.
- **Structured output vs free text:** structure enables automation but costs schema design and validation handling; free text is fine when a human reads the result.
- **Fresh reviewer vs same-session review:** a second session costs another run but gives independent scrutiny. A self-review in the generating session is cheaper and systematically weaker.
- **Single pass vs per-file plus integration pass:** for large PRs, focused passes keep depth consistent at the cost of more calls (see 4.6).
- **Permissions:** broader tool access makes fixes possible but enlarges the blast radius of mistakes or prompt injection through code under review; review jobs rarely need write tools.

### Exam traps

- "Set `CLAUDE_HEADLESS=true`" or "add `--batch`": non-existent features. Rule: the documented non-interactive mechanism is `-p`.
- "Redirect stdin from `/dev/null`": a Unix workaround that does not address how Claude Code is invoked.
- "Have the same session that wrote the code review it": it keeps its own reasoning context and is less likely to question itself. Rule: use an independent session; never rely on a model's self-review as the only check of its own output.
- "Re-run the review on every commit with no memory of earlier results": produces duplicate comments. Rule: supply prior findings and ask for new or unaddressed issues only.
- "Put the review criteria in the prompt of each pipeline script": duplicates configuration; CLAUDE.md keeps context versioned and shared.
- "Parse the model's prose with regexes": fragile; use schema-constrained output.
- "Switch the blocking check to batches to save 50%": no latency guarantee; unacceptable for a blocking workflow (sample question 11, answer A).
- "Raise the confidence threshold to cut false positives": a number is not a criterion; specify categories to report and skip.

### Check yourself

- A pipeline step running `claude "Analyze this PR"` never finishes. What is wrong and how is it fixed? Claude Code is waiting for interactive input; run it non-interactively with `-p`.
- A bot repeats the same ten comments after every push. What change is needed? Pass the prior findings into the prompt and instruct Claude to report only new or still-unaddressed issues.
- A team wants the code generator to double-check its own output in the same session to save cost. Why is this weak? The session retains its generation reasoning and is biased towards its decisions; an independent session reviews more effectively.
