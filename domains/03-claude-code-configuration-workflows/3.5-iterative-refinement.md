# 3.5 Apply iterative refinement techniques for progressive improvement

## Knowledge of

- Concrete input/output examples as the most effective way to communicate expected transformations when prose descriptions are interpreted inconsistently.
- Test-driven iteration: writing test suites first, then iterating by sharing test failures to guide progressive improvement.
- The interview pattern: having Claude ask questions to surface considerations the developer may not have anticipated before implementing.
- When to provide all issues in a single message (interacting problems) versus fixing them sequentially (independent problems).

## Skills in

- Providing 2-3 concrete input/output examples to clarify transformation requirements when natural language descriptions produce inconsistent results.
- Writing test suites covering expected behavior, edge cases, and performance requirements before implementation, then iterating by sharing test failures.
- Using the interview pattern to surface design considerations (e.g., cache invalidation strategies, failure modes) before implementing solutions in unfamiliar domains.
- Providing specific test cases with example input and expected output to fix edge case handling (e.g., null values in migration scripts).
- Addressing multiple interacting issues in a single detailed message when fixes interact, versus sequential iteration for independent issues.

## Code snippets

These are prompt patterns rather than API code.

### Concrete input/output examples when prose is read inconsistently

```text
Transform legacy log lines into structured records. Examples:

Input:  "2026-03-04 12:01:55 ERR payment timeout order=8841"
Output: {"ts": "2026-03-04T12:01:55Z", "level": "error", "event": "payment_timeout", "order_id": 8841}

Input:  "2026-03-04 12:02:10 WARN retry 2/3 order=8841"
Output: {"ts": "2026-03-04T12:02:10Z", "level": "warning", "event": "retry", "order_id": 8841, "attempt": 2}

Input:  "2026-03-04 12:03:00 INFO started"
Output: {"ts": "2026-03-04T12:03:00Z", "level": "info", "event": "started", "order_id": null}
```

Two or three examples, including the awkward case (missing field, null).

### Test-driven iteration

```text
1. "Write tests for parse_duration(): '90s' -> 90, '2m' -> 120, '1h30m' -> 5400,
    '' -> ValueError, '10x' -> ValueError, None -> ValueError. Don't implement yet."
2. "Now implement it so these pass."
3. Paste the failing output back: "These 2 tests fail: <output>. Fix."
```

Cover expected behaviour, edge cases and performance requirements before implementing.

### Interview pattern in an unfamiliar domain

```text
I need a cache for product lookups. Before implementing, interview me: ask about
invalidation strategy, failure modes (what if the cache is down?), consistency needs,
TTLs and memory limits. Ask one group of questions at a time.
```

### One message vs sequential

| Situation | Approach |
| - | - |
| Problems interact (fixing the schema changes the migration and the serializer) | One detailed message with all of them |
| Problems are independent (a typo, an unrelated flaky test) | Fix sequentially |

### Edge case with a specific test case

```text
The migration crashes on null values. Add this case and make it pass:
  input:    {"id": 7, "email": null}
  expected: {"id": 7, "email": ""}  # null email becomes empty string, row is kept
```

## Commentary: the concepts behind the code

Names and flags are illustrative; know the concept, not the exact parameter. The snippets are prompts, so the reasoning is given here rather than inline.

### The design decision

Improvement converges fastest when feedback is concrete and checkable. Examples and tests turn an ambiguous description into something the model can match or fail against; an interview surfaces requirements before they become rework; and the way problems are batched into messages should reflect whether they interact. The principle: replace interpretation with evidence wherever possible.

### Walk-through

- **Input/output examples:** prose such as "structured records" admits many readings (field names, casing, how absent values appear). Three examples fix the mapping, and the third, with a missing field and a `null`, pins down the awkward case that prose would leave open. Two or three varied examples are enough; more add cost and risk over-fitting to their incidental features.
- **Tests first:** the tests encode expected behaviour, edge cases (`''`, `'10x'`, `None`) and, where relevant, performance before any implementation exists. "Don't implement yet" separates specification from solution, so the tests are not shaped around code already written.
- **Failure output as feedback:** pasting the failing output gives the model an objective, specific signal instead of "it's still wrong". Each iteration narrows the gap and the loop ends when the tests pass, a condition that does not depend on judgement.
- **Interview pattern:** in an unfamiliar domain the developer does not know which questions matter (invalidation, behaviour when the cache is down, consistency needs, TTLs). Having Claude ask surfaces considerations that would otherwise appear as production bugs. Asking one group at a time keeps the exchange manageable.
- **One message vs sequential:** when fixing the schema changes the migration and the serializer, sequential fixes can undo each other, so the interacting problems are described together and solved as a whole. Independent problems (a typo, an unrelated flaky test) are cleaner as separate steps with separate verification.
- **Edge-case test case:** giving the exact input and expected output for the null email removes the ambiguity about what "handle nulls" means. Here the expectation also records a decision (keep the row, use an empty string), which prose could leave unstated.

### Trade-offs and alternatives

- **Examples vs more detailed prose:** examples are shorter and less ambiguous for transformations; prose is better for rules and rationale. Use both when the rule has exceptions the examples cannot show.
- **Tests first vs examples only:** tests are executable and repeatable, so they suit logic with many edge cases; examples suit formatting-style transformations. Tests need effort to write and are only as good as their coverage.
- **Interview vs specifying upfront:** an interview costs a round of conversation but is cheaper than rebuilding a design; when the domain is familiar and requirements are clear, it is unnecessary.
- **Batching vs sequencing:** one message for interacting issues avoids oscillation; one long message of unrelated issues dilutes attention and makes it harder to tell which change fixed what.
- **Iteration limits:** if repeated rounds do not converge, the specification (tests or examples) is usually the problem; clarify it rather than repeating the same request.

### Exam traps

- "Describe the transformation in more detail in prose" when results are inconsistent: the diagnosed problem is interpretation, and concrete input/output examples remove it. Rule: when prose is read inconsistently, show examples.
- "Implement first, then write tests to match": tests written after the code tend to confirm what it does rather than what was needed.
- "Fix one issue per message always": ignores that interacting fixes conflict. Rule: interacting problems go in one message, independent ones sequentially.
- "Put everything in one message always": loses the clean verification of independent fixes.
- "Just tell the model to be careful with nulls": vague instruction. Rule: give a specific failing case with input and expected output.
- "Start coding the cache straight away and adjust": in an unfamiliar domain the unknown unknowns are the risk. Rule: use the interview pattern to surface them first.
- "Ask the model whether its own result is correct": self-assessment is weaker than a test result; an executable check gives independent evidence.

### Check yourself

- A log-conversion prompt yields different field names on different runs. What is the most direct fix? Add two or three concrete input/output examples, including an edge case such as a missing field.
- Changing a database schema breaks the migration script and the API serializer at once. Separate messages or one? One message describing all three, because the fixes interact.
- A developer is building something in a domain they do not know. How can the design gaps be found before coding? Ask Claude to interview them about failure modes, consistency and limits before implementing.
