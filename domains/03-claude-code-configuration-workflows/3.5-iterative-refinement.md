# 3.5 Apply iterative refinement techniques for progressive improvement

> [!NOTE]
> **At a glance**
>
> - **Examples:** concrete input/output pairs beat prose when descriptions are interpreted inconsistently.
> - **Tests first:** write the suite, then iterate by sharing failures.
> - **Interview:** have Claude ask questions to surface considerations you have not anticipated.
> - **Batching:** interacting problems go in one message; independent ones are fixed sequentially.

## Example

These are prompt patterns rather than API code.

### Concrete input/output examples when prose is read inconsistently

```text
Transform legacy log lines into structured records. Examples:

Input:  "2026-03-04 12:01:55 ERR payment timeout order=8841"
Output: {"ts": "2026-03-04T12:01:55Z", "level": "error", "event": "payment_timeout", "order_id": 8841}

Input:  "2026-03-04 12:02:10 WARN retry 2/3 order=8841"
Output: {"ts": "2026-03-04T12:02:10Z", "level": "warning", "event": "retry", "order_id": 8841, "attempt": 2}

Input:  "2026-03-04 12:03:00 INFO started"
Output: {"ts": "2026-03-04T12:03:00Z", "level": "info", "event": "started", "order_id": null}
```

Two or three examples, including the awkward case (missing field, null).

### Test-driven iteration

```text
1. "Write tests for parse_duration(): '90s' -> 90, '2m' -> 120, '1h30m' -> 5400,
    '' -> ValueError, '10x' -> ValueError, None -> ValueError. Don't implement yet."
2. "Now implement it so these pass."
3. Paste the failing output back: "These 2 tests fail: <output>. Fix."
```

Cover expected behaviour, edge cases and performance requirements before implementing.

### Interview pattern in an unfamiliar domain

```text
I need a cache for product lookups. Before implementing, interview me: ask about
invalidation strategy, failure modes (what if the cache is down?), consistency needs,
TTLs and memory limits. Ask one group of questions at a time.
```

### One message vs sequential

| Situation | Approach |
| - | - |
| Problems interact (fixing the schema changes the migration and the serializer) | One detailed message with all of them |
| Problems are independent (a typo, an unrelated flaky test) | Fix sequentially |

### Edge case with a specific test case

```text
The migration crashes on null values. Add this case and make it pass:
  input:    {"id": 7, "email": null}
  expected: {"id": 7, "email": ""}  # null email becomes empty string, row is kept
```

## How it works

> [!IMPORTANT]
> **Replace interpretation with evidence.** Examples and tests give the model something to match or fail against, an interview surfaces requirements before they become rework, and batching should reflect whether problems interact.

1. **Pin the mapping with examples.** "Structured records" admits many readings; two or three varied examples, including a missing field or `null`, fix it. More add cost and risk over-fitting.
2. **Write tests first.** They encode behaviour, edge cases (`''`, `'10x'`, `None`) and performance; "Don't implement yet" keeps specification separate from solution.
3. **Feed back failure output.** Pasted failures are an objective signal, not "it's still wrong"; the loop ends when tests pass, independent of judgement.
4. **Interview in unfamiliar domains.** You do not know which questions matter (invalidation, cache-down behaviour, TTLs); asking one group at a time surfaces what would otherwise be production bugs.
5. **Batch by interaction.** Interacting fixes (schema, migration, serializer) can undo each other sequentially; independent ones (a typo, a flaky test) stay separate for clean verification.
6. **Pin edge cases exactly.** Input plus expected output removes ambiguity in "handle nulls" and records the decision (keep the row, use an empty string).

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Examples | Short and unambiguous for transformations | Cannot show rules or rationale; add prose when there are exceptions |
| Tests first | Executable and repeatable for logic with many edge cases | Effort to write; only as good as coverage |
| Interview | Cheaper than rebuilding a design | A round of conversation; unnecessary when requirements are clear |
| One message for interacting issues | Avoids oscillation | Unrelated issues in one long message dilute attention |
| Sequential fixes | Clear verification of what fixed what | Interacting fixes can conflict |

If repeated rounds do not converge, the specification (tests or examples) is usually the problem; clarify it rather than repeating the request.

> [!WARNING]
> **Exam traps**
>
> - **"Describe the transformation in more detail in prose"** → the problem is interpretation. When prose is read inconsistently, show examples.
> - **"Implement first, then write tests to match"** → tests written after code confirm what it does, not what was needed.
> - **"Fix one issue per message always"** → interacting fixes conflict. Interacting problems go together, independent ones sequentially.
> - **"Put everything in one message always"** → loses clean verification of independent fixes.
> - **"Just tell the model to be careful with nulls"** → vague. Give a failing case with input and expected output.
> - **"Start coding the cache straight away and adjust"** → unknown unknowns are the risk. Interview first.
> - **"Ask the model whether its own result is correct"** → weaker than a test; an executable check is independent evidence.

<summary>A log-conversion prompt yields different field names on different runs. What is the most direct fix?</summary>

</details>

<details>

One message describing all three, because the fixes interact.
</details>
