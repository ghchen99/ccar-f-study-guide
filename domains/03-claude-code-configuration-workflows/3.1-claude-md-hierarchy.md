# 3.1 Configure CLAUDE.md files with appropriate hierarchy, scoping, and modular organization

> [!NOTE]
> **At a glance**
>
> - **Hierarchy:** user (`~/.claude/CLAUDE.md`), project (root or `.claude/CLAUDE.md`), directory (subfolder `CLAUDE.md`).
> - **Sharing:** only committed files reach teammates; user-level instructions never do.
> - **Modularity:** `@import` organises long files; `.claude/rules/` splits topics.

## Example

### Where each file lives and who gets it

```text
~/.claude/CLAUDE.md          user-level: only you, all projects, NOT shared via git
~/.claude/rules/*.md         user-level rules
<repo>/CLAUDE.md             project-level (or <repo>/.claude/CLAUDE.md): team, via git
<repo>/CLAUDE.local.md       personal, this project, gitignored
<repo>/.claude/rules/*.md    project rules (topic files, optionally path-scoped)
<repo>/packages/api/CLAUDE.md   directory-level: loads on demand when Claude reads/edits a file there
```

All discovered files are concatenated, not overridden; files from the filesystem root down to the working directory load at launch, closer ones later.

**"The new teammate doesn't get the instructions":** the rules sit in `~/.claude/CLAUDE.md` (never committed). Move them to the project `CLAUDE.md`.

### Project CLAUDE.md with `@import`

```markdown
# Project standards

See @README for the project overview and @package.json for npm scripts.

## Conventions
- Use 2-space indentation
- Run `npm test` before committing
- API handlers live in `src/api/handlers/`

@docs/git-instructions.md
```

Imports expand recursively (max four hops) and load with the importing file, so they organise but do not cut context cost. Relative paths resolve from the importing file; wrap a path in backticks to mention it without importing it.

Per-package standards, each pulling in only what that package needs:

```markdown
<!-- packages/billing/CLAUDE.md -->
<!-- directory-level: loads only when work touches this package, so other packages do not pay for payments rules -->
@../../docs/standards/typescript.md
@../../docs/standards/payments-compliance.md
```

### Split a monolith into rules

```text
.claude/
├── CLAUDE.md                  # short index of universal standards
└── rules/                     # one topic per file: easier to review, own and prune than one long file
    ├── testing.md
    ├── api-conventions.md
    └── deployment.md
```

Rules without `paths` frontmatter load at launch like `.claude/CLAUDE.md`. Add `paths` to load them conditionally ([3.3](3.3-path-specific-rules.md)).

### Verify what is loaded

```text
/memory          list CLAUDE.md / CLAUDE.local.md / rules locations, toggle auto memory   # first step when sessions or teammates behave differently
/context all     check the "Memory files" list
/init            generate a starting CLAUDE.md
```

Aim for under 200 lines per file and concrete, checkable instructions ("Use 2-space indentation", not "format code properly"). CLAUDE.md is context, not enforcement: for a rule that must always hold, use a hook.

## How it works

> [!IMPORTANT]
> **Scope configuration to the audience that needs it.** Scope decides both who receives an instruction and when it costs context; the wrong level hides it from those who need it or loads it where it is irrelevant.

1. **Match file to audience.** Only committed files reach a teammate who clones; `~/.claude/CLAUDE.md` lives on one machine, so rules written there never travel.
2. **Expect concatenation, not precedence.** User, project and directory files all apply; conflicts are settled by the model weighing contradictory text, so contradictions give inconsistent behaviour.
3. **Import for organisation, not cost.** Imports load with the importing file; only content that does not load at all (directory-level files, path-scoped rules) saves context.
4. **Import per package.** `packages/billing/CLAUDE.md` pulls in only its two standards; loading every standard everywhere dilutes attention.
5. **Split rules for ownership.** Unscoped `.claude/rules/` files behave like the project file; the gain is review and ownership (a security owner edits `deployment.md`), not smaller context.
6. **Verify, and know the limit.** `/memory` and `/context all` show what loaded, so check that before rewording prompts. Instructions are advisory context, never a guarantee.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Monolithic CLAUDE.md | Easy to discover | Grows until lines get unequal attention |
| Split `.claude/rules/` files | Short, topic-focused, easy to own | More files to find |
| Directory-level CLAUDE.md | Fits one package or service | Cannot follow a file type across directories ([3.3](3.3-path-specific-rules.md)) |
| Project file vs `CLAUDE.local.md` | Project file shares standards; local keeps personal URLs and experiments out of team context | Local content is invisible to the team |
| `@import` | One source of truth across packages | No context saving |
| Inlining | Self-contained | Duplicated text drifts |
| CLAUDE.md vs hook | CLAUDE.md is cheap and flexible | Probabilistic; hooks are deterministic but need code, so reserve them for must-never-happen rules |

> [!WARNING]
> **Exam traps**
>
> - **"Add the standards to `~/.claude/CLAUDE.md`"** → not shared via version control. Team instructions belong in a committed, project-scoped file.
> - **"Put a CLAUDE.md in every directory"** → duplicates content and fails for conventions that follow a file type, not a location.
> - **"Tell each developer to paste the rules into their own config"** → manual and drifts. Distribute through the repository.
> - **"Use `@import` to cut token usage"** → imports expand in place; they organise, they do not save context.
> - **"Repeat it in capitals so it is always followed"** → emphasis is not enforcement. Guaranteed behaviour needs a hook.
> - **"Behaviour differs between sessions, so rewrite the prompt"** → diagnose first with `/memory` to see which files loaded.

## Check yourself

<details>
<summary>A new hire's Claude Code ignores the team's API conventions while everyone else's follows them. Where do you look first?</summary>

Whether the conventions live in a user-level file on the other developers' machines. Move them to the committed project file.
</details>

<details>
<summary>A monorepo's <code>billing</code> package needs payments-compliance rules that <code>docs-site</code> must not load. What structure fits?</summary>

A directory-level CLAUDE.md in `billing` that imports only the relevant standards.
</details>

<details>
<summary>A team wants a rule that can never be violated. Is CLAUDE.md enough?</summary>

No. CLAUDE.md guides behaviour probabilistically; a hook gives deterministic enforcement.
</details>
