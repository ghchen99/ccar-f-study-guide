# 3.1 Configure CLAUDE.md files with appropriate hierarchy, scoping, and modular organization

## Knowledge of

- The CLAUDE.md configuration hierarchy: user-level (`~/.claude/CLAUDE.md`), project-level (`.claude/CLAUDE.md` or root `CLAUDE.md`), and directory-level (subdirectory `CLAUDE.md` files).
- User-level settings apply only to that user: instructions in `~/.claude/CLAUDE.md` are not shared with teammates via version control.
- The `@import` syntax for referencing external files to keep CLAUDE.md modular (e.g., importing specific standards files relevant to each package).
- `.claude/rules/` directory for organizing topic-specific rule files as an alternative to a monolithic CLAUDE.md.

## Skills in

- Diagnosing configuration hierarchy issues (e.g., a new team member not receiving instructions because they're in user-level rather than project-level configuration).
- Using `@import` to selectively include relevant standards files in each package's CLAUDE.md based on maintainer domain knowledge.
- Splitting large CLAUDE.md files into focused topic-specific files in `.claude/rules/` (e.g., `testing.md`, `api-conventions.md`, `deployment.md`).
- Using the `/memory` command to verify which memory files are loaded and diagnose inconsistent behavior across sessions.

## Code snippets

### Where each file lives and who gets it

```text
~/.claude/CLAUDE.md          user-level: only you, all projects, NOT shared via git
~/.claude/rules/*.md         user-level rules
<repo>/CLAUDE.md             project-level (or <repo>/.claude/CLAUDE.md): team, via git
<repo>/CLAUDE.local.md       personal, this project, gitignored
<repo>/.claude/rules/*.md    project rules (topic files, optionally path-scoped)
<repo>/packages/api/CLAUDE.md   directory-level: loads on demand when Claude reads/edits a file there
```

All discovered files are concatenated rather than overriding each other; files from the filesystem root down to the working directory load at launch, closer ones later.

**Diagnosing "the new teammate doesn't get the instructions":** the rules were written in `~/.claude/CLAUDE.md` (user-level, never committed). Move them to the project `CLAUDE.md` and commit.

### Project CLAUDE.md with `@import`

```markdown
# Project standards

See @README for the project overview and @package.json for npm scripts.

## Conventions
- Use 2-space indentation
- Run `npm test` before committing
- API handlers live in `src/api/handlers/`

@docs/git-instructions.md
```

Imports expand recursively (max four hops) and load with the importing file, so they organise a long file but do not reduce its context cost. Relative paths resolve from the file containing the import. Wrap a path in backticks to mention it without importing it.

Per-package standards, each pulling in only what that package needs:

```markdown
<!-- packages/billing/CLAUDE.md -->
<!-- directory-level: loads only when work touches this package, so other packages do not pay for payments rules -->
@../../docs/standards/typescript.md
@../../docs/standards/payments-compliance.md
```

### Split a monolith into rules

```text
.claude/
├── CLAUDE.md                  # short index of universal standards
└── rules/                     # one topic per file: easier to review, own and prune than one long file
    ├── testing.md
    ├── api-conventions.md
    └── deployment.md
```

Rules without `paths` frontmatter load at launch like `.claude/CLAUDE.md`. Add `paths` to load them conditionally (see 3.3).

### Verify what is loaded

```text
/memory          list CLAUDE.md / CLAUDE.local.md / rules locations, toggle auto memory   # first step when sessions or teammates behave differently
/context all     check the "Memory files" list
/init            generate a starting CLAUDE.md
```

Aim for under 200 lines per file and concrete, checkable instructions ("Use 2-space indentation", not "format code properly"). CLAUDE.md is context, not enforcement: for a rule that must always hold, use a hook.

## Commentary: the concepts behind the code

Names and flags are illustrative; know the concept, not the exact parameter.

### The design decision

Configuration should be scoped to the audience that needs it: the individual (user level), the whole team (project level, committed), one person on one project (local, gitignored), or one part of the codebase (directory level or path-scoped rules). Scope decides two things at once: who receives the instruction and when it costs context. Putting an instruction at the wrong level either hides it from the people who need it or loads it for work where it is irrelevant.

### Walk-through

- The location table maps each file to its audience. Only files committed to the repository reach a teammate who clones it; `~/.claude/CLAUDE.md` exists only on one machine. This is the diagnosis for "the new teammate does not get the instructions": the rules were written at user level and never travelled through version control.
- Files are concatenated rather than overriding each other, so user, project and directory instructions all apply together. A conflict is therefore resolved by the model weighing contradictory text, not by a precedence rule, which is why contradictory instructions across levels produce inconsistent behaviour.
- `@import` in the project file splits a long file into topic documents that humans can maintain separately. Imports load with the importing file, so they improve organisation but not context cost; the only way to avoid cost is for the content not to load at all (directory-level files, path-scoped rules).
- `packages/billing/CLAUDE.md` imports only the two standards that package needs. A maintainer who knows the domain chooses the imports; loading every standard everywhere would dilute attention with irrelevant rules.
- Rules in `.claude/rules/` without `paths` behave like the project file but with one topic per file. The gain is review and ownership (a security owner edits `deployment.md` without touching test conventions), not a smaller context.
- `/memory` and `/context all` show what is actually loaded. When two sessions behave differently, the first check is which files each one loaded, not the prompt wording.
- The note about hooks marks the limit of the mechanism: instructions are advisory context that the model usually follows, never a guarantee.

### Trade-offs and alternatives

- **One monolithic CLAUDE.md vs split files:** a single file is easy to discover but grows past the point where every line is read with equal weight; concrete, short, topic-focused files stay maintainable. Aim for brevity and checkable statements.
- **Directory-level CLAUDE.md vs path-scoped rules:** directory files suit conventions tied to one package or service; they cannot follow a file type across many directories (see 3.3).
- **Project vs `CLAUDE.local.md`:** shared standards belong in the committed file; personal sandbox URLs, preferences or experiments belong in the local file so they do not leak into the team's context.
- **`@import` vs inlining:** imports keep a single source of truth for standards reused by several packages; inlining duplicates text that drifts.
- **CLAUDE.md vs hook:** CLAUDE.md is cheap and flexible but probabilistic; a hook is deterministic but needs code. Use CLAUDE.md for conventions and style, hooks for must-never-happen rules.

### Exam traps

- "Add the standards to `~/.claude/CLAUDE.md`": not shared via version control, so teammates never receive them. Rule: instructions for the team must live in a committed, project-scoped file.
- "Put a CLAUDE.md in every directory": duplicates content and fails for conventions that follow a file type rather than a location.
- "Tell each developer to paste the rules into their own config": relies on manual action and drifts. Rule: distribute through the repository.
- "Use `@import` to cut token usage": imports expand in place and load with the importing file; they organise, they do not save context.
- "Make the instruction stronger or repeat it in capitals so it is always followed": emphasis does not convert context into enforcement. Rule: guaranteed behaviour needs a hook, not louder wording.
- "Behaviour differs between sessions, so rewrite the prompt": diagnose first with `/memory` to see which files loaded.

### Check yourself

- A new hire's Claude Code ignores the team's API conventions while everyone else's follows them. Where do you look first? At whether the conventions live in a user-level file on the other developers' machines; move them to the committed project file.
- A monorepo's `billing` package needs payments-compliance rules that `docs-site` must not load. What structure fits? A directory-level CLAUDE.md in `billing` that imports only the relevant standards.
- A team wants a rule that can never be violated. Is CLAUDE.md enough? No; CLAUDE.md guides behaviour probabilistically, and a hook is needed for deterministic enforcement.
