# 3.4 Determine when to use plan mode vs direct execution

> [!NOTE]
> **At a glance**
>
> - **Plan mode:** complex, multi-file, architectural or multi-approach work; explore and design before editing to avoid costly rework.
> - **Direct execution:** simple, well-scoped changes, such as one validation check in one function.
> - **Explore subagent:** isolates verbose discovery and returns a summary, preserving main context.

## Example

### Decide by task shape

| Task | Mode | Why |
| - | - | - |
| Monolith to microservices, dozens of files, service boundaries to decide | Plan | Architectural, multi-file, several valid approaches |
| Library migration touching 45+ files | Plan, then execute | Explore and design before editing |
| Choose between integration approaches with different infrastructure needs | Plan | Decision comes before code |
| Single-file bug fix with a clear stack trace | Direct | Well-scoped |
| Add a date validation conditional to one function | Direct | Trivial scope |

Complexity stated in the requirements is a reason to start in plan mode, not to wait and see if it emerges.

### Starting in plan mode

```bash
claude --permission-mode plan            # explore and propose; edits need approval
```

```python
from claude_agent_sdk import ClaudeAgentOptions

# SDK: Claude explores and plans; file edits go to your can_use_tool callback
ClaudeAgentOptions(permission_mode="plan")
```

Plan, then switch to direct execution to implement the approved plan.

### Keep verbose discovery out of the main context

Delegate to the read-only Explore subagent so only a summary returns.

```yaml
---
name: map-auth
description: Map where authentication is implemented
context: fork
agent: Explore
---

Find every place authentication is implemented in this repo. Return a short summary
with file references, not the files' contents.
```

Or ask in the prompt: `Use the Explore subagent to find all callers of process_refund and summarise.` Built-in agent options for `agent:` are `Explore`, `Plan` and `general-purpose`.

### Plan for investigation, direct for implementation

```text
1. (plan mode)    "Investigate how to migrate from lib-a to lib-b. List affected files,
                   breaking API differences, and a step order."      # wrong boundaries are cheapest to catch here, before any edit
2. Review and approve the plan.                                      # human checkpoint on the design, not on 45 diffs
3. (direct)       "Execute step 1 of the plan."                      # scoped, well-understood steps need no further exploration
```

## How it works

> [!IMPORTANT]
> **Match upfront thinking to the cost of being wrong.** Architectural, many-file or multi-design tasks risk a wrong structure found late, so explore and design first; for small, well-understood tasks planning is overhead. Isolate bulky discovery output either way.

1. **Read the task shape.** Scale, ambiguity and architectural consequence point to plan mode; a clear stack trace in one file points to direct.
2. **Make wrong turns cheap.** Plan mode reads and reasons without editing, so rejecting a plan costs minutes; reverting 45 half-migrated files costs far more.
3. **Start in plan mode when complexity is stated.** Starting directly bakes structural assumptions into edits, and the rework is what the plan would have avoided.
4. **Fork discovery.** The Explore skill with `context: fork` returns a short summary with file references instead of consuming the window ([3.2](3.2-slash-commands-skills.md)).
5. **Hand off between phases.** Investigate in plan mode, review the design, then execute step by step directly; they are phases of one task.
6. **Mirror it in the SDK.** `permission_mode="plan"` allows exploration while mutations go through an approval path.

## Trade-offs

| Choice | Strength | Cost |
| --- | --- | --- |
| Plan first | Pays off when structure is uncertain or changes hard to reverse | Upfront time; pure delay on a single-file fix |
| Iterate directly | Fast for small changes | Dependencies discovered after they are broken |
| Detailed upfront instructions | Works when the design is known and validated | Presumes the answer; otherwise exploration should produce it |
| Explore subagent | Saves context | Summary may omit details |
| Inline exploration | Full fidelity | Uses window space; isolate discovery whose raw output is not needed later |
| One large plan | Single design view | Goes stale; re-plan between phases, and review before approving |

> [!WARNING]
> **Exam traps**
>
> - **"Start with direct execution and let the implementation reveal the boundaries"** → rework risk peaks with many files and design choices. Start architectural work with exploration and design.
> - **"Write comprehensive upfront instructions for each service and execute directly"** → assumes the right structure without examining the code.
> - **"Begin directly and switch to plan mode if complexity appears"** → the complexity was already stated; waiting defeats the point of planning.
> - **"Use plan mode for everything to be safe"** → over-applies the tool. A single-file bug with a clear stack trace is direct.
> - **"Read all files in the main conversation to understand the codebase"** → exhausts context in multi-phase tasks. Isolate discovery in an Explore subagent.
> - **"Plan mode and direct execution are mutually exclusive for a task"** → the stated pattern plans for investigation and goes direct for implementation.

## Check yourself

<details>
<summary>A teammate must replace a library used in 45 files, with API differences between versions. How should the work be structured?</summary>

Plan mode to investigate affected files, breaking differences and order, then direct execution of the approved plan step by step.
</details>

<details>
<summary>A stack trace points at a null dereference on one line of one function. Plan mode or direct?</summary>

Direct. The scope is clear, and planning adds overhead without reducing risk.
</details>

<details>
<summary>Mapping every caller of a function would print hundreds of lines and the session is long. What helps?</summary>

Delegate the discovery to the Explore subagent so only a summary with file references returns to the main context.
