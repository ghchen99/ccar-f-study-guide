# 3.4 Determine when to use plan mode vs direct execution

## At a glance

- Plan mode is designed for complex tasks involving large-scale changes, multiple valid approaches, architectural decisions, and multi-file modifications.
- Direct execution is appropriate for simple, well-scoped changes (e.g., adding a single validation check to one function).
- Plan mode enables safe codebase exploration and design before committing to changes, preventing costly rework.
- The Explore subagent for isolating verbose discovery output and returning summaries to preserve main conversation context.

## Example

### Decide by task shape

| Task | Mode | Why |
| - | - | - |
| Monolith to microservices, dozens of files, service boundaries to decide | Plan | Architectural, multi-file, several valid approaches |
| Library migration touching 45+ files | Plan, then execute | Explore and design before editing |
| Choose between integration approaches with different infrastructure needs | Plan | Decision comes before code |
| Single-file bug fix with a clear stack trace | Direct | Well-scoped |
| Add a date validation conditional to one function | Direct | Trivial scope |

Complexity stated in the requirements is a reason to start in plan mode, not to wait and see if it emerges.

### Starting in plan mode

```bash
claude --permission-mode plan            # explore and propose; edits need approval
```

```python
from claude_agent_sdk import ClaudeAgentOptions

# SDK: Claude explores and plans; file edits go to your can_use_tool callback
ClaudeAgentOptions(permission_mode="plan")
```

Plan, then switch to direct execution to implement the approved plan.

### Keep verbose discovery out of the main context

Delegate to the read-only Explore subagent so only a summary returns.

```yaml
---
name: map-auth
description: Map where authentication is implemented
context: fork
agent: Explore
---

Find every place authentication is implemented in this repo. Return a short summary
with file references, not the files' contents.
```

Or ask in the prompt: `Use the Explore subagent to find all callers of process_refund and summarise.` Built-in agent options for `agent:` are `Explore`, `Plan` and `general-purpose`.

### Plan for investigation, direct for implementation

```text
1. (plan mode)    "Investigate how to migrate from lib-a to lib-b. List affected files,
                   breaking API differences, and a step order."      # wrong boundaries are cheapest to catch here, before any edit
2. Review and approve the plan.                                      # human checkpoint on the design, not on 45 diffs
3. (direct)       "Execute step 1 of the plan."                      # scoped, well-understood steps need no further exploration
```

## Why this matters

Names and flags are illustrative; know the concept, not the exact parameter.

> [!IMPORTANT]
> **The principle**

Match the amount of upfront thinking to the cost of being wrong. When a task is architectural, spans many files or has several valid designs, the expensive mistake is a wrong structure discovered late, so exploration and design come first and changes second. When a task is small and well understood, a planning phase is pure overhead. Separately, discovery work that produces large amounts of intermediate output should be isolated so the main context keeps room for the actual work.

**The flow**

- The task-shape table is the whole decision procedure: scale (dozens of files), ambiguity (several valid approaches) and architectural consequence (service boundaries) point to plan mode; a clear stack trace in one file, or one validation conditional, points to direct execution.
- Plan mode lets Claude read and reason without editing; edits require approval. This makes wrong turns cheap: rejecting a plan costs a few minutes, while reverting 45 half-migrated files costs far more.
- "Complexity stated in the requirements is a reason to start in plan mode" addresses the habit of starting directly and switching only when trouble appears. By then edits already encode assumptions about structure, and the rework is the cost the plan would have avoided.
- The Explore skill with `context: fork` runs discovery in a read-only subagent and returns a short summary with file references. Mapping where authentication lives can mean reading dozens of files; in the main context that output would consume the window and degrade later phases of a multi-step task.
- The three-step migration shows the hand-off: investigation in plan mode (affected files, breaking differences, step order), a human checkpoint on the design, then direct execution one step at a time. Plan and direct are phases of one task, not exclusive choices.
- The SDK `permission_mode="plan"` expresses the same idea programmatically: exploration is allowed, and mutations go through an approval path.

## Trade-offs

- **Plan first vs iterate directly:** planning costs time upfront and pays off when structure is uncertain or changes are hard to reverse; for a single-file fix it only delays the result. Exploring by editing risks discovering dependencies after they have been broken.
- **Detailed upfront instructions vs plan mode:** writing out the target structure presumes the answer. It works only when the design is already known and validated; otherwise exploration should produce it.
- **Explore subagent vs inline exploration:** a subagent saves context but returns a summary that may omit details; inline reading keeps full fidelity at the price of window space. For discovery whose raw output is not needed later, isolate it.
- **One large plan vs staged plans:** very large plans can go stale; re-plan between phases when earlier steps change the picture.
- **Plan quality:** a plan is only as good as its exploration; approving it without review defeats the checkpoint.

> [!WARNING]
> **Exam traps**

- "Start with direct execution and let the implementation reveal the boundaries": rework risk is highest exactly when many files and design choices are involved. Rule: architectural, multi-file work starts with exploration and design.
- "Write comprehensive upfront instructions for each service and execute directly": assumes the right structure is already known without examining the code.
- "Begin directly and switch to plan mode if complexity appears": the complexity was already stated in the requirements; waiting wastes the point of planning.
- "Use plan mode for everything to be safe": over-applies the tool. Rule: a single-file bug with a clear stack trace is direct execution.
- "Read all files in the main conversation to understand the codebase": exhausts context during multi-phase tasks. Rule: isolate verbose discovery in an Explore subagent and keep the summary.
- "Plan mode and direct execution are mutually exclusive for a task": the stated pattern combines plan for investigation with direct for implementation.

## Quick check

- A teammate must replace a library used in 45 files, with API differences between versions. How should the work be structured? Plan mode to investigate affected files, breaking differences and order, then direct execution of the approved plan step by step.
- A stack trace points at a null dereference on one line of one function. Plan mode or direct? Direct; the scope is clear and a planning phase adds overhead without reducing risk.
- Mapping every caller of a function would print hundreds of lines and the session is long. What helps? Delegate the discovery to the Explore subagent so only a summary with file references returns to the main context.
